改造 · 小程序共用后台后的第一优先页 本页是小程序云打印与取件的唯一管理面。 2026-08-16 裁定小程序与一体机共用同一套后台（数据底座已同源：同一张 EndUser、 同一张 Order、同一套 AI/简历/权益模型）。 但本页是按一体机视角设计的，两个关键维度缺失—— ① 分不出订单来自哪个入口；② 看不到取件生命周期。

这两条不补，运营在小程序上线后会立刻遇到： 「用户问我的件怎么取，查不到」「老板问小程序转化率，算不出来」。

订单管理

本页管全渠道订单——一体机现场下单与小程序云打印下单在同一张表。 取件流程只存在于小程序云单；一体机是现场即时出纸，无取件环节。

当前为 mock 模式（VITE_API_MODE 不等于 http），页面数据和未接后端的操作不会写入数据库。

为什么必须加「渠道」而不是靠推断

M1 · 一切统计的前提

Order 现有字段只有 terminalId、endUserId、 paymentSource（资金性质：offline/free/manual_confirmed）、 payChannel（支付通道标识）——没有一个表示「这单从哪个入口来」。

目前只能靠推断，而且推不准： 一体机下单写 terminalId + endUserId（匿名时为 null）； 小程序云打印下单写的是同样的字段（terminalId 是用户选的门店）。

→ 「匿名 + 有 terminalId」只能判定为一体机；会员单完全分不出来。 而会员单恰恰是小程序的主体。
channel
建议取值 kiosk / miniapp_cloud；未来加入口（H5、支付宝小程序）时追加
写入位置
一体机 print-jobs.service.ts 建单处；小程序 member-print-order-create.service.ts 建单处
读取位置
admin-orders-readonly.controller.ts 加 channel 查询参数；service 层加展示字段
存量订单：迁移时可按「匿名 + terminalId → kiosk」回填一部分， 但会员存量单无法可靠回填——建议留空并在界面显示「未标注」，不要猜。

[pickupStatus, pickupCodeExpiresAt] —— 说明设计上就预期要按这两维查询
但 apps/admin/src/routes/orders/index.tsx 对 pickupStatus 是 0 处引用。 用户来问「我的件怎么取 / 为什么过期了 / 能不能延期」，运营在后台看不到任何取件信息。 索引都建好了却没人查，是明显的「后端做完、前端没接」。
为什么会有一批「本可取消却过期」的单（2026-08-16 由小程序线复核提供）： 后端 member-print-order-create.service.ts 的 cancel() 实现是完整的 （归属校验 + pickupStatus:'pending' 与 printTaskId:null 前置 + 免费单分支 + 写 member.print_order.cancel 审计）， utils/api.js 里也定义了 cancelCloudPrintOrder—— 但小程序页面 0 处调用。

→ 用户建了待到机订单只能等它过期，没有取消入口。 运营在本页看到的「已过期」里，有一部分本可以被用户自己取消。 这不是 Admin 的问题，属小程序线缺口，此处仅标注成因，便于运营判断。
待取件 pending 已亮码 claimed 已取件 used 已过期 expired 已取消 cancelled
处置动作需产品确认：过期件能否延期？能否重新生成取件码？退款与取件状态如何联动？ 这些是业务规则，不该由开发默认——本原型只画出可见性，不预设动作。

落地口径
  • 路由不变：仍是 /orders，加 2 列 + 2 个筛选。现有 539 行，加完后建议把筛选条抽成子组件。
  • M1 先做：Order.channel 是渠道对比、转化统计、问题定位的共同前提， 不做则本页新增的一切都算不出来。
  • M2 只画可见性，不预设处置动作：过期延期、重发取件码、退款联动都是业务规则，需产品确认。
  • 存量不猜：会员存量单无法可靠回填 channel，界面显示「未标注」， 不要按 terminalId 猜成一体机——那会污染统计。
  • 一体机无取件环节：「取件」列对 kiosk 单显示「—」，不是「无数据」，是业务上不存在。
  • Partner 侧暂不开放本页：若将来开放，必须按 orgId 限定本机构终端， 否则一家机构可见全平台会员订单（见 共用后台裁定 M3）。
