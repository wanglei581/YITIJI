改造 · 小程序共用后台后唯一有法律风险的一页 现状是「请求驱动」，缺「授权台账」。 本页管的是会员主动提交的导出 / 撤回授权请求； Admin 侧只有三个端点（GET data-requests / retry / reject）。

但没有任何「查某个用户授权了什么」的能力。 用户投诉「我没同意过用 AI 分析我的简历」时，运营查不了—— 只能等对方走完提交请求的流程。小程序放量后这类问询会显著增加 （微信登录 + resume/job-fit/consent + ai-consents/job_ai/revoke 三条授权链路）。

会员隐私

隐私请求（导出 / 撤回 / 注销）与 AI 授权台账。 授权在一体机与小程序共用同一张 UserAiConsent，本页两端都能查。

当前为 mock 模式（VITE_API_MODE 不等于 http），页面数据和未接后端的操作不会写入数据库。

来源渠道为什么显示「未标注」

需后端补

UserAiConsent 有 terminalId（可为 null）， 但它不等于渠道：

场景terminalId能否判定渠道
一体机上授权（已登录）有值可以
小程序里授权null只能靠 null 反推
一体机匿名场景可能为 null与小程序混淆
这与订单的渠道问题是同一型（见 订单管理 · M1）。 建议同一批做：给 UserAiConsent 也加渠道标识， 与 Order.channel 共用同一套取值（kiosk / miniapp_cloud …）， 避免两处各定一套枚举。

存量不猜：已有授权记录无法可靠回填，界面显示「未标注」， 不要按 terminalId 是否为 null 猜成小程序——那会把一体机匿名授权错误归到小程序。

合规用途

这是本页的立身之本
  • 争议举证：用户称「我没同意过」，可调出授权时间、版本与完整历史
  • 版本追溯：同意书改版后，能查出某用户当时同意的是哪一版
  • 撤回核验：确认撤回是否真正生效（revokedAt 有值且后续无新授权）
  • 范围核对：确认平台实际使用的 AI 能力是否都在已授权 scope 内
只读，不提供「代用户授权」动作。 Admin 可以查、可以导出举证，但不能替用户勾同意—— 那会让整套授权链失去法律意义。

落地口径
  • 路由不变：仍是 /member-privacy，加 1 个 Tab。现有 213 行，体积充裕。
  • 模型零改动即可起步：UserAiConsent 是 append-only 表、索引齐全， 只需补 GET /admin/member-privacy/consents?endUserId= 一个只读端点。
  • 只读：不提供「代用户授权」动作——那会让授权链失去法律意义。 撤回仍走会员本人的 me/ai-consents/:scope/revoke。
  • 渠道标识与订单 M1 同批做：UserAiConsent 与 Order 共用同一套渠道取值，不要两处各定一套枚举。
  • 存量不猜：无法可靠回填的显示「未标注」， 不按 terminalId 是否为 null 反推——一体机匿名授权同样为 null。
  • 「授权与调用不一致」比对建议做成常驻巡检： 它能自动发现「撤回后仍在调用」这类合规事故，价值高于人工抽查。
