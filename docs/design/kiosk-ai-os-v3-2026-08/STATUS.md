## 四、新硬件（摄像头 + 收音一体 / 嵌入式扫码器）

规划见 `hardware-camera-scanner-plan.md`。三条不能忘的：

1. **付款码支付后端已写好**（`POST /orders/:id/code-pay` + 自动收敛 cron），
   但设计稿一个字没有。不过**它不是「只差设计稿」** —— 还卡着屏幕识读率 ≥95% 的真机探测、
   微信/支付宝商户权限、退出 `FREE_MODE` 的授权、一分钱支付与退款验收。
2. **摄像头 ≠ 证件照页就能开放**。29 现在锁着的主因是**后端与输出链路为空**，不是没有取像。
   建议分两步：先开「上传已有照片 → 体检 → 换底 → 排版」，摄像头与拍摄环境验收后再开「现场拍摄」。
   没有照片纸与色彩验收之前，**只能叫「证件照排版/数字文件」**，不能宣称满足正式证件办理要求。
3. **不是所有二维码流程都该改成扫码器**。登录、手机传文件、招聘会签到是
   「机器 → 手机」的接力方向，扫码器替代不了手机接收。

## 六、方法上的教训（比结论更值得留下）

本轮**四次**发现「检测器自己是瞎的」，每一次都曾让报告显示「全绿」：

| 盲区 | 后果 | 怎么发现的 |
| --- | --- | --- |
| `stage.js` 的 `audit()` 忘了 `return` | 9 项基础检查全部不可见 | 读代码时偶然看到 |
| 回归台只统计**顶层数字键** | 嵌套的留白/卡内溢出/假入口全漏，报「1096 组合 0 缺陷」 | 与整改代理的报告对不上 |
| 「假入口」**专门跳过 `<button>`** | 「真按钮但没接线」永远检不出 | **所有者亲自逮到**「手机扫码点了没反应」 |
| 「卡内空洞」只看底边 | 贴底的绝对定位页码让纸样永远读 0；居中构图被误判成没写完 | 整改代理拒绝「补假页码消数」时带出来 |

由此定下三条纪律，写在这里而不是留在记忆里：

1. **检测器自己必须被检测。** 每加一项检查，都要用「造一个真缺陷 → 它必须报出来」验一遍。
   本轮写「死按钮」检查时，第一版因为 `<button>` 默认 `type="submit"` 而**永远报 0**，
   就是靠这个反例测出来的。
2. **不可复现的检测器比没有更糟。** 死按钮检查第二版同一份代码连跑四次得到 0/72/67/99
   （探测本身改变了现场），改成「扫描出候选 → 每个候选在新装载的干净页面上单独复验」才稳定。
3. **噪声等同于失明。** 误报会让人开始不信报告，真缺陷跟着一起被忽略。
   所以「疑似未登记的轴」从几十条降到 0、「联动接线·声明条数」这种统计值不再当缺陷报。
