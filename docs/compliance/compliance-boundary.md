## 一、背景说明

当前公司**暂无人力资源服务许可证**。

本系统的定位是：AI 求职打印服务终端。公司是**设备与软件供应方**，向求职者提供我们自己的工具服务（AI 简历、模拟面试、职业规划、打印扫描），**不运营招聘信息，不构成招聘平台**。

2026-09-26 起托管选 a：我方云上不存岗位、招聘会、企业资料；一体机只在运营机构自己的终端上放该机构官方渠道的二维码；政策不属于招聘信息，由机构在我方云上自行发布（见 §1.1）。小程序首发不放岗位、招聘会、找企业；政策与职业圈动态首发也不放（产品负责人 2026-09-25 拍板，政策仍供一体机使用）。

代码切换见 [next-tasks.md](../progress/next-tasks.md) 3.13–3.15。切换完成前，下文 §二–§四 关于岗位、招聘会数据的规则仍约束现有代码，但**不得据此新增功能**。

开发前必须阅读本文档，确认不触碰合规红线。

### 1.1 2026-09-25：岗位 / 招聘会信息展示本身的许可证风险（检索意见，以律师与主管部门书面答复为准）

商业收口专家团（Grok 联网检索官方原文，Agy、Claude 复核）的结论：**「只展示岗位、不做投递」同样可能需要人力资源服务许可证**，此前「第三方信息入口」的定位不能当作免证依据。

- 《网络招聘服务管理规定》（人社部令第 44 号）第二条对「网络招聘服务」的定义不以投递、收简历为要件，第九条要求取得人力资源服务许可证，第十条要求服务范围注明「开展网络招聘服务」：<https://www.gov.cn/gongbao/content/2021/content_5588822.htm>。
- 人社部等五部门 2026 年 1 月《关于规范网络平台招聘类信息发布的通知》：通过互联网站、应用程序等发布招聘信息，应依法取得人力资源服务许可证：<https://www.mohrss.gov.cn/xxgk2020/fdzdgknr/zcfg/gfxwj/jy/202601/t20260113_565366.html>。
- 微信小程序：涉及求职/招聘信息展示须选择「生活服务-求职/招聘」类目并提交人力资源服务许可证，官方社区多次答复「只展示」也不例外：<https://developers.weixin.qq.com/miniprogram/product/material/>。
- 一体机不受微信类目约束，但同样通过信息网络向公众展示；能否按《人力资源市场暂行条例》第十八条的「供求信息发布」备案处理，**不确定**，只接受属地人社部门书面答复。

**产品负责人决定（2026-09-25）：** 许可证由产品负责人自行办理；一体机上的招聘会保留；小程序首发不上岗位、招聘会、找企业页面，按非招聘类目提审，拿证并通过求职/招聘类目后再加回；一体机岗位列表是否保留待产品负责人确认。本节不放宽第二节任何一条禁止项。

**产品负责人决定（2026-09-26）与三方评审结论（Claude 汇总；Grok 代码清点与联网检索各一路；Agy 两轮反方审查；以律师与主管部门书面答复为准）：**

- **决定：** 岗位、招聘会、企业资料、政策这类招聘相关内容，改由机构端的运营机构（公共就业服务机构、高校就业中心、持证人力资源服务机构）自己审核、发布、署名；我方管理员后台对这些内容只保留紧急下架。
- **依据（原文已核）：** 44 号令第十一条把「为劳动者介绍用人单位」「为用人单位推荐劳动者」「举办网络招聘会」列为网络招聘服务，第十七条把用人单位材料的真实性、合法性审查义务放在从事网络招聘服务的机构身上；上文五部门通知的文号是人社厅发〔2025〕60 号；江苏 2026-05 典型案例警示「互联网平台企业搭建平台供用人单位自行发布招聘信息，均应当申领人力资源服务许可」（南京市人社局转载）；网络安全法 2025 年修正、2026-01-01 施行后，第四十九条规定网络运营者发现违法信息应停止传输、消除、保存记录并报告——紧急下架是这项义务，本身不构成发布者身份。Grok 抽查 5 份 2025–2026 年公告：就业信息系统、就业一体机类政府采购的资格条件不要求人力资源服务许可证；招聘会承办、劳务品牌类政府购买服务要求持证。
- **现状差距（候选 `e9f6e4bed` 代码实测）：** 审核与发布只在我方管理员侧；管理员还能新建企业资料并挂岗位、新建线下机构并替它建岗位、改招聘会正文与展位资料、批量发布；公开读取不按终端所属机构隔离，AI 推荐岗位的候选池跨机构，小程序读取不带终端；企业来源方、招聘会主办方这两类机构绑定终端时不校验类型。整改见 next-tasks.md 步骤 3.11–3.15。**整改完成前，管理员侧现有审核发布仍是唯一的发布路径；不得在管理员侧新增代建或发布招聘类内容的功能；本文件第二节及以下规则照旧。**
- **三方建议（9/26 晚已由产品负责人拍板采纳，见下一条）：** 公司做「设备与软件供应方」（卖终端、随机交付软件、按年收维保），不做招聘信息运营方，不承接需要持证的就业服务外包；收费不与岗位、招聘会、浏览、投递、入职挂钩；AI 岗位推荐只在运营机构的终端上、只用该机构的岗位、以该机构名义提供，公司自营点位与小程序不做，功能名称与说明文案交律师确认；律师书面同意前，不在我方云上托管多家机构的招聘数据。
- **产品负责人拍板（2026-09-26 晚，3.11「按推荐执行，托管选 a」）：** 公司做设备与软件供应方，收费只有设备款与维保费；一体机只放运营机构官网或官方渠道的二维码，**我方云上不存岗位、招聘会、企业资料**，完整招聘功能只在客户私有化部署（b）里由客户运营；客户机器上的打印由客户买断额度或走客户自己的商户号；试点在自营点位时招聘模块整体关闭。官方渠道二维码的边界：链接域名只能落在机构入驻时核验过的该机构官方域名内（入驻交盖章确认函）；一体机不打开外部网页；二维码下注明渠道提供方。政策不属招聘信息，仍在我方云上由机构自行审核发布，我方只留紧急下架。选 a 的代价已告知产品负责人：招聘会现场的展位图、到场码、拜访单与 AI 岗位推荐在我方云上暂停；岗位匹配改为用户自填岗位要求。整改见 next-tasks.md 3.13–3.15；整改完成前，本节「现状差距」一条照旧有效。

#### E. AI 内容边界

- AI 简历建议与模拟面试不得出现基于性别、年龄、婚育、民族、户籍、健康状况的歧视性表述；AI 不得替求职者编造学历、工作经历或证书。这是产品红线：《就业促进法》第三章主要约束用人单位与职业中介，不要写成所有 AI 软件都直接适用；自动化决策的公平性可对照《个人信息保护法》第二十四条。

且会直接触碰第二节「绝对禁止的功能」。二者互为表里。

#### 岗位有效期：读取时派生，不落库

条款 1 的「标注有效期限或者及时更新」在实现上落为：**`validThrough` 已过的岗位不再对求职者展示**。

- 判定只在**读取时**进行（`services/api/src/jobs/job-validity.ts`），不写库、无定时任务、无迁移。
- 求职者可见路径（`/jobs`、`/jobs/:id`、`/jobs/requirement-stats`、找企业「在招岗位 / openJobCount」、AI 岗位推荐候选池）一律过滤。
- 管理端 / 机构端**照常看得见**过期岗位并标注「已过期」，`publishStatus` 保持库里真值 `published`，「下架」按钮不受影响 —— 运营要能发现并处置。
- 门禁：`pnpm --filter @ai-job-print/api verify:job-validity-expiry`。

> **生产存量数据的处置不在技术侧**：读取过滤不改动任何一行数据。
> 已过期岗位是否下架、是否联系来源机构更新，属运营动作，需产品负责人具名授权。

### 4.3B 已知缺口（尚未实现，登记备查）

- ~~招聘人数（`headcount`）字段缺失~~ **已补齐（2026-08-18）**：此前该字段是「两端都接了、中间断掉」——
  `WebhookJobItemDto` / `ImportJobItemDto` 已接收并校验后丢弃（机构报送在静默消失），
  而 `ExternalJobDTO.headcount` / `JobListItemDto.headcount` 已在读取契约里声明且恒为 `undefined`。
  现已补 `Job.headcount Int?`（两份 schema + 两份迁移），并贯通 Excel 确认导入 / Partner 导入 /
  Webhook / API 拉取四条链路，Kiosk 详情页展示，缺值显示「来源平台未提供」（不补 0 / 不估算）。
  门禁：`verify:job-headcount`。
- **发布路径完全不校验字段完整性（条款 1 的其余五项）**。条款 1 要求六项：用人单位基本情况、
  招聘人数、招聘条件、工作内容、工作地点、基本劳动报酬。当前只有 `company`（用人单位）与
  `city`（工作地点）实际必填（`JOB_REQUIRED_FIELDS` = externalId/title/company/city/sourceUrl）；
  `salary` / `salaryMin` / `salaryMax`（基本劳动报酬）、`description`（工作内容）、
  `requirements`（招聘条件）**全部可空且不阻断发布**。
  `JobQualityService` 已经算出 `qualityLevel: ready / partial / insufficient`，
  但 `jobs-admin.service.ts` 的 `publishJobSource` **完全不读它** —— 一条 `insufficient`
  岗位照样能发布上线。补法应是在发布闸门加字段完整性判定（可复用 content-trust 的
  「预览阶段分流 + 单条发布拦截」双层形态），属产品决策，需先定「哪几项缺失时禁止发布」。
- **「标注有效期限**或者**及时更新」的第二条腿未落地**。条款 1 是二选一：本轮实现的是第一条腿
  （`validThrough` 已过即不展示）。第二条腿「及时更新」对应数据新鲜度：`job-quality.service.ts`
  已按 30 天窗口算出 `syncTimeStale`，但它**只进质量快照与按来源聚合的 `staleJobs` 计数**，
  不影响任何求职者可见路径。因此一条 `validThrough = null` 且 `syncTime` 是半年前的岗位，
  两条腿都不满足，却仍照常公开展示。
  注意本轮**刻意**对 `validThrough = null` 放行（缺有效期是数据质量问题，不等于失效，
  按缺失即判过期会误杀大批仍在招的岗位），所以这个缺口不会被 `verify:job-validity-expiry` 覆盖。
- **来源方岗位正文的虚假宣传检测（条款 3）**：现有禁词门禁只扫我方 UI 文案，
  不扫导入进来的岗位正文中的「高薪」「保录」类表述。
- **歧视性表述筛查的能力边界**：确定性关键词只能抓写得直白的部分，
  隐晦表述抓不到；`contentFlags` 为空**不代表**内容合规，人工审核仍是判定方。

### 4.4 系统只允许记录的用户行为

| 允许记录 | 禁止记录 |
|---------|---------|
| 浏览岗位 | 企业筛选结果 |
| 收藏岗位 | 第三方后续处理信息 |
| 外部跳转（记录跳转行为，不记录投递结果） | 面试邀约记录 |
| 打印记录 | 候选人评价 |
| AI服务调用记录 | 企业端任何数据 |
| 招聘会浏览记录 | 第三方平台后续结果 |
| 政策浏览记录 | 官方平台办理结果 |
| **用户本人自填的求职进度**（见 §4.4A） | 由平台或第三方写入 / 更新的求职进度 |

2026-06-12 已接真的浏览与跳转记录边界：

- `BrowseLog` 仅记录登录会员本人浏览过的岗位 / 招聘会 / 政策目标快照。
- `ExternalJumpLog` 仅记录登录会员本人打开过的来源平台投递入口、来源平台预约入口或官方入口。
- `targetTitle`、`sourceName`、`sourceUrl`、`externalId` 必须由服务端从已审核且已发布的目标对象补齐，前端不得伪造。
- 记录失败不得阻断用户浏览、查看二维码或打开来源平台入口。
- 不记录第三方平台上的投递结果、预约结果、企业查看、筛选、面试或任何第三方后续处理信息。
- `BrowseLog` / `ExternalJumpLog` / `Favorite` **本身不得新增任何求职进度或投递状态字段**。§4.4A 的自填进度是独立模型，不是给这三张表扩列。

### 4.4A 用户本人自填的求职进度（2026-09-02 新增，经产品负责人具名授权）

**判定原则：合法性由「谁写的」决定，不由字段名决定。** 同样一个「已投递」，用户自己敲进本系统的是**个人求职记事本**；由企业、来源平台或本平台写入的是**招聘闭环数据**。前者是求职者个人服务，不构成职业中介；后者需人力资源服务许可证。§4.4 表格里「不记录投递结果」这一句，管的一直是后者 —— 即**不从第三方回流结果**，而不是禁止用户记录自己的事。本节把这个区分写明，不放宽任何一条原有红线。

先例：小程序 `apps/miniapp/pages/job-tracker/` 早已提供五列看板（意向 / 已投递 / 面试中 / 已拿Offer / 已拒绝），纯 `wx.getStorageSync` 本地存储、不回传后端，`feature-scope.md` 已定性为「仅为本人本地记录，不是平台投递」。本节是把同一性质的能力接入后端与一体机，使其跨设备可用。

允许：

- 登录会员**本人手动**创建、修改、删除自己的求职进度条目。
- 关联本站**已审核已发布**岗位时，公司名 / 岗位名 / 来源名由服务端从该岗位派生（防前端伪造）；用户手填时由用户自述。
- 纳入「我的」个人资产，可导出、可删除，随账号注销一并清理。

禁止（任一触发即为越界）：

1. **服务端从任何第三方来源写入或更新进度状态。** 没有回流入口，就没有招聘闭环。
2. **向企业、来源机构或任何第三方回传、展示、导出该数据**，含合作机构后台。系统不提供任何对外读取接口。
3. **按岗位 / 企业 / 来源机构聚合自填进度并对外呈现。** 逐条不回传但按企业出「投了多少人、几个到面试」，等于重建候选人漏斗，同样越界。平台内部运营统计亦不得下钻到可识别个人的粒度。
4. 在 `BrowseLog` / `ExternalJumpLog` / `Favorite` 上扩展进度或状态字段（见 §4.4 末条）。
5. 用户可见文案暗示平台参与投递、代投或掌握投递结果。文案主语必须是用户（「记录一次投递」），且继续遵守 §三 禁词。
6. 存储简历文件或将简历与进度条目绑定后提供给任何第三方。

实现约束与门禁：本能力落为独立模型 `JobApplication`，其 `channel` 在无证期只接受「用户自报的站外投递」一个取值，`statusSource` 只接受「用户自填」，`resumeFileId` / `consentId` 恒为空且无写入路径 —— 逐条由 `verify:job-application-track` 断言。平台内投递（形态 A）另受 `src/common/recruitment-capability.ts` 的许可证闸门管控，与本节无关且不因本节放宽。设计依据见 [recruitment-closure-license-gated-plan-2026-09.md](../product/recruitment-closure-license-gated-plan-2026-09.md) §3。

### 4.5 企业展示（CompanyProfile）边界（2026-06-12 新增，长期红线）

企业展示 = 企业风采 / 来源企业与岗位导览，**不是招聘平台、不是企业发岗平台**：

| 只能做 | 不能做 |
|--------|--------|
| 展示来源机构提供并经管理员审核发布的企业信息（含 logo/封面/宣传片，媒体随企业资料一并审核） | 企业自主入驻、企业 HR 后台 |
| 企业关联「已审核已发布」岗位的导览 | 平台内投递、企业收简历 |
| 「去来源平台投递 / 扫码投递 / 去来源平台查看」外部引导 | 企业查看/筛选候选人、面试邀约、Offer 管理 |
| 详情页指标（在招岗位/所在城市/员工规模/展位号）按 Admin 开关展示，数据为空不造假 | 写死统计数字、展示假企业/假岗位/假视频 |
| 岗位匹配参考：仅本人三档参考（较高/中等/偏低），不代表录用结果 | 百分比匹配度、录用概率、结果回传企业 |

- 企业数据必须含来源四要素（source_org_id / external_id / source_name / source_url），默认 `pending + draft`，管理员审核通过后才能发布。
- Partner 仅维护本机构来源数据（导入/编辑一律回 pending+draft 强制重审）。
- 浏览企业 / 打开企业来源页进入 §4.4 的 BrowseLog / ExternalJumpLog（targetType=company_profile，action=external_open），同样不得记录任何投递/办理结果。

### 4.6 线上平台导航目录边界（2026-08-10 新增）

> **2026-09-26：** 一体机原来写死的 4 个商业招聘网站按步骤 3.2 下线；这一页按 3.14 改成「本机构官方渠道」，只放运营机构自己官方域名的二维码。

线上平台目录只提供经管理员核验的第三方官方首页或官方招聘入口，不等于数据接入源、合作关系或平台内招聘服务：

- 目录 CTA 只允许“前往官方平台查看 / 扫码打开来源平台”；进入具体岗位后才可使用“去来源平台投递 / 扫码投递”。
- 必须核验 HTTPS 官方域名及重定向最终域；未建立书面合作关系时禁止“合作平台、官方合作、认证伙伴”等表述。
- 目录发布不能自动启用 JobSource 或授予 Partner 数据接入权，数据源启用也不能自动发布目录项。
- 只允许记录 `external_open`，由服务端补齐目标快照；不记录第三方投递、预约或后续处理结果。

### 4.7 线下机构信息边界（2026-08-10 新增）

- CTA 只允许“查看机构信息 / 查看门店指引 / 前往机构自行咨询”；不得使用“应聘到店办理、预约登记、平台代办、代收费用”等表述。
- 机构资料审核、资质核验和每条岗位审核是三道独立门禁；没有真实有效资质时不得显示核验徽章。
- 电话、地址、营业时间由服务端从已审核发布对象补齐；只记录 `external_open`，不记录咨询、到店、收费、投递或办理结果。
- 当前岗位仍必须满足 §4.1 来源四要素和 HTTPS 来源入口；无 `sourceUrl` 的线下岗位在正式修订本合规边界并完成法务确认前保持 fail-closed。

## 五、文件安全要求

### 5.1 直传对象完整性

- COS 预签名 PUT URL 一经签发，在其自身到期前不能由本 API 撤销；不得把 `complete` 的成功响应表述为已作废该存储侧凭证。
- `completeUpload` 记录服务端计算的 SHA-256 基线；后续受控读取、下载授权和打印建单必须复核。内容变化，或因超过服务端嗅探阈值未能得到 SHA-256，均按 `FILE_CONTENT_CHANGED` fail-closed，文件标为隔离并留下审计。
- 本地代理上传的 raw PUT 仍由上传态 CAS 保护；上述 COS 限制不改变它的覆盖拒绝语义。

用户文件（简历、扫描件、证件照、身份证复印件）属于敏感数据，必须遵守：

| 要求 | 说明 |
|------|------|
| 临时签名 URL | 所有文件访问必须使用带时效的签名链接，不得使用永久公开链接 |
| 有效期限制 | 敏感文件签名 URL 有效期建议不超过 30 分钟 |
| 自动清理 | 系统应支持配置文件自动过期清理策略 |
| 管理员访问日志 | 管理员每次访问用户文件必须记录日志 |
| 不长期保存敏感文件 | 身份证、简历等文件不应永久保存，设置清理周期 |
| 删除日志保留 | 文件删除后必须保留删除操作日志（不保留文件本身） |

## 六、打印接口安全要求

奔图 CM2800ADN/CM2820ADN 系列对接时，安全规范如下：

| 要求 | 说明 |
|------|------|
| appKey / appSecret 只存服务端 | 禁止在前端代码、环境变量文件中保存 |

## 八、营销 / 权益 / 套餐 / 补贴 / 支付合规边界

> 新增于 2026-06-07，关联规划：[next-tasks.md](../progress/next-tasks.md) §个人资产中心 + 权益活动 + 服务套餐 产品规划（Phase C-2 ~ C-6）、[feature-scope.md](../product/feature-scope.md) §六。
> 本节为「个人资产中心 / 权益活动中心 / 服务套餐 / 支付核销 / 政策补贴」补充合规边界，**不推翻 §二~§七，仅做维度补充**。

### 8.1 招聘闭环红线（重申，永不突破）

权益活动、服务套餐、企业赞助等任何商业化能力，**都不得**借机引入 §二 的 8 类招聘闭环功能（一键投递 / 收简历给企业 / 企业筛选候选人 / 面试邀约 / Offer 管理 / 候选人推荐 / 自营招聘闭环 / 企业发岗直收简历）。

### 8.2 补贴类功能边界

| 只能做 | 不能做 |
|--------|--------|
| 政策说明 | 承诺补贴到账 / 必得 |
| 材料清单 | 未授权代用户申请 |
| 官方申请入口（外链） | 长期保存身份证 / 银行卡 / 社保等高敏材料 |
| 申请材料打印 | 把「补贴券核销」包装成「政府补贴金发放」 |
| 申请指引 | — |

- 「我的权益」中的「补贴资格提示」只是**信息指引**，不得展示金额到账、发放状态等承诺性文案。
- 补贴申请材料如含身份证 / 银行卡 / 社保等，沿用 §五文件安全：临时签名 URL + TTL 清理，不长期留存。

### 8.3 企业赞助边界

- 企业可赞助权益（如赞助打印券 / 材料包），**仅体现为品牌露出 + 权益发放**。
- 企业**不得**通过赞助活动获取用户简历、候选人数据或任何可回流企业的求职者材料。
- 赞助不得形成「求职者 → 企业」的简历投递 / 候选人池。

### 8.4 服务套餐边界

- 套餐**只卖工具服务和打印服务**（AI 简历优化、面试训练、证件照、打印额度等），**不卖「录用结果」**。
- 套餐文案**禁止**「保面试 / 保录用 / 补贴必到账 / 名企内推 / 代投简历」等承诺。
- AI 模拟面试 / 面试训练结果**只给求职者本人**，不推送企业（沿用 feature-scope §六）。

### 8.5 支付 / 核销 / 退款边界

- 支付凭证 / 密钥（微信、支付宝、校园卡等）**只存服务端**，前端不得保存，沿用 §六打印接口安全的密钥原则。
- 券 / 免费次数 / 补贴券**核销必须幂等 + 落库审计**；**免费单也落库**。
- 退款**幂等**；**不得把支付异常伪装成打印任务状态**。
- 「补贴券核销」限于平台内服务 / 打印券，**不等于、也不承诺政府补贴金到账**。

### 8.6 营销 / 权益功能开发检查清单

- [ ] 是否新增了任何招聘闭环功能（投递 / 收简历 / 候选人 / 面试 / Offer）？
- [ ] 补贴类是否只做指引（说明 / 清单 / 官方入口 / 打印 / 指引），没有承诺到账或代申请？
- [ ] 企业赞助是否杜绝了简历 / 候选人数据回流企业？
- [ ] 套餐文案是否无「保录用 / 保面试 / 补贴必到账」承诺？
- [ ] 支付密钥是否只在服务端？券核销 / 退款是否幂等且落库审计？
- [ ] 高敏材料（身份证 / 银行卡 / 社保）是否只用临时签名 URL + TTL，未长期保存？

### 8.7 AI 简历优化 / 导出 / 收费边界（2026-06-29）

AI 简历诊断、优化、生成、导出、模板重排和打印属于工具服务，可以作为套餐、单次服务、优惠券或会员权益售卖；收费对象是服务处理、成果导出、文件保存和打印，不得包装成招聘结果。

允许做：

- 向求职者本人展示简历诊断、优化建议、优化前后对比、最终预览、在线编辑、AI 一键调整、导出和打印。
- 按服务成果收费：如最终优化成果导出、PDF / PNG / DOCX / TXT / Markdown 下载、长期保存、二次优化、打印页数、套餐包或券核销。
- 对已付费且未修改的同一成果，在有效保存期内允许重新下载 / 重新打印入口；是否再次收取打印费按打印订单和套餐规则执行，不能重复扣同一导出权益。同一成果必须由服务端成果版本 ID、内容哈希或 `FileObject` 标识判定，导出 / 打印权益核销以该标识作为幂等键；内容修改生成新版本，新版本按服务规则重新计费或核销。
- 使用系统内已审核已发布岗位，或用户手动粘贴岗位名称 / JD / 专业方向作为本人简历优化参考。
- 将优化后或派生成果物保存为 `FileObject`，使用临时签名 URL 预览 / 下载，并按文件保存期限策略进入本人文档或简历记录。

禁止做：

- 承诺「保面试 / 保录用 / 录用概率 / 通过率 / 名企内推 / 代投简历 / 100% 格式保真」等结果或保真承诺。
- 为企业生成候选人池、向企业或合作机构发送求职者简历、优化稿、诊断报告、联系方式或画像。
- 在 AI 简历优化页新增平台内投递、平台收简历、候选人推荐、企业查看简历、企业筛选、面试邀约或 Offer 管理。
- 将用户粘贴的外部 URL 自动抓取后当作已审核岗位入库，或把任意外部 URL 触发为来源平台投递 / 预约记录。
- 让 AI 新增未经用户确认的学校、公司、证书、时间段、薪资、获奖、工作经历等事实。

外部岗位信息边界：

- 首期只支持系统已审核岗位和用户手动粘贴 JD；外部 URL 仅可作为用户提供的参考文本来源提示，不自动抓取。
- 后续如支持 URL 解析，必须先完成来源白名单、robots / 频控、内容安全、日志脱敏、来源展示、用户确认和合规审查；解析结果仍只服务本人优化，不构成平台岗位发布或投递入口。
- 系统不得把用户简历、优化稿或 JD 分析结果回传给外部招聘来源、企业或合作机构。

文件与格式边界：

- 原始简历、语音转写文本、优化稿、导出图片和 PDF 都属于用户求职材料，沿用 §五文件安全要求和 [会员个人数据留存矩阵](./member-personal-data-retention.md)。
- 优化后 PDF / PNG / 打印预览应来自同一模板渲染链路，以保证最终成果物一致；这不等于承诺还原用户上传原件的 Word 样式或排版。
- 导出为图片可以提高最终预览和打印一致性，但图片格式不可编辑；页面必须避免把图片导出描述成可编辑 Word 原文或原版式 100% 还原。
- DOCX / TXT / Markdown 属于模板渲染派生的可编辑内容结构导出，不是用户上传原件，不保证与 PDF / PNG 像素一致，也不承诺还原上传原件的 Word 样式。
- 页面需要向用户展示成果物保存期、到期或长期保存状态；长期保存必须有用户主动确认和条款版本记录。

收费与订单边界：

- 付费动作必须先展示价格、权益抵扣、优惠券抵扣、套餐消耗、打印费用和退款/重试规则。
- 免费次数、优惠券、套餐权益和 0 元单也必须幂等落库并保留审计，不得只靠前端状态判断。
- 支付凭证、退款、对账和券核销只在服务端处理；不得把支付异常、AI 异常或导出异常伪装成打印任务状态。
- 退款与重复扣费处理应按订单 / 支付域建模，不挂靠 `PrintTask` 本身；打印任务只承载打印履约状态。

### 8.8 机构侧收费与机构数据回流边界（2026-07-31 新增，长期红线）

前面 §8.1–8.7 已覆盖商业化的总体约束（§8.1 任何商业化能力、§8.3 企业赞助、§8.7 简历优化 / 导出收费边界）；本节**专门补充**两件此前未单独成文的事：**向合作机构 / 线下机构收费的计价基础**，以及**给机构回流什么数据**。这是当前公司无人力资源服务许可证条件下最容易踩线的两处。

#### 8.8.1 机构结算计费基础

**禁止**按招聘成果计费。下列任一计价方式都构成效果付费招聘中介：

- 按候选人数 / 简历数 / 投递量计费
- 按面试量 / 到面率计费
- 按 Offer 量 / 入职量 / 成单量计费
- 按「推荐成功」「匹配成功」抽成
- 阶梯定价中把上述任一指标作为档位依据

**「不按成果计费」是必要条件，不是充分条件。** 许可要求并不以是否按结果收费为前提——即使完全按曝光量收费，只要收的是「为用人单位发布 / 展示招聘信息」这件事，仍可能落入需许可的网络招聘服务范围。因此计费基础必须分成两类：

**第一类：与招聘内容无关，可作为候选计价口径**

- 终端服务费 / 场地服务费（按终端数、按点位、按时长）
- SaaS 订阅费（按账号数、按功能模块、按周期）
- AI 工具使用量（按调用次数 / token / 时长，收的是算力与工具服务）
- 打印与耗材（按页数 / 份数）
- 非招聘类内容的接入与运维服务（政策公告、机构介绍等）

**第二类：涉及招聘内容，许可前置，未取得许可前不得收费**

- 岗位 / 招聘会 / 校招信息的接入、发布、展示、置顶、推荐位
- 按招聘内容曝光量（展示次数）计费
- 按投递入口外部跳转次数计费
- 任何以「让更多求职者看到这家企业的岗位」为卖点的付费

第二类**必须先由法务与属地人力资源社会保障主管部门确认口径、取得所需许可后**才能实施收费；技术侧可以先把计量能力做出来（曝光 / 跳转统计本身用于运营与对账是允许的），但**不得在许可结论明确前开启对应收费项**。相关规定至少包括《网络招聘服务管理规定》《人力资源服务机构管理规定》及人社部关于规范网络平台招聘类信息发布的要求；具体适用以法务意见和主管部门答复为准，本文档不作法律结论。

合同、价目、发票口径必须与上述分类一致，不得在合同外用「按效果调整」的口头或补充约定绕过，也不得把第二类收费包装成第一类（例如把岗位置顶费写成「SaaS 增值模块」）。

#### 8.8.2 给机构的**用户行为类**数据只能是聚合数据

**适用范围**：本节只约束**涉及 endUser 行为、画像与使用分析**的数据。机构本身的业务对象数据不在此列——机构资料、自己配置的数据源、自己维护的岗位 / 招聘会 / 政策公告、导入批次与同步日志、终端设备状态等，仍按 [CLAUDE.md](../../CLAUDE.md) §9「合作机构后台」范围正常提供对象级明细。

对机构的任何**用户行为类**报表、导出、API 回传：

- **只给聚合统计**，不给 endUser 行为明细，不给可重识别到个人的行为序列
- 必须设**最小样本阈值**：低于阈值（建议 N=5）的分组不展示数值，显示「样本不足」
- 不给求职者身份、联系方式、简历内容、诊断 / 优化 / 面试报告、画像标签
- 不给「谁看过我的岗位」这类可定位到人的清单
- 曝光 / 跳转统计只表示「内容被展示 / 被打开来源平台入口」，**不得表述或暗示为投递、报名、预约成功**
- 统计必须有保留周期，到期清理；导出须记审计日志

#### 8.8.3 计费依据的可靠性要求

- **不得用运维观测日志作为计费、履约或退款依据。** `AiServiceLog` 是 best-effort 写入（失败只告警不阻断）且成本为估算值，只能用于运维观测与趋势判断。
- 计费必须走独立履约账本：预占 → 履约 → 提交，失败释放；具备幂等键、不可丢失写入、可审计、可对账。
- 缓存命中、重试、超时、异常降级都必须有明确的「是否扣费」定义，且以服务端判定为准，不依赖前端状态。

#### 8.8.4 开发检查清单（机构侧）

- [ ] 计费基础是否完全避开候选人 / 投递 / 面试 / Offer 指标？
- [ ] 合同、价目、发票口径是否与允许的计费基础一致，无「按效果」补充约定？
- [ ] 给机构的每一项数据是否都是聚合值？是否设了最小样本阈值？
- [ ] 曝光 / 跳转文案是否明确不等于投递 / 预约成功？
- [ ] 计费是否走独立履约账本而非运维日志？幂等键与审计是否齐备？
- [ ] 机构导出 / API 回传是否记审计日志、是否有保留周期？

### 8.9 简历智能上下文与 AI 辅助填写边界（2026-08-06 新增，长期红线）

“用简历建议填写”属于只服务求职者本人的工具能力，不是自动决策或代办能力。所有页面必须遵循 [简历智能上下文与 AI 辅助填写契约](../product/resume-context-ai-assist-spec.md)。

只能做：

- 从本人简历中提取有原文证据的字段，并标注来源、可信等级和是否经过标准化。
- 将行业、岗位、经验段和关键词作为待核对建议，不包装成事实。
- 默认只填空字段；覆盖已有值必须显示差异并逐项确认。
- 在页面草稿内应用建议，并允许修改、拒绝和撤销。
- 按受控页面白名单返回最少字段，AI 失败时回退手填。

永远不能做：

- 静默覆盖用户值，或把模型推断写成已确认事实。
- 自动投递、预约、报名、签到、外跳、支付、退款、打印提交、录音、签名盖章或官方申报。
- 预测录用概率、面试通过率或政策资格，或承诺办理结果。
- 推断性别、民族、婚育、健康、残障、宗教、政治面貌、户籍性质、低保、失业登记或社保状态。
- 将简历、画像、字段建议、诊断、匹配或训练结果提供给 Admin、Partner、企业、校方、招聘会主办方或第三方工具。
- 用岗位 AI 授权、文件保存授权或其他同意替代专用的画像长期复用同意。

公共终端中，字段值不得写入 `localStorage`、`sessionStorage`、IndexedDB、URL、埋点、错误日志或普通审计 payload。会话清场、撤回同意、删除来源简历、删除相关 AI 记录、账号删除或 TTL 到期后，画像必须同步失效；长期复用必须单独同意、加密、可撤回、可删除且不得晚于来源简历到期时间。

开发检查清单：

- [ ] 每个字段是否有明确分类：原文事实、标准化事实、派生建议或用户偏好？
- [ ] 事实建议是否能回指本人可见证据，且可信等级未高于 OCR/提取可信等级？
- [ ] 是否默认只填空字段，低可信和推断项默认不选，并提供撤销？
- [ ] 页面是否只获得其白名单字段，没有通用任意路径或任意动作接口？
- [ ] 是否完全隔离企业、Partner、校方和第三方工具，且日志不含字段值或原文？
- [ ] 是否覆盖退出、切换账号、待机、硬隐私超时、BFCache、删除和撤回后的清场？
