# 计价与权益：后端现状核对（2026-08-11）

**触发**：产品负责人指出「活动优惠、金额、卡券、优惠券、活动这些不是固定的，是根据后台调整来作为选项和显示的结果」，并说明后端正在改造、正在与前端做对接。

**结论先行**：方向正确，但**「给结算页加一个用券按钮」当前为 NO-GO**。原因不是页面没做，是后端已有的核销语义只支持「整单免单」，把「按页额度」接上去会算错账。

本文只记**读源码复核过**的事实与可执行结论。每条都注明出处，便于后端同学直接定位。

---

## 一、P0：一张「剩 7 页免费额度」会整单免单，且只扣 1

`services/api/src/benefit-redemption/benefit-redemption.service.ts`

源码注释原文：

> C5-4 订单核销：券/免费次数/权益**全额抵扣一个未支付订单**……全额抵扣（**本波不接部分抵扣**）。

实际两行：

```js
discountCents: order.amountCents               // 免掉整单金额
data: { quantityRemaining: { decrement: 1 } }  // 只扣 1
```

**后果**：一张 `quantityRemaining = 7` 的免费打印额度，用在 15 面 / 3.00 元的订单上，
整单免掉 3.00 元，额度只扣 1，还剩 6。照此再用 6 次 —— **每月 20 页的额度可以白打 105 面**。

**这不是纸面风险，两个前提都已具备：**

1. 管理员**可以**创建任意 `quantityTotal` 的权益
   （`services/api/src/member-benefits/admin-member-benefits.service.ts:84`，
   只有 `subsidy_eligibility_hint` 被强制为 `null`）。
2. 核销服务**完全不区分 `benefitType`** —— `coupon` / `free_quota` / `package_entitlement`
   三种可核销品类走同一套全额免单逻辑，只是把 `kind: grant.benefitType` 记进账本。

**处置**：在补齐「额度单位 + 抵扣规则 + 预占」之前，
**不要给 Kiosk 开放任何指向 `/orders/:id/redeem` 的用券入口**，
也不要发放 `quantityTotal > 1` 的可核销权益。

## 二、四条被推翻的既有认知（原以为如此，实际不是）

| 原以为 | 实际（含出处） |
|---|---|
| C5-4 订单抵扣还没做 | **已上线**，`POST /orders/:id/redeem` 存在；但无 Kiosk 入口、且只支持整单免单 |
| `PriceConfig.effectiveFrom` 控制调价排期 | `PricingService` **根本不读它**；Admin 改价**立即生效**。且 `serviceKey @unique` 使同一服务**无法同时保存现价和未来价**（`payment/pricing.service.ts`） |
| `unit='page'` ≈ 屏上公示的「印刷面」 | `page` 的真实含义是**所选文档内容页**；**双面与「一面排 N 页」都不减少计费数量** |
| `print_duplex_surcharge` 与「双面不加价」冲突 | 它**只是 schema 注释里的举例**，未播种、未被 `PricingService` 读取 —— **不是当前的运行冲突** |

另有一条断层：`BenefitStatus='expired'` **不会自动更新**，
权益列表原样返回数据库 `status`（`member-benefits.service.ts:35`），
因此可能出现**权益页显示「可用」、核销时按时间被拒**。

## 三、计价单位的收口口径

**不新增模糊的 `'surface'`，也不把 `'page'` 口头解释成别的意思。**

- 数据库 `unit='page'` 保留以兼容历史订单（`itemsJson` 已落库）。
- API 增加明确的 `billingMetric: 'document_page'`。
- **屏上统一写「按所选文档页计费」**，并补一句
  **「双面只影响用纸张数，不减少计费页数」**。
- 未来真要按物理面收费，再新增 `'printed_side'` 并修改公式，
  **不要继续复用含义不清的 `page`**。

「双面不加价」商业上站得住：两面仍有两次成像、碳粉与设备损耗，只省一张纸。
更准确的公示措辞是「双面不另收设置费，仍按所选文档页计费；双面可减少用纸」。

**隐藏冲突**：若启用「一面排 2/4 页」，服务端仍按文档页收费，与实际印刷面不等。
该参数在计价规则收口前应**继续隐藏或固定为 1**。

## 四、线下场景推演里必须处理的几件事

这台机器**无人值守、站着用、旁边排队**，用户含中老年与应届生。以下为必须改：

1. **后台改价时用户正停在核价页** —— 当前无锁价（无 `quoteId`/`expiresAt`），
   前端调无状态报价、建单时后端再算一次，**两次可能不同**。
   须做短时锁价（建议 3 分钟）；过期后必须停在确认页明示「原金额 → 新金额」，
   只保留「按新价格继续」「返回修改」，**不能自动跳到支付码**，
   也**不能靠「实付以收银台为准」免责**。
2. **活动下线 ≠ 已发券失效**。活动只控制「还能不能新领」；已发权益是独立契约，
   须绑定不可变规则版本。需要撤销时走单独「撤销权益」动作并记录原因，
   **用户侧明确显示「已撤销及原因」，不能伪装成过期**。
3. **有效期判定统一为服务端时间** `validFrom <= serverNow < validUntil`，
   不用终端本地时间；不同接口不得分别使用 `<` / `<=`。
4. **断网**：旧价只能标「上次同步价，仅供参考」，
   **不能用旧价收钱、不能离线核销、不能展示「当前可用 7 页」**。
   但机器不必变砖：选文件、预览、调参数、看参考价、留本次草稿都应继续可用；
   只禁用「确认支付 / 使用权益 / 提交打印」并给出重试入口。
5. **不能把登录设成打印前置条件**。现场输手机号、收短信、看协议，
   站立操作 + 排队，流失很高，中老年用户尤其明显。
   主路径应为「游客上传 → 核价 → 可直接付款打印」，
   「已有权益？扫码登录查看」作为分支。文案只能写「登录后查看可用权益」，
   **不能写「登录立减」**（服务端尚未确认他有没有可用券）。
6. **公共终端清场**：完成页倒计时自动退出；空闲超时之外还要有
   **不受 busy 抑制的硬隐私超时**；清除登录态、权益列表、订单、文件预览、
   支付状态、路由历史、BFCache 与内存任务上下文；返回/前进/刷新都不能恢复旧页。
   支付结果不确定时，清场后只显示**无个人信息**的「上一笔订单仍在核实，请联系工作人员」。
7. **打印卡纸而券已核销**：不能删核销记录来「回滚」，也不能无凭据把券加回去。
   须走服务端状态机：报价 → 权益预占 → 支付/零元确认 → 核销提交 → 履约完成；
   打印失败时区分「确认未出纸（自动补偿恢复）」与「部分出纸/无法确认
   （保持异常处理中、同单免费续打、不重复扣权益）」。
   相关风险点：`apps/terminal-agent/src/agent/task-runner.ts` 对部分
   「队列未出现或超时」仍可能按 completed 回传。
8. **两台机器用同一张券**：只能靠数据库原子预占 + CAS 决定，
   失败方收到明确错误码后自动重新报价。**不能做前端锁，不能先显示「使用成功」再请求后端。**
   引入部分额度后，CAS 必须同时核算「已预占数量」，不能只读余额。
9. **旧前端遇到不认识的新券类型**：必须有默认分支
   「此权益暂不支持在本机使用，请在手机端查看或联系工作人员」——
   不显示金额、不出现使用按钮、不崩白屏。
   TypeScript 联合类型不是运行时保护，数据库字段是开放字符串。

## 五、合规：两处必须改的文案

1. **「政府买单」那句必须删除。**
   设计稿 `24-benefits.html` 写着「你免费打的这些页，本机是按页向人社结算的 ——
   所以这不是我们送你的，是政府买单」。
   现有模型只能证明发放来源分类为 `sourceType='gov'`，
   **不能证明本次打印已纳入财政采购结算，更不能向用户承诺政府付款**。
2. **`subsidy_eligibility_hint` 必须从「可用权益」中彻底分栏**，
   建议命名「政策资格参考」，不显示余额、金额、抵扣、领取成功或绿色勾选。
   固定提示：「依据当前政策信息整理，仅供参考。是否符合条件、是否受理及是否发放，
   以官方部门审核结果为准。本机不代办，也不发放补贴资金。」

## 六、另一条独立 P0（与权益无关，不要等改造顺手做）

`apps/kiosk/src/pages/print/CashierPaymentPanel.tsx:128` —
**当前收银页允许手输并明文回显 18 位付款码，付款码还进入 React state。**

付款码是一次性支付凭证。须改为扫码器专用、不可见输入，
只显示「已读取 / 正在提交」，提交后立即清空；
**禁止手输、日志、URL、storage 和错误回显**。

## 七、推荐的推进顺序

```
先冻结计价单位
→ 再补权益规则（额度单位 / 抵扣算法 / 适用范围 / 预占 / 失败补偿）
→ 再升级成带版本与有效期的 quote
→ 最后把服务端结论接入现有确认页与收银页
```

这样不会新增重复入口，也能保持当前打印、支付、核销账本为唯一主链。
**不要另建第二套订单或核销账本** —— 现有 `PriceConfig` / `Order` /
`BenefitGrant` / `RedemptionRecord` 与审计表都应继续复用。

首期可以只支持一种规则：`free_units + document_page + 不叠加`，
先把「7 页抵 7 页」做正确，再开放满减与折扣。

## 八、给后端的字段缺口清单

| 位置 | 缺什么 | 为什么 |
|---|---|---|
| 价格 | `priceVersionId`、作用范围、`effectiveFrom/Until`、发布状态 | `serviceKey @unique` 只能存一个现价，`effectiveFrom` 不参与读取，无法排期与追溯 |
| 计量 | `billingMetric = document_page / printed_side / item / use` | `page` 无法区分文档页、纸张、印刷面 |
| 权益规则 | `ruleVersionId`、`effectType`、`quantityUnit`、面值/折扣率、封顶、最低消费、适用 serviceKey、色彩与终端范围、叠加策略 | `benefitType` 只是品类，不足以计算优惠 |
| 发放快照 | `ruleSnapshot` 或不可变规则版本引用、撤销原因/时间 | 活动变化后仍要按领取时规则兑现 |
| 预占 | `BenefitReservation`：grant / quote / 数量 / 金额 / 状态 / 过期时间 / 幂等键 | 防两机并发与「报价时可用、付款时消失」 |
| 订单金额 | 区分 `grossAmountCents` / `discountCents` / `payableAmountCents` / `paidAmountCents` | 当前 `amountCents` 在全额券场景仍保留原值，无法支持部分抵扣 |
| 核销 | `RedemptionRecord.quantity` 写**真实消耗页数**；放宽一订单一条的唯一约束；增加补偿/冲正关联 | **7 页额度必须扣 7，不是扣 1** |
| 履约 | `outputOutcome = no_output / partial / unknown / complete`、可信来源、打印尝试号 | 卡纸时决定自动恢复、续打还是人工处理 |

`rulesText` 只能给人看，**绝不能参与计算**。
后台若要配「满 5 元减 2 元」或「免费黑白 7 页」，必须有结构化规则。

**核销凭据不要让前端拼**：确认时前端只传 `quoteId` + 幂等键；
即使为兼容仍带 `fileUrl/params`，服务端也只能用于核对摘要，
金额与优惠只认 `quoteId` 绑定的快照。
`grantId` 不是金额凭据；用户身份来自登录令牌，
**前端不得传 `endUserId`、discount、剩余额度或有效状态**。

## 九、前后端职责边界（评审确认成立）

前端**不**计算最终金额、**不**判定过期/适用范围/叠加/剩余额度、**不**生成折扣额、
**不**把「接口返回过一次」当成支付或核销成功。

前端**要**承担：展示服务端报价与优惠分解、报价有效期与服务器时间；
本地倒计时只作提示，到期仍以服务端复核为准；
参数格式即时校验只为提效，**不作为安全边界**；
把服务端机器码映射成适合站立场景的一句话 + 一个下一步动作；
未知类型 / 超时 / 断网统一 **fail-closed**。

后端慢时不能一直转圈：2 秒显示「正在核对价格和权益」，
8–10 秒显示「暂时无法核价」并给 ≥56px 的「重新核价」与「返回修改」，
**保留文件预览与参数，不能把用户赶回第一步**。
