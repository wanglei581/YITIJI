## 一、结论

找回的工程不是空壳：它是一套可运行候选的原生微信小程序，共 57 个注册页面，已经覆盖登录、AI 简历、模拟面试、职业规划、公开就业信息、材料包、终端选择、打印订单和本人资产等大部分页面资产。最新方案不应再按“源码完全丢失、从零重建 41 页”推进。

但页面存在不等于商业闭环完成。当前工程仍是独立仓库、原生 JavaScript/WXML/WXSS 和五 Tab 信息架构；最新方案目标是主仓库唯一 `apps/miniapp/`、四个业务对象 Tab，以及严格的 Order-only 待到机履约。尤其是现有支付页仍为流程预览，材料包流程允许先取得到机码，不能据此宣称“手机下单支付到一体机打印”已经完成。

因此采用三步策略：先保全并审计找回源码；再选择性复用页面、接口门面和视觉资产；最后在 Gate 0 冻结工程路线后迁入主仓唯一源码。迁入前不复制成第三份源码，也不把旧流程直接发布。

## 三、最新方案需要补充的功能

### Gate 0：工程与事实冻结

1. 冻结原生微信小程序继续演进或迁移 Taro 4 的技术决策；不能边开发边维持两套正式源码。
2. 将最终发布源码迁入主仓唯一 `apps/miniapp/`，接入 CI、构建、合规文案和发布配置守卫。
3. 从干净 `main` 复核微信登录、材料包、JSAPI 支付、`claim-pickup`、终端列表和本人资产端点，不能只信独立仓接口注释。
4. 保留现有五 Tab，直至用户明确冻结“今天 / 材料 / 发现 / 我的”四 Tab；本轮首页重排不等于 Tab 决策已通过。

### M0-M1：先形成随身 AI 求职准备闭环

1. 真实“今天”聚合接口：本人下一步、进行中 AI 任务、待支付/待到机订单与通知摘要。
2. 统一“材料”主页：简历、文档、AI 报告、材料包和到机凭证按对象归档。
3. 统一“发现”主页：岗位、招聘会、政策、企业和服务机构形成编辑部式信息流。
4. “我的”收敛为账户台账：权益、订单、消息、反馈、设置、隐私与协议；资产明细归业务页。
5. 小青意图到真实页面的受控路由、AI 结果下一步和本人确认；不允许模型直接支付、打印或外跳。
6. 补齐服务机构列表/详情、意见反馈和订单售后入口。

### M2：手机下单到一体机打印

1. 材料包条目快照、锁定、页数与价格快照由服务端负责。
2. 微信 JSAPI 支付、查单、回调验签、取消、过期和原路退款完成真实验收。
3. 支付成功只创建 Order 和待到机凭证，不创建 Agent 可 claim 的 PrintTask。
4. 到机码必须在支付状态、文件 TTL、终端能力和幂等条件全部满足后有效；到机核验事务中才创建 PrintTask。
5. 新增订单详情与实时打印监控，状态只能来自 API/Agent 回流；没有真实队列数据时不展示等待分钟数。
6. 从原订单发起反馈与异常核查，不另造孤立售后系统。

### M3-M4：手机独占与商业扩展

1. 微信订阅消息、真实位置导航、语音模拟面试、招聘会行前助手。
2. Offer 对比、薪资沟通练习、HR 常识问答三类低风险微应用。
3. 会员套餐、跨端权益和单位经济看板；不按招聘结果或岗位曝光收费。

## 四、本轮首页下半区设计

首页不再用五个圆形快捷入口、平均宫格或纵向长目录。最终结构固定为 `100vh` 一屏工作台，禁止首页纵向滚动；沿用找回工程原有的暖奶油纸感、棕黑正文、陶土红、麦金与来源蓝，不新增绿色大背景或另一套主题。三个业务区按可用高度自适应：

1. **求职准备**：简历诊断是唯一主动作；简历生成、模拟面试、职业规划和岗位匹配参考压缩为右侧次级目录。
2. **材料与打印**：材料包是主对象；我的简历、文档、订单、扫描同步和在线打印作为紧凑工具区。文案不宣称支付和远程打印已经完成。
3. **可信信息**：岗位是主对象；招聘会、政策、企业信息为右侧来源目录，明确“去来源平台投递”。
4. 小青与消息并入页头图标工具，不再占据一整段内容，也不做 AI 功能墙。
5. 删除近期动态空态；真实“今天任务”聚合接口上线前，首页只显示稳定的简历检查建议，不造假订单或办理动态。

本轮只改找回工程的 `pages/home/home.js`、`home.wxml`、`home.wxss`，未改 API、支付、数据库、全局 Tab、其他业务页或 `project.config.json`。
