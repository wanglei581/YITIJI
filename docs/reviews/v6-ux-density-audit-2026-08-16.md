## 零、先说清楚判据：这块屏到底有多大

所有字号建议都基于实测物理尺寸，不是桌面浏览器手感。

27 寸 16:9 面板旋转成竖屏，1080×1920：

| 量 | 值 |
| --- | --- |
| 面板物理尺寸 | 597.7 × 336.2 mm |
| 竖屏后每像素 | **0.311 mm/px**（约 81.6 PPI，低密度屏） |

换算到站姿 **600 mm** 视距的视角（视角 = 可读性的真正判据）：

| 字号 | 物理高 | 视角 @600mm | 评价 |
| --- | --- | --- | --- |
| 10.5 px | 3.27 mm | 18.7′ | 不可用 |
| **11 px** | 3.42 mm | **19.6′** | 中文笔画糊成一团，禁止用于正文 |
| 12 px | 3.74 mm | 21.4′ | 仅限有冗余的次要信息 |
| **13 px** | 4.05 mm | **23.2′** | 当前全站辅助信息的默认值，**偏低** |
| **15 px** | 4.67 mm | 26.8′ | 可作正文下限 |
| **16 px** | 4.98 mm | **28.5′** | 建议正文基准 |
| 18 px | 5.60 mm | 32.1′ | 舒适 |
| 20 px | 6.23 mm | 35.7′ | 舒适 |

参照：`tokens.css` 自己写过「12px 在 1080 宽、站立约 60cm 下看不清」，因此把 `--fz-1` 从 12 提到 13。**这个推论方向是对的，但停早了一档**——用户画像含中年再就业人群（40 岁后普遍老视），且站姿、赶时间、旁边有人。13px 应是**辅助信息下限**，不是正文默认。

行长判据：中文超过 **30–35 字/行**回扫困难。本轮把 **>35 字/行**记为超标，**>45 字/行**记为严重。

## 二、跨页面的系统性问题（建议在设计系统层统一改）

这几条在很多页重复出现，逐页修不划算，应在 `tokens.css` / `components.css` 一次改掉，再让 44 页迁移直接继承。

### S1. 硬编码小字号绕过了令牌体系

`README §6.5` 写明「色值、圆角、间距、字号一律走变量，禁止硬编码」，但共享 CSS 里仍有：

| 硬编码值 | 规则数 | 典型用途 |
| --- | --- | --- |
| `font-size: 11px` | 12 | `.ev` 证据胶囊、`.meta` 文件属性 |
| `font-size: 10px` | 5 | 报告页脚、页码 |
| `font-size: 12px` | 4 | 预览内小标题 |

`--fz-1` 是 13px，也就是说**全站最小的三档字号全部低于令牌下限、且不受令牌管辖**。

建议：
- `--fz-0: 13px` 设为绝对下限，删除所有 10/11/12px 硬编码
- 正文基准从 15px 提到 **16px**（`--fz-3`），辅助信息 15px，元信息 13px
- 增加一条构建期断言：共享 CSS 内 `font-size` 小于 13px 即报错

### S2. 「解释性小字」已成为全站默认习惯，总量超过主内容

几乎每张卡下面都挂一条 13px 灰色说明，类名分散在 `.dcard-hint` / `.aibar-note` / `.rdy-s` / `.tp-s` / `.exit-s` / `.in-note` / `.msg-tail` / `.concl-note` / `.gate-s` / `.thumbs-note` / `.xlane-ds` / `.src-ds`。

这些话本身是**对的**（诚实、边界清楚），问题是**排版没跟上诚实度**：13px + 40–70 字/行 + 无层级，站着看就是一片灰噪声，结果是**该读的和不该读的一起被跳过**。

建议统一为三档，而不是一档：

| 档 | 用途 | 规格 |
| --- | --- | --- |
| `.note--risk` | 隐私、不可逆、费用 | 15px / 1.7 / max-width 30em / 带图标 / 琥珀或朱砂底 |
| `.note--how` | 这一步怎么用 | 15px / 1.7 / max-width 32em / 默认显示 |
| `.note--meta` | 时间戳、外部 ID、来源 | 13px / 1.5 / 可换行不折叠 |

超过 3 行的一律折叠（页面已有「展开」控件，复用即可）。

### S3. 孤字（行尾掉 1–2 字）：83 个页面×阶段组合中 66 个命中

实测按渲染后行盒统计（跨元素边界），末行 ≤2 字的文本节点：

| 页 | 例 | 字号 | 末行字数 |
| --- | --- | --- | --- |
| 11 s2 | 「综合理由：8 条要求里 5 条能在你的简历原文里找到对应句子，差的 3 条…」 | 15px | 0.9 |
| 44 | 「本机不代收简历、不代收任何费用…请勿支付押金或未公示费用。」 | 22px | 2 |
| 24 | 「最终由服务端在核价那一刻判定」 | 18px | 1 |
| 36 | 「先挑一场，再决定带什么去」 | 18px | 1 |
| 37 | 「练一场，或者先弄清自己适合什么」 | 18px | 1 |
| 06 s2 | 「第 2 页含身份证号，建议遮盖后再打印」 | 15px | 1（"印"单独成行） |

18–22px 的**标题**掉一个字到第二行，在站姿下非常刺眼。README §9.2 把孤字列为「只能人工看」的项——它其实可以机器判，判据就是上表这一列。

建议：
1. 给标题类加 `text-wrap: balance`（Chrome 114+，Windows Edge/Chrome Kiosk 满足）
2. 正文段落加 `text-wrap: pretty`
3. 把「末行 ≤2 字」加进全量自检的第 11 项，和「标点顶行首」同级

> 注：README §9.1 写的自检入口 `verify.html` **已不存在**（当前工作区显示为删除），实际在跑的是 `tools/regress.html`（内部调 `v3Audit` 5 处）。README 这一段是过期引用，随本轮一并更正。

### S4. 内置触控检查器有两个盲区（本轮唯一一处工具缺陷）

先说结论：**实测 45 页的产品级可点区域全部 ≥48px，主按钮 ≥64px，触控是合格的。**（我一度按 `getBoundingClientRect` 量出 45.8px，那是 `.stage` 被 `transform: scale(0.954)` 缩放后的屏幕像素，除掉缩放后正好 48px——这个坑 `stage.js` 已经处理对了。）

但 `stage.js:213–228` 的检查器本身有两个洞，会让**未来**的违规静默通过：

```js
var hit = screen.querySelectorAll('a,button,input,[role="button"],.tile,.step,.slab,.scene,.dir-row,.node')
…
if (b.height / sc < 47.5 && wrap.getBoundingClientRect().height / sc < 47.5) small.push(hit[j])
```

1. **选择器漏了 `[data-href]` 与 `[onclick]`**。全站大量卡片是 `<div data-href="…">`，根本不进检查集合——P34 的 8 个入口卡、P06 的 6 张来源卡都靠它跳转。今天它们尺寸达标，是运气不是门禁。
2. **只判高度不判宽度**，且阈值写成 `47.5` 而非 `48`。一个 30px 宽 × 60px 高的图标按钮会被判合格。

建议改成：

```js
var hit = screen.querySelectorAll(
  'a,button,input,select,textarea,[role="button"],[data-href],[onclick],' +
  '.tile,.step,.slab,.scene,.dir-row,.node')
…
var w = b.width / sc, h = b.height / sc
if (w < 48 || h < 48) { /* 再看 wrap，仍不足才计入 */ }
```

（`.chip` 不要加进去——实测 34px 的 `.chip` 全部是状态标签而非按钮，加进去会产生 100+ 条误报把真问题淹掉。）

### S5. 缩略图宽高比与主预览不一致

全站 `.sheet-a4` 实测 **564×797 / 516×730，比值 0.707–0.708**，与 A4 的 1/1.414 精确吻合，**没有变形**——这一点做得好，用户担心的「上传后比例不对」在主预览上不存在。

但同屏的 `.thumb` 是 **84×122，比值 0.689**，比 A4 高了 2.5%。同一页里两个不同比例的「同一份文件」，是可察觉的不一致。

建议：`.thumb` 改 **84×119**（或直接 `aspect-ratio: 1/1.414` + `width:84px`），与 `work.css:394` 已有的写法对齐。

### S6. 「同一个动作出现两次」

多页把同一动作既放右栏又放 ActionBar：

- P07 s4：右栏「送 AI 简历诊断」（48px）+ ActionBar「送 AI 诊断」（64px 主按钮）
- P34：hero 卡「进入岗位台 →」+ ActionBar「进岗位台看全部 →」，**href 完全相同**

且 P07 那一处是**倒置的**：被主推的「送 AI 诊断」在右栏只有 48px，而它下面用户更可能真正想要的「存进我的文档」有 81px。

建议：ActionBar 主按钮是唯一的「本屏主推」，右栏同名按钮一律降级为文字链或去掉。

## 四、做得好、迁移时不要弄丢的

审查要求「站在用户角度找不合适的地方」，但有几处如果在迁移中被"简化"掉会造成实质倒退，一并记下：

1. **空态文案没有一句「暂无数据」**。全站 0 处。实际写法是：
   - 「「处理中」这一类现在没有记录 / **不凑数、不拿别的类别充数**。换一个筛选，或者去做一份新的。」+ 三个具体按钮
   - 「还没有简历 / 体检要对着一份具体的简历做。现在没有文件，就没有可诊断的对象——本机**不会拿模板生成一份假简历**来演示给你看。」
   这是本次审查里质量最高的部分，**空态必须带下一步动作**这条已经做到了。
2. **P19 智慧校园未接入态**是诚实降级的范本：明写「不摆任何假数字」「本机不替学校填一个看起来像真的值」，逐项列「谁提供、现在是什么状态」，并把用户导向今天真的能用的路（扫描成 PDF）。
3. **降级不阻断业务**：P09 `ai-down` 写「诊断服务中断，不给结论。左边的原文可以正常翻看、打印、存档。」
4. **A4 比例精确**：所有主预览 0.707–0.708，无拉伸变形。
5. **触控尺寸实测全部达标**（见 §S4）。
6. **合规边界零违规**：按钮文案白名单、三档参考无百分比、来源三字段齐全，与 2026-08-15 那轮结论一致，本轮真实渲染下复核无新增问题。
