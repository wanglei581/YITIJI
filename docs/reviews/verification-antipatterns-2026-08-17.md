# 验证反模式清单（2026-08-17）

> **这份文件的存在理由**：2026-08-17 一天内，同一类错误发生了 **17 次**——
> 工具或检查器给出了看起来正常、实则错误的信号，而我们信了。
>
> 代价包括：一个 P0（首页招聘会恒为空）被自己的验证系统保护了很久；
> 五个正确的修复被门禁挡在外面；一次我把坏 YAML 合进 main，连累所有 PR 的 CI 转红。
>
> 归纳由 DeepSeek 与 antigravity 两个独立模型分别产出后合并。

---

## 一、六条根本模式

### 模式 1：工具假成功——退出码 0，但什么都没做

| 案例 | 表现 |
|---|---|
| `timeout 900 agy ...` | macOS 没有 `timeout` 命令，整条没执行，**退出码 0** |
| `agy -p --effort high "PROMPT"` | `-p` 把 `--effort` 当成了 prompt 值，它回答的是「什么是 --effort」 |
| `agy --sandbox` 无命令权限 | **不报错，凭知识编了个答案**——比报错更危险 |
| `codex exec` 认证过期 | 输出文件 **0 字节**，进程还挂着，退出码 0 |
| `bash -n f 2>&1 \| head -1 && echo "有效"` | `&&` 挂在 `head` 上，**无论如何都打印「有效」** |

**为什么难发现**：退出码 0 与「成功」在直觉上等价，而这些工具把失败写进了 stdout 或干脆静默。

**防呆**：
- 派出外部 CLI 后**先验产出**（文件大小、内容是否包含预期字段），再对外宣称它在跑。
- 管道里判断退出码要用 `PIPESTATUS`，不要让 `&&` 挂在管道末端的 `head`/`tail` 上。
- 正式派活前做一次**冒烟测试**：让它执行一条你已知答案的命令，对得上再派。

### 模式 2：检查了，但检查的是错的东西

| 案例 | 表现 |
|---|---|
| `command_timeout` 够不够 | 写成了判断它「存不存在」，存在就跳过 → 3m 超时没改到，扫描被截断两次 |
| basename 查引用 | `01-home.html` 同时命中两个不同目录的同名文件 → 0 引用误判成 8 处 |
| `git diff <ref> -- <path>` | 把**未跟踪文件静默报成「已删除」**，产出假的 `+0 -N` diffstat |
| 反向注入 `replace(..., 1)` | 子串出现多次只替换第一处 → 注入没生效，却当成「门禁没抓住」 |
| 提取 YAML 的 script 块做 `bash -n` | awk 缩进算错，新旧两份报同样的错 → **对照实验无效** |

**防呆**：
- 查文件引用**一律用仓库相对全路径**，或 `(^|/)filename$`，禁止裸 basename。
- 判断文件归属用 `git hash-object` 比对 blob，不要看 diffstat。
- 反向注入后**先确认注入真的生效**（残留计数为 0），再看门禁反应。
- 对照实验必须**先证明「坏的那份真的会红」**，否则实验无效。

### 模式 3：门禁本身不可靠（**代价最高**）

| 子类 | 案例 |
|---|---|
| **把 bug 钉死** | 门禁要求代码里必须存在一行有缺陷的判断（比对接口根本不下发的字段）→ 首页招聘会恒为空这个 P0 被保护了很久。**今天共发现 5 条同类** |
| 空转 | 断言 `/<KioskFeedbackDialog/`，组件改名成 `<KioskFeedbackDialogXX` 照样通过 |
| 报错不给证据 | 打印「违规文件：」后面是空的 |
| 汇总在明细前 | `N/M` 打在明细**前面**，日志一截尾就只剩个数字 |
| 空库恒绿 | 空数据库上通过、真实数据下才红 |
| 孤儿门禁 | 没注册进 package.json、CI 不引用 → 连元门禁的「342/348」都看不见它 |

**为什么最贵**（两个模型独立得出同一结论）：
其余模式造成的是**小时级急性阻塞**；这一条是**慢性剧毒**——
它不是漏过 bug，而是**主动杀死正确的修复**。工程师改对了，CI 却红，
于是怀疑自己并撤回改动，形成「自动化系统逼迫人写 bug」的闭环。
同时制造虚假安全感：「我们有 348 道门禁」。

**防呆**：
- 断言用**词界与闭合匹配**（`/<Component\b[^>]*>/`），或直接基于 AST。
- 门禁循环前加**非空底线断言**：`assert scanned.length > 0`。
- 新增/修改门禁必须做**先破后立**：注入缺陷 → 必须红 → 还原 → 回绿，三步都要在 PR 里留证。
- 报错格式统一为 `[FAIL] 规则 | 文件:行号 | 实际 vs 期望`；违规列表为空却返回失败，视为门禁自身缺陷。
- **严禁以「让门禁变绿」为目标改代码**。改断言前必须写明「为什么此断言先前是错的」。

### 模式 4：拿错误的快照当现状

| 案例 | 用的快照 | 真实现状在 |
|---|---|---|
| 「admin 发布按钮没修」 | 主仓工作区 | `origin/main`（早已修好） |
| 「API 构建挂了一整天」 | 主仓工作区 | `origin/main`（那模块只存在于工作区） |
| 「errorCode 到不了客户端」 | 生产 `dist` | `origin/main`（已加） |

本仓库有 **64 个 worktree**，主仓 checkout 常停在别的分支且带大量未提交改动。

**防呆**：任何「某文件/功能是否存在、是否已修复」的结论，动手前必须跑一条对 `origin/main` 的验证命令：

```bash
git ls-tree -r origin/main <path>     # 存在性
git show origin/main:<path>           # 内容
```

**不要**用 `ls`、不要读生产 `dist`（那是某个旧 SHA 构建的产物）。

### 模式 5：状态歧义——「没消息」不等于「进行中」

`gh pr checks` 在 PR 与 main 冲突时显示「no checks reported」，
与「排队中」**完全无法区分**——两个 PR 因此静静空转 25 分钟。

**防呆**：checks 为空时先查 `mergeStateStatus`，是 `DIRTY` 就先解冲突，不要当成 pending 等。

### 模式 6：测试把缺陷写成了期望值（**最隐蔽**）

前五条讲的是「验证没跑」「验证跑错了对象」「门禁本身不可靠」。这一条不同：
**门禁跑了、可靠、断言也没写错语法 —— 它只是钉在了错误的那一面。**

2026-09-08 实证。`apps/kiosk/tests/visual/kiosk-visible-actions-truth.spec.ts` 里写着：

```ts
expect(payload.factsConfirmedAt).toBeUndefined()
```

用例已经勾完事实核对墙、点了「确认导出」，页面也确实把时间戳传给了
`exportGeneratedResume(..., { factsConfirmedAt })`，而规格 `ResumeGenerateExportDto`
写的是**登录用户导出必填，缺失即 400**。真相是前端适配层按一条**已经过期的注释**
把该字段丢了，写用例的人照着当时观察到的行为，把这个缺陷固化成了期望值。

后果：**所有登录会员的「简历优化导出」100% 失败**（`400 RESUME_FACTS_NOT_CONFIRMED`），
匿名用户完全不受影响 —— 因为后端闸门对匿名早返回不校验。这条缺陷一路绿着活到今天。

**为什么它比「断言写漏了」严重一个量级**：写漏只是没抓到；
**把缺陷写成期望值，等于给缺陷发了一张永久通行证**，还让后来者以为那就是规格。
而且这类缺陷天然只打登录态，走查点一遍全绿：四观测量只记 method+path 不记状态码，
400 和 200 在日志里长得一模一样。

**两条判据**（产品负责人已采纳为全局检查项）：

1. 凡是断言「期望不存在」的（`toBeUndefined()` / `toHaveCount(0)` / `not.toContain()`），
   **要能说出为什么该不存在**。说不出来，就是照着行为写的。
2. **反向变异**：把被断言的行为改成「正确的样子」，如果测试转红，
   那这条断言钉的就是缺陷不是规格。
   （常规变异测试是「改坏了要红」，这里是**「改对了不该红」**。）

排查技巧：**先找同文件里做同一件事的兄弟方法**。本例 `exportResumeRecord` 一直是对的、
`exportGeneratedResume` 不对，两者相邻，一对一反证，比通读调用链快得多。

存量已扫过一次：kiosk 28 个 spec、312 条「断言不存在」里只有这 1 条属此类
（另 2 条「网撒得比规格宽」待产品判），清单见
[kiosk-absent-assertion-audit-2026-09-08.md](kiosk-absent-assertion-audit-2026-09-08.md)。
**是个别失误，不是系统性习惯** —— 但正因为稀有，下次再出现时更没人会怀疑它。

## 二、验证防呆 6 问（动手前自问）

```
1. 我亲眼看到它失败过一次吗？
   → 现在故意把逻辑改坏，它会当场变红吗？

2. 这个 0 是做完了的 0，还是半路死掉的 0？
   → 报错被管道吞了吗？产物是不是 0 字节？命令在当前 OS 上真的存在吗？

3. 如果把输入全清空，它还会是绿的吗？
   → 空库、0 匹配、空列表会不会让循环直接跳过，产生假绿？

4. 我现在验证的，是我想验证的那份代码吗？
   → 工作区干净吗？dist 是刚打的吗？CI 是排队还是因冲突根本没跑？
   → 我验了内容，验了包住它的那一层吗？

5. 我是在测真实业务语义，还是在测一个名字/外壳？
   → 检查的是值和范围，还是仅仅查了它「存不存在」？

6. 这条断言是照着规格写的，还是照着我刚看到的行为写的？
   → 断言「期望不存在」时，说得出为什么该不存在吗？
   → 把行为改成「正确的样子」，这条测试会红吗？红了就是它钉着缺陷。
```

> 第 4 条的最后一句来自 2026-08-17 的实际教训：
> 我用 `bash -n` 验了脚本、验了 base64 还原一致，**唯独没验包住它们的 YAML**——
> 而仓库里就有 `pnpm verify:repository-integrity` 专门干这件事，我没跑。
> **工具一直在，缺的是「什么时候必须跑」。**

## 三、改 workflow 的硬性要求

改动 `.github/workflows/**` 后，推之前必须本地跑：

```bash
pnpm verify:repository-integrity
```

它校验所有 workflow 的 YAML 语法。跳过它的代价（2026-08-17 实测）：
坏 YAML 进 main → GitHub 无法解析该文件 → 识别不出 `workflow_dispatch`（dispatch 一律 422）
→ 且 `Repository integrity gate` 转红 → **连带所有在跑的 PR 全部失败**。
