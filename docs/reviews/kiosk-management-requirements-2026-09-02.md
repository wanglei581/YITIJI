# 一体机功能「需要被管什么」需求清单（2026-09-02）

> **这是需求清单，不是现状盘点。**本文只回答一个问题：运营方要把「职易达」这台机器
> 真正运营起来，**需要能做什么**。本文**没有**、也不打算判断后台现在有没有这些能力——
> 后台现有能力由另一条线独立盘点（`admin-capability-inventory-2026-09-02.md`），
> 两份文档交叉对比才有意义，所以本文刻意不引用、不预设任何后台现状。

## 0. 口径与边界

### 0.1 数据来源

| 来源 | 用途 |
|---|---|
| `docs/graph/graph.json` → `apps.kiosk.routes`（107 条运行时路由） | 功能归组的完整底稿，确保无遗漏 |
| `docs/design/kiosk-redesign-2026-08/` 51 张原型 + `DESIGN-PLAN.md` + `audit-notes.md` | 每个功能对用户到底是什么、交付物是什么、状态机有哪些分支 |
| 各路由声明的 123 个 kiosk 端点 | 让每条管理需求落到可写端点的具体维度上 |

覆盖校验：107 条路由 → 32 个功能，无重复、无遗漏（逐条比对过）。

### 0.2 「运营方」是谁

管这些机器的人：大厅现场值守、区域运维、平台运营、财务对账、合规与投诉处理。
他们要回答的四件事就是本文的四个类别：

| 类别 | 运营的原话 | 落到系统里是什么 |
|---|---|---|
| **看得见** | 「这台机器现在在干什么？这个月花了多少钱？」 | 指标、分布、失败原因、成本、口径明确的统计维度 |
| **改得了** | 「这个功能先别开」「这个价改一下」 | 配置项、开关、额度、模板、文案，且要有生效范围与生效时间 |
| **停得掉** | 「出事了，先停」 | 分级熔断：停单机 / 停功能 / 停某账号 / 限流 / 强制降级 |
| **查得到** | 「昨天下午有人投诉，查一下」 | 审计流水：谁、何时、对什么、做了什么、当时现场是什么样 |

### 0.3 一条贯穿全文的硬边界：**看得见 ≠ 看得到内容**

**运营应当能看到「发生了什么」，但默认不能看到「用户写了什么」。**

具体到每个功能，本文按三档标注可见性：

| 档位 | 含义 | 例子 |
|---|---|---|
| **M（元数据可见）** | 时间、终端、功能、耗时、结果、失败码、计费金额、文件大小/页数/类型。**默认可见** | 「12:04 在 3 号机做了一次简历诊断，耗时 8.2s，成功，成本 ¥0.11」 |
| **R（受控可见）** | 内容片段或结构化摘要。**必须走审批 + 目的登记 + 留痕 + 有效期**，且默认脱敏 | 投诉工单里用户主动附上的那一份文件，运营在处理期内可读 |
| **N（永不可见）** | 原文内容。**任何角色、任何理由都不通过后台开放** | 简历正文、身份证影像、面试录音原声、付款码 |

**任何标注 R 的访问都必须落审计，且被访问者可在「我的 → 隐私与数据请求」里看到有人访问过。**
这条不是可选项：`CLAUDE.md` §11「管理员访问文件必须记录日志」是硬要求。

### 0.4 合规红线（写需求时不得越界）

- 岗位、招聘会、企业只做**第三方 / 官方来源信息入口**。本文**不提出**任何需要
  平台内投递、收简历、候选人筛选、面试邀约、Offer 管理的管理需求。
- 因此「投递结果」「面试结果」「录用结果」这三类数据**根本不存在**，
  运营的任何转化率指标都只能算到「打开了来源平台」为止，不能再往下算。
- 用户文件不长期保存；管理需求里凡是涉及文件的，一律带「留痕 + 有效期」。

## 2. 逐功能管理需求

> 每条「不管的后果」都写成一个**具体场景**，不写「影响运营效率」这种空话。

---

### F01 待机宣传屏与广告播放

**看得见**
- 每台机器每天的待机时长占比、被触摸唤醒次数、播放素材逐条的曝光次数与实际播放完成率；
  素材加载失败次数（按素材 ID × 终端），视频解码失败与卡顿次数。
  *不管的后果*：某台机器的视频素材编码不被 Edge 支持，屏幕整天黑着，运营在办公室看不出来——
  巡场的人到现场才发现这台机器已经黑屏了一周。
- 每条素材的**生效期与到期倒计时**，以及「已过期但仍在播」的清单。
  *不管的后果*：一场已经开完的招聘会海报在大厅循环播了两周，求职者按海报时间跑空一趟。

**改得了**
- 按终端 / 终端分组下发播放方案：素材顺序、单条时长、循环方式、静音策略、亮度/时段（营业时间外是否黑屏）。
- 无操作进入待机的**超时秒数**可配置，且**忙碌态豁免**（正在打印/正在支付时不得插入待机）可配置。
- 素材上下架时间（定时生效、定时下架），支持只对某几台机器生效。
  *不管的后果*：市里临时要求撤下某条宣传内容，只能一台一台跑现场拔 U 盘。

**停得掉**
- 一键停掉某条素材（全网 / 指定终端）并立刻回落到默认底图，**不需要重启机器**。
- 一键关闭整个待机屏功能（保持常亮首页）。
  *不管的后果*：一条素材里出现了错别字或过期二维码，撤下要等到下次巡场——错误内容持续对外播放。

**查得到**
- 素材上传/替换/上下架/投放范围变更的操作流水：谁、何时、改了哪台机器的哪条素材、上一版是什么。
- 单台机器的实际播放日志（时间戳 + 素材 ID），用于对外解释「某个时间点屏幕上到底在放什么」。
  *不管的后果*：有人投诉「你们屏幕上放了 XX 内容」，运营无法自证那台机器当时在放什么，只能全额认错。

### F02 终端本机身份、能力开关与设备状态

**看得见**
- 每台终端的**心跳状态**（在线/离线/心跳过期）+ 最后一次心跳时间；
  打印机状态（就绪/忙/卡纸/缺纸/报错码）+ 状态来源（Agent 上报 vs 未知）+ 上报时间。
- 全网终端一屏总览：在线数、离线数、打印机不可用数、按站点/区域分组。
- 每台机器**当前生效的能力开关快照**（哪些功能开着、哪些锁着、锁的原因）。
- **明确标注「本机拿不到」的项**（耗材余量、扫码器在线、摄像头），这些**必须显示为未知，不得渲染成正常**。
  *不管的后果*：后台把没上报的项默认画成绿色，运营以为 5 号机一切正常，
  实际它已经离线 6 小时，用户在现场排队点不动。
- 离线时长排行 + 同一台机器的离线频次（抖动 vs 真宕机）。
  *不管的后果*：某台机器每天离线 20 次、每次 3 分钟，看总在线率是 96% 很好看，
  但每天有几十个用户在中途被打断，永远查不出来。

**改得了**
- 逐终端的能力开关（`capabilities`）：彩色打印、双面、扫描、U盘、AI 各能力、支付通道，
  支持**终端级**与**全网级**两层，终端级优先。
- 终端基础配置：`printerName`（配置项，不硬编码型号）、纸张默认、营业时间、所属站点、联系电话。
- 心跳过期判定窗口（当前设计口径 5 分钟）可配置，不同网络质量的站点可给不同阈值。
- 设备不可用时**屏幕上显示的话术**可配置（例：「打印机维护中，AI 简历服务仍可使用」）。
  *不管的后果*：打印机坏了一整天，屏幕只会显示一句通用报错，用户以为整台机器废了，
  连能用的 AI 简历服务也没人用。

**停得掉**
- **单台终端整机停服**（远程置为维护态）：屏幕显示维护公告，所有下单入口关闭。
- **按功能停服**：只停打印、只停支付、只停某个 AI 能力，其余照常。
- **按站点/分组批量停服**。
- 停服必须**fail-closed**：停服指令未确认送达时按「已停」处理，不得因为拿不到终端回执就继续放行下单。
  *不管的后果*：打印机卡纸报废，但下单和支付照常，一小时内 30 个用户付了钱拿不到纸，
  全部要人工退款。

**查得到**
- 终端注册/改名/换绑站点/能力开关变更/维护态切换的完整操作流水（谁、何时、改前改后）。
- 设备状态时间线：可回放「某天 14:00–15:00 这台机器的打印机是什么状态」。
  *不管的后果*：用户投诉「昨天下午你们机器根本打不了」，运营无法证实也无法证伪，
  只能按投诉方说的赔。

### F03 登录与身份验证

**看得见**
- 短信验证码：发送量、成功率、失败原因分布（限流/欠费/号段不通/网关错误）、单条成本、日累计花费。
- 登录成功率、按失败码分布（`SMS_CODE_INVALID` / `EXPIRED` / `LOCKED`）、锁定账号数。
- 扫码登录：出票量、认领率、超时未认领率（按终端）。
- 免登录使用占比（多少人根本没登录就把事办完了）。
  *不管的后果*：短信通道欠费停发，用户在机器前连续点五次「获取验证码」都收不到，
  以为机器坏了转身走人——运营到月底看短信账单才发现。

**改得了**
- 验证码冷却秒数、有效期、单号码/单终端/单 IP 的日发送上限。
- 扫码票据有效期（当前设计口径 3 分钟）。
- 是否允许免登录使用某个功能（逐功能配置，例：打印可匿名，AI 简历必须登录）。
- 短信模板文案与签名。
- 登录失败锁定策略（几次锁、锁多久、怎么解锁）。
  *不管的后果*：有人写脚本对着短信接口刷，一晚上刷掉几千条短信费，且无法临时收紧阈值。

**停得掉**
- 临时关闭某种登录方式（例：短信通道故障时只留扫码）。
- **单账号封停**（禁止登录，并使其在场会话立即失效）。
- 短信发送全局熔断（超过日预算自动停发并告警）。
- 单终端登录熔断（某台机器被人反复刷时只停这一台）。
  *不管的后果*：一个号码在一台机器上反复触发验证码，运营除了拔网线没有别的办法。

**查得到**
- 每次验证码发送与每次登录尝试的流水：时间、终端、手机号（**掩码存储，明文不入日志**）、结果码、来源 IP。
- 账号封停/解封的操作人与理由。
- **手机号明文属于 N 档，运营列表页只能看掩码；解掩码需审批 + 留痕 + 有效期。**
  *不管的后果*：投诉「我没登录过怎么有我的记录」，运营查不到那次登录是在哪台机器、什么时间发生的。

### F04 会话安全、超时清空与断点续办

**看得见**
- 会话超时触发次数、用户点「继续」vs 自动清空的比例、清空失败次数（按终端）。
- **清空失败**是独立指标，必须单独告警。
- 平均会话时长、在哪一步被超时打断最多（按路由）。
- 断点续办：待办任务数、续办成功率、续办失败原因（订单已关/超时/终端不匹配）。
  *不管的后果*：某台机器的清空逻辑因为异常一直失败，上一个用户的简历留在页面上，
  下一个用户直接看到——直到有人投诉才知道。

**改得了**
- 无操作警告倒计时秒数、警告后强制清空秒数，可按功能区分
  （填表页给长一点、支付页不能中途清）。
- 待办任务的保留时长（多久之后不再提供续办）。
- 「结束并清空」按钮的行为范围（清哪些、不清哪些）。
  *不管的后果*：默认 60 秒对着长表单的中老年用户太短，填到一半被清空，重填三次后放弃。

**停得掉**
- 远程强制结束某台终端上的当前会话并清空（现场发现有人把材料忘在屏幕上时用）。
- 关闭断点续办功能（怀疑续办链路被滥用时）。
  *不管的后果*：现场工作人员看到屏幕上停着别人的身份证扫描件，只能自己上手点，
  点错还可能把人家的订单取消。

**查得到**
- 每次超时/清空/续办的流水：终端、会话 ID、触发原因、清空结果、涉及哪些任务 ID
  （**只记 ID 与结果，不记内容**）。
  *不管的后果*：用户说「我的文件被你们弄没了」，运营无法说明是超时清空还是根本没上传成功。

### F05 首页与服务导航

**看得见**
- 首页各入口的点击量与点击后的完成率（进入 → 拿到交付物）。
- 各域 Hub 页的跳出率（进了 Hub 又直接退回首页 = 用户没找到）。
- 「被点了但当前不可用」的入口点击次数（用户点了个锁着的功能）。
  *不管的后果*：某个入口因为能力被关而灰着，每天被点 200 次，
  运营完全不知道有这么多人在找这个功能。

**改得了**
- 首页与各 Hub 的**磁贴排序、显隐、文案、图标**，可按终端分组差异化
  （高校点位和社区点位要的不是同一套入口）。
- 入口的角标/提示语（例：「本月免费 1 次」）。
- 入口指向的目标路由（在合规白名单内）。
  *不管的后果*：某个站点主要办打印，但打印入口排在第二屏，
  运营改不了顺序，只能让现场人员一个个口头指路。

**停得掉**
- 隐藏某个入口（全网 / 指定终端），且隐藏后**深链也要拦住**——
  不能只藏磁贴，用户从「我的」里的历史记录点回去还能进。
  *不管的后果*：功能已经宣布下线，磁贴藏了，但用户从历史记录点进去还能用，
  产生了不该产生的订单和成本。

**查得到**
- 导航配置变更流水（谁、何时、改了哪一台的哪个入口、改前改后）。
  *不管的后果*：某天首页少了一个入口，没人承认改过，回滚不了。

### F06 帮助求助、法律协议与现场人工出口

**看得见**
- 帮助页各主题的查看量、看完之后仍然发起工单/求助的比例（= 这条帮助没解决问题）。
- 「联系现场工作人员」被触发的次数与所在页面（用户在哪一步卡住了）。
- 协议/隐私政策的**当前生效版本号与生效时间**，以及各版本的同意人数。
  *不管的后果*：隐私政策更新了，但某几台机器还在展示旧版本，
  用户在旧版本上点了同意——一旦出监管检查，同意链条对不上。

**改得了**
- 帮助条目内容与分类（不重新发版就能改）。
- 协议正文与版本号，支持定时生效、灰度到部分终端先验。
- 现场求助方式配置（该站点的值守电话 / 是否显示在屏幕上 / 是否只走呼叫按钮）。
  *不管的后果*：站点值守电话变了，屏幕上还是旧号码，
  用户打过去是空号——机器等于没有人工出口。

**停得掉**
- 下架某条错误的帮助内容。
- 协议版本回滚到上一版。
  *不管的后果*：新版协议里写错了保留期限（写成 30 天但系统按 7 天清），
  改回来要等发版，中间每一次同意都是错的。

**查得到**
- 协议版本变更流水 + 每个用户同意的是哪一个版本号、什么时间、在哪台机器同意的。
  这条是**监管取证材料**，必须能单条导出。
  *不管的后果*：被问「用户同意的是哪一版」，答不出来，等同于没有取得同意。

### F07 文件搬运入池（手机接力 / U盘 / 到机码 / 本机选择）

**看得见**
- 四个通道各自的使用量、成功率、失败原因分布
  （格式不支持 / 超大小 / 上传中断 / 会话过期 / 到机码输错 / U 盘读不到）。
- 上传会话的平均耗时与超时率（手机接力等太久用户会走）。
- 文件类型与大小分布、单次办理平均文件数。
- **存储用量与增长曲线**（按终端、按文件类别），以及**超过保留期仍未清理**的文件数量与最老一份的年龄。
  *不管的后果*：清理任务静默失败三个月，对象存储里堆了几万份简历和身份证复印件，
  账单暴涨还只是次要的——真正的风险是一次泄露把三个月的敏感文件一次性泄干净。
- 到机码：生成量、核销率、输错次数分布、过期未用比例。
  *不管的后果*：到机码有效期设得太短，一半的用户手机传完文件走到机器前码已过期，
  运营只看到「上传成功率高」，看不到「走到机器前没用上」。

**改得了**
- 单文件大小上限、单次会话文件数上限、允许的格式白名单（当前设计口径：打印上传只收 PDF/JPG/PNG）。
- 上传会话有效期、到机码位数与有效期、错误重试次数。
- **各类文件的保留期**：敏感（证件类）/ 一般（普通文档）/ 离场即清 三档，
  且这套口径必须与「我的 → 隐私」页展示的口径**同一处配置、同一处生效**。
- 是否开放某个通道（例：出于安全先关掉 U 盘导入）。
  *不管的后果*：保留期在后台改了，屏幕上还写着旧天数，用户按屏幕说的等第 8 天来取，
  文件已经在第 7 天被清掉了。

**停得掉**
- 关闭任一上传通道（全网 / 单终端）。
- **单账号上传封禁**（有人反复上传大文件占存储）。
- 上传总量熔断（超过日配额时暂停接收新文件并告警）。
- 单份文件的**紧急下架**：立刻使其所有签名链接失效（收到内容违规举报时）。
  *不管的后果*：有人上传了违法内容并把签名链接发给别人，
  运营除了删整个账号没有别的手段，链接在有效期内一直可访问。

**查得到**
- 每份文件的生命周期流水：上传时间、通道、终端、大小、类型、
  被哪些任务引用、每一次签名链接签发（谁签的、给谁、有效期）、删除时间与删除原因。
- **管理员访问文件必须单独留痕**：谁、何时、因为哪个工单/审批看了哪一份，
  且**被访问者可见**。
- 文件内容本身：**N 档**（永不在后台开放浏览）；
  因投诉/违规调查需要查看的，走 **R 档**：审批 → 目的登记 → 时限内可读 → 到期自动失效 → 通知用户。
  *不管的后果*：运营为了处理一个投诉直接开了个后台预览页把文件点开看，
  没有审批、没有留痕、用户不知情——这一次访问在合规上等同于泄露。

### F08 隐私预检与 PII 裁决

**看得见**
- 预检触发率（多少份材料被检出含身份证号/手机号/银行卡号等）、各类命中分布。
- 用户裁决分布：遮挡 / 保留 / 跳过预检 的比例。
- **「跳过预检」的绝对数量与占比**——这是风险指标，必须单独看。
- 预检服务失败率与超时率。
  *不管的后果*：预检服务连续报错自动降级成「跳过」，一周内几千份带完整身份证号的
  材料原样打印并留存，没有任何人知道降级发生过。

**改得了**
- 检测哪些 PII 类别、各类别的默认动作（默认遮挡 / 默认提示）。
- 是否允许「跳过预检」，以及跳过时的二次确认文案。
- 证件类文件自动加水印的开关与水印内容模板。
  *不管的后果*：身份证复印件不自动加「仅供 XX 用途」水印，
  打出来的复印件被拿去冒办业务，责任落到运营方。

**停得掉**
- 预检服务不可用时的**默认行为可配置**，且必须支持配成 **fail-closed（不可用即不许继续打印）**。
- 关闭「跳过预检」按钮（收紧模式）。
  *不管的后果*：预检挂了默认放行，是把「合规内建」直接变成了「合规看运气」。

**查得到**
- 每次预检的流水：任务 ID、命中类别与**位置**（第几页第几处）、用户裁决、最终是否遮挡。
- **命中的原文片段属于 N 档**——只记「第 3 页命中身份证号 1 处」，
  **不记那 18 位数字本身**，也不在后台任何页面回显。
  *不管的后果*：为了「方便核查」把命中片段存进日志，
  于是审计日志本身变成了全平台身份证号最集中的一张表。

### F09 打印参数、预览与能力门控

**看得见**
- 参数分布：黑白/彩色、单双面、份数、页范围使用率、纸张类型。
- 因能力锁定而无法选择的次数（用户想彩打但这台机器彩打被关了）。
- 预览失败率与原因（取不到 / 链接过期 / 格式不支持）。
- 页数统计口径的异常：文档页数与计费页数不一致的单子（页范围解析问题的早期信号）。
  *不管的后果*：页范围解析有 bug 把 `1-3,2-4` 算成 7 页而不是 4 页，
  每一单都多收钱，直到用户拿着小票来吵才发现。

**改得了**
- 逐终端的能力锁：彩色锁、双面锁、文档类型锁，且**锁的原因文案可配**。
- 份数上限、页范围段数上限、单次任务总页数上限。
- 各参数的默认值（不同站点默认黑白双面省纸 vs 默认彩色）。
  *不管的后果*：一台机器被人一次提交 500 份，纸和粉当天耗尽，
  后面所有用户都办不了。

**停得掉**
- 关闭彩色打印（粉快用完时）、关闭双面（定影/翻转单元故障时），只关这一项不停整机。
- 单账号的页数配额熔断。
  *不管的后果*：彩粉见底但彩打入口还开着，打出来一半褪色，用户要求重打+退款。

**查得到**
- 每单的参数快照（用户最终确认的那一版），用于事后核对「他到底选了几份」。
- 能力锁变更流水。
  *不管的后果*：用户说「我明明选的双面，你们打成单面还按单面页数收钱」，
  运营没有参数快照，说不清。

### F10 报价、建单与价目

**看得见**
- 价目配置的**当前生效版本**与生效范围（全网 / 分组 / 单机）。
- 报价调用量、报价失败率、零元单占比。
- 客单价、单页均价、按纸张/彩黑/单双面的收入结构。
- **报价金额与最终支付金额不一致的单子**（应当恒为 0，非 0 即事故）。
  *不管的后果*：报价用旧价目、建单用新价目，用户看到 ¥3.00 却被扣 ¥5.00，
  这是**直接的收款争议**，且会在几百单里同时发生。
- 建单失败率与失败码分布。

**改得了**
- 价目表：按纸张尺寸 × 彩黑 × 单双面 的单价、起步价、最小计费页数、抹零规则。
- **计费总开关**（`billingEnabled`：某些政府购买服务点位需要全免费）。
- 价目**生效时间**（定时生效）、**生效范围**（分站点定价）。
- 优惠/权益抵扣规则与叠加顺序。
  *不管的后果*：新点位谈的是政府买单免费，但价目改不了范围，只能全网免费或全网收费，
  要么白送几千块，要么违约。

**停得掉**
- 价目变更的**灰度与一键回滚**（先在 1 台机器生效，确认无误再铺开）。
- 出现报价异常时**停止建单**（宁可不接单也不能错收钱）。
  *不管的后果*：价目改错了一个小数点，单价从 0.3 元变成 3 元，
  没有回滚就要靠人工一单一单退。

**查得到**
- 价目每一次变更的完整流水：谁、何时、改前改后、生效范围、生效时间、是否灰度。
- 每一单的**报价快照**（当时用的是哪一版价目、算出了哪几行 `priceLines`）。
  *不管的后果*：财务对账发现某天收入异常，无法定位是哪一次价目变更造成的，
  也无法重算那天的应收金额。

### F11 收银台支付、对账与退款

**看得见**
- 按通道（微信/支付宝/sandbox）的成功率、平均支付耗时、失败码分布。
- **未决态存量**：停在 `paying` / `pending-verification` / `reconciling` 的订单数与最老一单的年龄。
  这是最需要盯的一个数——它直接对应「用户的钱去哪了」。
- 回调丢失次数与主动对账（`reconcile`）触发次数、对账修正的订单数与金额。
- 退款：申请数、成功率、平均时长、退款金额合计。
- **每日三方对账差额**：系统账 vs 渠道账，逐笔可下钻。
- **sandbox 通道是否在生产终端上被启用**——这一项必须有独立告警。
  *不管的后果*：某台机器误配成 sandbox 通道，用户"付款成功"、纸也出了，
  但一分钱没进账，一天下来白送几百单。

**改得了**
- 各通道的启用/停用（全网 / 单终端）、多通道时的展示顺序。
- 收款码有效期、轮询间隔、自动对账触发条件与重试次数。
- 未决订单的自动关单时限。
- 退款审批阈值（多少钱以下可一线直接退，超过要审批）。
  *不管的后果*：微信通道当天限额用完，无法临时切到只走支付宝，
  整个下午所有机器都收不了钱。

**停得掉**
- **停单个支付通道**、**停某台机器的收款**、**停全网收款**（三档必须独立）。
- 停收款时下单链路必须同步 fail-closed：不能出现「收不了钱但还能建单」的中间态。
- 单账号支付熔断（异常刷单）。
  *不管的后果*：支付渠道出故障返回假成功，运营只能整机断网，
  连不涉及支付的 AI 简历服务也一起停了。

**查得到**
- 每一次支付尝试的完整流水：订单、通道、attemptId、状态迁移时间线、
  金额与优惠**锁定快照**、回调原文（脱敏后）、对账结果。
- 退款操作的操作人、理由、审批人、退款凭证号。
- **付款码（18 位）属于 N 档**：等同现金，只在内存中存在，
  **绝不进入 DOM、URL、日志、数据库、后台任何页面**。
  *不管的后果*：为了排查问题把付款码打进日志，日志被导出一次就等于把用户的钱包交出去。
- **人工改单/改状态的能力必须存在但必须留痕 + 双人复核**（回调永久丢失时的最后手段）。
  *不管的后果*：没有人工兜底，回调丢失的单子永远卡着，用户的钱扣了、纸没出、系统说未支付；
  有人工兜底但没留痕，则内部人可以把任意订单改成已支付。

### F12 出纸释放、打印进度与取件码核销

**看得见**
- **已支付但未出纸**的订单数（`paid` 但 `release` 未成功）与最老一单的年龄——**最高优先级指标**。
- 释放失败原因分布（打印机离线/卡纸/缺纸/Agent 未认领/任务超时）。
- 从支付到出纸的耗时分布（P50/P95）。
- 取件码：签发量、核销率、过期未取数量、**核销失败次数**、异地核销尝试（在另一台机器上输码）。
- 每台机器的出纸量、卡纸率。
  *不管的后果*：一台机器的 Agent 挂了但心跳还在，付了钱的单子全部堆在队列里，
  用户站在机器前等了十分钟什么都没出来，第二天运营才从工单里知道。

**改得了**
- 取件码位数、有效期（当前设计口径有 24h 凭码取件的说法）、允许核销的终端范围
  （只在原机取 vs 同站点任意机器取）。
- 释放重试次数与重试间隔、任务超时时限。
- 打印任务队列的并发与优先级。
- 出纸失败后的默认处置（自动重试 / 自动转待取 / 自动发起退款）。
  *不管的后果*：默认策略是「失败就关单」，用户付了钱、纸没出、单子还关了，
  只能走投诉才能拿回钱。

**停得掉**
- **暂停某台机器的出纸释放**（发现打印内容异常或机器故障时），已支付订单转为「待取件」不作废。
- 作废某个取件码（发现被冒领风险时）。
- 全网暂停释放（打印内容出现批量违规时）。
  *不管的后果*：发现有人用机器批量打印违规内容，运营只能拔电源，
  已支付的正常用户订单一起被作废。

**查得到**
- 每单的履约时间线：建单 → 支付 → 释放 → Agent 认领 → 出纸完成 / 失败，每一步的时间与操作方。
- 取件码的每一次核销尝试：时间、终端、输入是否正确、是否成功、由谁核销
  （用户自助 vs 现场人员代核销）。
- **现场人员代核销必须留痕**（这是「别人的材料被别人取走」唯一的追溯手段）。
  *不管的后果*：用户说「我的简历被别人取走了」，运营查不到是谁在什么时候核销的那个码。

### F13 纸质扫描（ADF）

**看得见**
- 扫描会话量、成功率、失败原因（ADF 卡纸/未放纸/超时/Agent 未响应/投递失败）。
- 平均页数、平均耗时、重扫率（重扫率高 = 扫描质量有问题）。
- 扫描件的存储用量与保留期到期情况。
- **扫描是否收费**要和口径一致——若设计上「扫描不收费」，则应有指标验证确实没有产生扫描计费。
  *不管的后果*：某次改动让扫描误进了计费链路，用户被按页收了扫描费，
  和屏幕上写的「扫描不收费」直接矛盾，属于**多收钱**。

**改得了**
- 分辨率/彩黑/输出格式（PDF/PDF-A/JPEG）的可选项与默认值。
- 单次扫描页数上限、会话有效期、`controlToken` 有效期。
- 扫描件的保留期（扫描件里常有身份证、毕业证，应当按敏感档处理）。
  *不管的后果*：扫描件按普通文档留 90 天，实际上里面全是证件影像，
  保留期和敏感档口径不一致，一次检查就是问题。

**停得掉**
- 关闭扫描功能（单机 / 全网）。
- 中止某个进行中的扫描会话（现场发现有人在扫不该扫的东西）。
  *不管的后果*：ADF 走纸机构故障会撕纸，运营关不掉这个入口，
  用户把毕业证原件喂进去被撕坏，赔的是原件。

**查得到**
- 每个扫描会话的流水：终端、页数、参数、结果、生成的文件 ID、投递给了谁。
- **扫描图像内容属于 N 档**；后台只展示页数与缩略图占位，不展示可辨识内容。
  *不管的后果*：后台列表页贴心地渲染了缩略图，运营列表一拉就是一屏身份证。

### F14 文件加工：图片转 PDF、签名盖章

**看得见**
- 各加工能力的调用量、成功率、失败原因、平均耗时与图片张数分布。
- 签名盖章：授权勾选率（设计上未勾选不可生成，所以这个值应恒为 100%，
  **低于 100% 就是门控被绕过**）。
- 加工产物的去向分布（存手机 / 发邮箱 / 打印），以及各去向的免费/收费口径是否正确执行。
  *不管的后果*：授权门控被某次改动绕过，出现了未经授权就合成签名的文件——
  这在法律效力上是伪造，比任何技术故障都严重。

**改得了**
- 单次可合成的图片张数上限、输出 PDF 的页面尺寸与留白规则。
- 签名/印章的可用位置、尺寸限制、是否允许上传印章图。
- 授权声明文案（法律效力声明是要出现在屏幕上的，必须可改可版本化）。
  *不管的后果*：法务改了声明措辞，改不进去，屏幕上还是旧措辞。

**停得掉**
- 单独关闭签名盖章（这是所有功能里法律风险最高的一个，必须能独立停）。
- 关闭图片转 PDF。
  *不管的后果*：接到举报说有人用这台机器伪造盖章文件，
  运营没有单独的开关，只能停整台机器。

**查得到**
- 每次签章合成的流水：任务 ID、授权勾选时间戳、授权文案版本号、
  签章位置、输出文件 ID、后续是否被打印。
- **签名图像与印章图像属于 R 档**（配合执法或投诉调查时可调阅，走审批 + 留痕）。
  *不管的后果*：公安来查一份伪造盖章的材料是不是这台机器出的，
  运营拿不出任何可以证明或排除的记录。

### F15 AI 助手「小青」对话（含语音）

**看得见**
- 对话轮次量（按天/按终端/按账号）、平均轮次、会话时长。
- **Token 用量与成本**：按 provider × 模型 × 功能 × 天，**必须能算出单次成本与日累计花费**。
- 失败率与失败类型分布（provider 超时 / 限流 / 内容安全拦截 / 余额不足）。
- 意图识别后跳转的分布（用户问完之后真的去办事了吗）。
- 语音：转写调用量、时长、成本、失败率。
- **单账号 / 单终端的调用排行**（找出异常刷用）。
  *不管的后果*：模型供应商悄悄涨价或某个 provider 挂了，
  运营要等用户投诉「小青不理我」才知道；成本要等月底账单才知道，
  而那时钱已经花完了。

**改得了**
- provider 与模型选择、超时、重试次数、**降级顺序**（主模型不可用时退到哪个）。
- 单次最大 token、上下文轮数上限。
- **限流**：单账号 N 次/分钟、N 次/天；单终端 N 次/分钟；全网 QPS 上限。
- **预算**：日/月成本上限，触顶后的行为（降级到小模型 / 只回固定话术 / 直接停）。
- 系统提示词与话术模板、免责声明文案（「不是真人」的声明必须可版本化）。
  *不管的后果*：一个人在机器前反复刷对话玩，一天刷掉几百块 API 费用，
  运营没有任何频次限制手段。

**停得掉**
- 关闭 AI 助手（全网 / 单终端 / 单账号），关闭后**页面必须显示诚实空态**
  （「AI 顾问暂停服务」），不得假装在思考。
- 一键切到备用 provider。
- 预算触顶自动熔断。
  *不管的后果*：provider 返回了不当内容，运营停不掉，只能眼看着它继续对着公众屏幕输出。

**查得到**
- 每次调用的元数据流水（**M 档**）：时间、终端、账号、功能、模型、
  输入/输出 token、耗时、结果码、成本。
- **对话内容属于 R 档**：默认不可读；因内容安全举报、投诉或监管要求需要调阅的，
  走审批 + 目的登记 + 时限 + 留痕 + 用户可见。
- 内容安全拦截命中的**类别与计数**（M 档）可见，**命中的原文**（R 档）需审批。
  *不管的后果*：为了做质量分析把所有对话原文存下来给运营随便看，
  用户和 AI 说的求职焦虑、家庭困难、身体状况全部变成运营可翻阅的档案。

### F16 简历采集与 AI 解析（含 OCR）

**看得见**
- 解析调用量、成功率、失败原因分布（格式不支持 / 页数超限 / OCR 失败 / LLM 失败）。
- **OCR 与 LLM 分开计量**：各自的调用量、成本、失败率、平均耗时。
- OCR 置信度分布与低置信度占比（低置信度高 = 用户拿到的解析结果不可信）。
- **OCR 失败后是否仍调用了 LLM**——设计口径是「OCR 失败不调 LLM」，
  这个值应恒为 0，非 0 即在白烧钱。
- 图片简历 / 扫描版 PDF / 文本 PDF 的构成比例（决定成本结构）。
  *不管的后果*：OCR 供应商密钥被禁用，所有图片简历解析失败但仍继续调 LLM，
  每一次都花钱产出一份空报告，用户拿到无意义结果，钱也花了。

**改得了**
- OCR provider 与密钥、受控页数上限（当前设计口径 ≤3 页）、置信度阈值。
- 解析的 LLM 模型、超时、重试。
- 单账号解析次数额度（免费几次、超出怎么办）。
- 支持的输入格式白名单。
  *不管的后果*：有人上传 50 页 PDF 反复解析，单次成本翻十几倍且无上限。

**停得掉**
- 关闭 OCR（保留纯文本解析）、关闭整个解析能力。
- 单账号解析封禁。
- 成本熔断。
  *不管的后果*：OCR 计费方式变更导致成本突然涨十倍，
  运营发现时已经花掉几千块。

**查得到**
- 每次解析的元数据（M 档）+ **结构化结果的字段完整度**（哪些槽位解析到了）。
- **简历原文与解析出的结构化个人信息属于 N 档**：
  姓名、电话、身份证号、学校、工作经历**不在后台任何列表页展示**。
- 密钥轮换记录（谁在什么时候换了 OCR/LLM 密钥）。
  *不管的后果*：后台为了「方便排查解析质量」把解析出的结构化字段展示出来，
  于是后台变成了一个可检索的求职者个人信息库——这已经不是产品边界问题，是数据安全事故。

### F17 简历 AI 诊断与逐条优化

**看得见**
- 诊断调用量、优化调用量（**分开计量**，是两次独立的模型花费）、成功率、单次成本。
- 逐条裁决的分布：采纳 / 保留 / 自己写 / 未决——这是衡量 AI 建议质量的唯一真实信号。
- 生成后是否被导出或打印（= 用户认不认这份结果）。
- 报告生成失败率与失败原因。
  *不管的后果*：模型换了版本之后建议质量下滑，采纳率从 60% 掉到 15%，
  运营手上只有「调用量还在涨」这一个数，看不出用户其实已经不用了。

**改得了**
- 诊断维度清单与权重、优化建议的条数上限。
- 模型与温度、单次 token 上限。
- 单账号免费诊断/优化次数、超出后的处理（收费 / 拒绝 / 降级）。
- 「AI 只新增版本、永不覆盖原件」这条规则的实现参数（保留多少个版本）。
  *不管的后果*：版本数无上限，一个用户攒了 40 版简历，存储和列表都撑不住；
  或者版本被覆盖，用户的原件丢了。

**停得掉**
- 关闭诊断 / 关闭优化（独立开关）。
- 单账号频次熔断。
  *不管的后果*：一个人反复对同一份简历刷诊断，成本无上限。

**查得到**
- 每次诊断/优化的元数据 + **裁决动作流水**（哪一条被采纳、什么时候）。
- **简历正文、诊断结论正文、优化前后的对照文本属于 N 档**。
  运营能看到「做了一次优化、给出 12 条建议、采纳 7 条」，
  **不能看到那 12 条建议写的是什么，更不能看到简历内容**。
  *不管的后果*：把「建议原文」放进后台以便运营评估质量，
  等于把用户简历的具体缺陷（学历、空窗期、离职原因）暴露给运营人员。

### F18 从零生成简历（语音访谈填槽 + 模板 + 导出）

**看得见**
- 访谈完成率（开始了多少、答完了多少、中途放弃在第几题）。
- 语音转写调用量、时长、成本、失败率；语音 vs 打字的使用比例。
- 生成成功率、导出/打印转化率。
- 模板使用分布（哪个模板真的被用）。
  *不管的后果*：语音转写在嘈杂大厅的准确率极低，用户答三题就放弃，
  运营只看到「生成量少」，找不到原因是转写不准。

**改得了**
- 访谈题库（题目、顺序、跳题逻辑、快捷回答选项）——**不发版就能改**。
- 模板库的上下架、默认模板、模板与岗位类型的对应。
- 语音转写 provider、单次录音时长上限。
- 导出格式与水印。
  *不管的后果*：题库写死在代码里，现场发现某道题所有人都答不上来，
  要等下次发版才能改。

**停得掉**
- 关闭语音输入（只留打字），关闭整个生成能力。
- 下架某个模板（模板排版有问题时）。
  *不管的后果*：某个模板导出的 PDF 在打印机上错位，
  运营下不掉这个模板，每天继续有人打出废纸并要求退款。

**查得到**
- 每次生成的元数据 + 使用了哪个模板哪个版本。
- **访谈答案、录音、生成的简历内容全部 N 档**；
  **录音默认不落盘**（设计口径已明示「录音不落盘」），若为质量分析需要留存必须单独取得授权。
  *不管的后果*：为了「优化题库」把录音存下来，用户在公共大厅说出的家庭情况、
  身体状况被完整录下并可被运营回放。

### F19 求职材料工坊

**看得见**
- 各材料类型（求职信/封面/清单）的生成量、成功率、成本。
- 生成后打印率（生成了不打 = 用户不满意或流程断了）。
- 模板使用分布。
  *不管的后果*：某类材料生成后只有 5% 被打印，说明产出不可用，
  但成本每次都照付。

**改得了**
- 材料模板库（增删改、上下架、按站点差异化）。
- 每类材料的生成参数与字数范围。
- 免费额度与收费口径（设计上有「扫描不收费」这类逐项标注，需要可配）。
  *不管的后果*：屏幕上标的「不收费」和实际计费不一致，用户当场发现被收了钱。

**停得掉**
- 关闭整个工坊 / 单独下架某类材料。
- 单账号额度熔断。
  *不管的后果*：某类材料模板里有错误表述（例如承诺了本平台不能承诺的事），
  下不掉，继续对外产出。

**查得到**
- 生成流水（元数据）+ 模板版本。
- **材料正文 N 档**。
  *不管的后果*：出现「机器生成的求职信里写了不实内容」的投诉时，
  没有模板版本记录，说不清是模板问题还是模型问题。

### F20 AI 求职决策报告（岗位匹配 / 职业规划 / 自我评估）

**看得见**
- 三类报告各自的生成量、成功率、单次成本、平均耗时。
- **授权（consent）取得率与撤回率**——这三类都要读用户简历，授权链条必须可量化。
- 打印率（报告生成了有没有被带走）。
- 自我评估：作答完成率、中途放弃点。
- 岗位匹配：三档结论（高/中/低）的分布——**分布严重偏斜说明模型在敷衍**。
  *不管的后果*：模型退化成不管输入什么都输出「中等」，
  运营看调用量一切正常，用户拿到的每一份报告其实都是废纸。

**改得了**
- 各报告的维度定义与文案模板、结论档位的划分口径。
- 自我评估题库与题目顺序。
- 模型、token 上限、单账号频次与免费额度。
- 授权文案与授权范围（授权只覆盖本次任务，不扩展到历史记录——这条是硬口径，需可版本化）。
- 报告的保留期与自动删除（自我评估设计口径有「24h / 撤回即物理删除」的承诺）。
  *不管的后果*：屏幕上向用户承诺 24 小时删除，后台保留期配成 90 天，
  这是**对用户明确作出的承诺没有兑现**——比没承诺更严重。

**停得掉**
- 三类报告各自独立开关（岗位匹配涉及第三方岗位数据，风险面和职业规划不同）。
- 单账号频次熔断、全局成本熔断。
  *不管的后果*：岗位数据源出问题返回脏数据，匹配报告全是错的，
  停不掉单项只能把整个简历服务一起停。

**查得到**
- 每次生成的元数据 + **授权记录**（何时授权、授权范围、何时撤回、撤回后是否真的删了）。
- **报告正文与用户的评估答案 N 档**。
- 撤回授权后的**删除执行结果**必须可查（删了几条、有没有失败）。
  *不管的后果*：用户撤回授权，系统显示成功但后台删除任务失败，
  数据还在——用户以为删了，实际没删，这是最典型的「承诺与事实不符」。

### F21 AI 模拟面试（含语音录音与转写）

**看得见**
- 场次量、完成率（开始 vs 答完）、平均轮次、平均时长。
- **成本三段分开算**：出题（LLM）+ 转写（ASR）+ 报告生成（LLM），
  这是全产品**单次成本最高**的功能，必须能看到单场成本。
- 转写失败率、音频上传失败率。
- 报告打印率。
- 练习单（`practice-sheet`）生成量。
  *不管的后果*：一场面试可能有十几轮语音转写，单场成本是简历诊断的十倍以上；
  没有单场成本视图，运营根本不知道这个功能在吃掉多少预算。

**改得了**
- 题库（行业 × 难度 × 时长）与出题策略、每场题目数上限。
- 单场时长上限、单账号每日场次上限。
- 语音 provider、单条录音时长上限、是否允许语音（公共场所可能要求只用打字）。
- **音频保留策略**：默认应为「转写后即删」，保留天数可配但要有上限。
  *不管的后果*：录音永久保留，一台机器一年攒下几万条求职者的语音，
  这是极高价值的生物特征相关数据，一旦泄露不可挽回。

**停得掉**
- 关闭语音模式（降级为打字）、关闭整个模拟面试。
- 单账号场次熔断、全局成本熔断。
  *不管的后果*：ASR 供应商按秒计费且当月涨价，一天烧掉一个月预算，
  没有熔断只能等账单。

**查得到**
- 每场的元数据 + 三段成本明细 + 每一轮的时间线。
- **音频原声与转写文本、面试答案、报告正文全部 N 档**。
- 音频删除的执行结果可查。
- 「本机不评分、不排名、不预测通过」是设计硬口径，
  因此**后台不得存在任何按用户面试表现排序、打分、导出名单的能力**。
  *不管的后果*：为了「帮助机构了解求职者水平」把面试评分导出给合作机构，
  这一步就直接跨过了合规边界（详见 §4）。

### F22 签约风险提示（合同 AI 审查）

**看得见**
- 审查任务量、成功率、平均页数与耗时、单次成本。
- 授权取得率（这个功能读的是劳动合同，授权链条最敏感）。
- OCR 覆盖率与用户确认页数的情况（`awaiting_confirmation` 分支）。
- 报告生成与打印率、任务取消率。
- **功能开关当前状态**（设计口径为默认关闭，只有真实 capability 开启后才生效）。
  *不管的后果*：capability 被误开到全网，机器开始对着劳动合同输出「风险提示」，
  而这些提示在法律上没有任何依据——用户据此拒签或签署，后果由运营方承担。

**改得了**
- 功能开关（默认关、逐终端开）、最大页数、模型与提示词。
- **免责声明文案**（「不构成法律意见」必须可版本化并强制展示）。
- 授权范围文案（授权只覆盖本次任务）。
- 报告与原件的保留期（合同是高敏感文件，应走最短保留档）。
  *不管的后果*：免责声明措辞被法务要求修改但改不了，
  产品在没有合规措辞的情况下继续输出法律相关建议。

**停得掉**
- 一键全网关闭（这是所有 AI 功能里唯一一个「宁可不做」的）。
- 单终端关闭、单账号频次熔断。
  *不管的后果*：模型给出了错误的法律判断并被用户采信，
  运营停不掉，错误持续扩散。

**查得到**
- 每次审查的元数据 + 授权记录 + 免责声明版本号 + 用户确认动作。
- **合同原文与审查结论正文 N 档**（合同里有薪资、竞业、违约金，全是最敏感的信息）。
- 删除执行结果可查（设计口径明确「删除结果以真实返回为准，失败时诚实说明」，
  所以删除失败必须在后台可见并可重试）。
  *不管的后果*：用户点了删除，前端说删了，后台删除任务失败没人管，
  劳动合同原件留在存储里。

### F23 岗位信息浏览与外跳（含岗位 AI 解释 / 匹配 / 推荐）

**看得见**
- 岗位列表浏览量、搜索关键词分布（**热词表可见，但不与个人绑定**）、筛选使用率。
- 详情页浏览量、**外跳点击量（去来源平台 / 扫码）**——这是本产品能统计的终点，再往下没有数据。
- 按来源机构的岗位数、同步时间新鲜度、**过期岗位仍在展示的数量**。
- 岗位 AI 能力（解释 / 匹配 / 推荐）的调用量、成本、失败率。
- **来源三要素缺失的岗位数**（来源机构 / 同步时间 / 外部 ID 任一为空）。
  *不管的后果*：某个数据源两周没同步，机器上还在展示已经招满的岗位，
  用户扫码过去发现岗位早已下线——白跑一趟，且投诉的是本平台。

**改得了**
- 列表排序与默认筛选、每页条数。
- 岗位 AI 能力的开关、模型、频次限额。
- 岗位卡片上展示哪些字段（合规要求来源三要素常驻，这部分不可关）。
- 外跳前的提示文案（按钮文案受合规白名单约束，见 §4）。
  *不管的后果*：某个来源的岗位质量差需要临时降权，运营改不了排序。

**停得掉**
- **按来源机构下架**（某个数据源出问题时一次性隐藏它的全部岗位）。
- 单条岗位下架（举报虚假招聘时）。
- 关闭岗位 AI 能力。
- 关闭外跳（某个来源平台被查处时，二维码必须能立刻失效）。
  *不管的后果*：接到举报说某来源平台在骗培训费，
  运营只能一条一条藏岗位，藏的过程中还在有人扫码过去。

**查得到**
- 岗位上下架、审核状态变更、来源配置变更的操作流水。
- 单条岗位的完整来源溯源（哪个数据源、哪一批同步、外部 ID、原始字段）。
- 用户侧只记录**浏览与外跳**（设计口径明确），**不记录投递结果**。
  因此审计里**不存在也不得存在「谁投了哪家」这种记录**。
  *不管的后果*：出现虚假招聘纠纷，运营拿不出「这条岗位是哪个来源、什么时候同步进来的」，
  无法把责任界定到来源机构。

### F24 来源目录：线上平台 / 线下机构 / 找企业

**看得见**
- 各目录的浏览量、外跳/扫码量、按机构或平台的分布。
- 线下机构：营业状态展示是否准确、机构信息的最后更新时间。
- 企业目录：**指标展示开关的当前状态**（设计口径明确「指标受 Admin 开关控制」）。
- **来源三要素完整率**（这是合规硬指标）。
  *不管的后果*：一家已经注销的中介机构还挂在「线下机构」里，
  用户按地址跑过去扑空，甚至被拉进旧地址的骗局。

**改得了**
- 机构/平台/企业条目的增删改、排序、置顶、标签（官方 vs 经营性）。
- 企业详情展示哪些指标（开关）。
- **防诈提示条文案**（「不代收费用」「全流程只到到店咨询为止」这类声明必须可配可版本化）。
- 线上平台目录的条目（当前设计口径是硬编码常量，需求上应可运营配置）。
  *不管的后果*：某个线上平台改域名，机器上的二维码指向旧域名，
  旧域名被人抢注做钓鱼站——本平台的屏幕在给钓鱼站导流。

**停得掉**
- 单条机构/平台/企业下架，按类型批量下架。
- 关闭整个目录入口。
- **紧急二维码失效**（外跳链接立刻停用）。
  *不管的后果*：接到通报说某机构涉嫌违法收费，运营下架要走发版流程，
  期间机器继续在给它导流。

**查得到**
- 条目的增删改流水（谁、何时、改前改后、来源依据是什么）。
- 每条外跳的记录（时间、终端、目标机构）——**只记跳转动作，不记跳转之后的任何结果**。
  *不管的后果*：监管来问「你们为什么在政府大厅的机器上推荐这家机构」，
  运营答不出是谁加的、依据是什么。

### F25 招聘会全链

**看得见**
- 场次数、按状态（未开始/进行中/已结束）分布、来源机构分布、来源三要素完整率。
- 各场次的详情浏览量、参展企业查看量、导览图打开量、资料打印量、外部预约入口打开量。
- 参会规划（`visit-plan`）的生成量、成本、打印率——**这条走 AI 且有限流（设计口径 6/min）**。
- 签到：签到量与失败原因分布。
- **已结束但仍在展示的场次数**、**资料签名 URL 过期导致打印失败的次数**。
  *不管的后果*：招聘会已经开完两周还挂在首页，用户按上面的时间地点跑过去，
  现场空无一人——这是本产品最容易发生也最容易被投诉的一类事故。

**改得了**
- 场次的上下架、置顶、展示时间窗（结束后多久自动下架）。
- 导览图与展位数据的上传与更新（设计已把这列为 P1 缺口）。
- 资料文件的签名 URL 有效期。
- 参会规划的 AI 开关、限流阈值、模型。
- 签到方式（本机签到 vs 只引导到主办方渠道）——**签到在主办方那边完成是设计口径**。
  *不管的后果*：场次结束不自动下架，全靠人工，忘了就一直挂着。

**停得掉**
- 单场次下架、按来源机构批量下架。
- 关闭参会规划 AI（成本或质量问题时）。
- 关闭资料打印（资料内容有误时）。
  *不管的后果*：主办方临时取消一场会，运营下架不及时，
  几十个人白跑一趟并把责任归给本平台。

**查得到**
- 场次数据的来源溯源与每次同步/审核/发布的操作流水。
- 资料文件的每一次签名链接签发记录。
- 签到记录：时间、终端、场次——**只记「在本机打开了签到入口/完成了本机侧动作」，
  不构成向主办方提供求职者名单**（见 §4 待判定项）。
  *不管的后果*：主办方事后要核对到场人数，运营手上的口径和主办方对不上，
  也说不清本平台记的到底是什么。

### F26 政策服务与资格自查

**看得见**
- 政策条目浏览量、按领域分布、来源二维码打开量。
- 资格自查：发起量、完成率、各结论分支的分布。
- **来源地址缺失或无效的政策条目数**（设计口径：无效来源时二维码置灰并常显原因）。
- 政策条目的最后更新时间与**已失效但仍在展示**的数量。
  *不管的后果*：补贴政策已经调整（金额变了、截止日过了），机器上还是旧版，
  用户按旧版准备材料跑到窗口被退回——这类投诉直接指向政府大厅本身。

**改得了**
- 政策条目的增删改、生效期、来源链接、所属领域。
- 资格自查的题库与判定规则（设计口径为**确定性判定、零 LLM**，
  所以规则必须是可配置的规则表，不是模型）。
- 结论话术（**不得承诺到账**，这条是硬口径，文案要可版本化审核）。
  *不管的后果*：自查规则写死在代码里，政策一调整就要发版，
  中间几周所有人拿到的都是错的判定。

**停得掉**
- 单条政策下架、按领域批量下架。
- 关闭资格自查（政策调整期间，宁可不给判定也不给错判定）。
  *不管的后果*：政策调整当天，自查还在按旧规则告诉用户「您符合条件」，
  用户据此放弃了别的机会。

**查得到**
- 政策条目变更流水（谁、何时、依据哪份文件）+ 生效版本号。
- 每次自查的**答案与结论**：这里有个关键取舍——
  自查答案可能包含户籍、就业状态、低保、残疾等**敏感个人信息**。
  需求是：**答案默认 N 档，只保留结论分支与规则版本号用于统计**；
  若确需保留答案用于申诉举证，必须单独授权 + 加密 + 最短保留期。
  *不管的后果*：为了做「政策覆盖分析」把自查答案原样入库并可在后台检索，
  运营后台里就有了一张按户籍/低保/残疾可筛选的人员表——这是重大合规风险。

### F27 未接入 / 未开放专区门控

**看得见**
- 各未开放专区的进入次数（有多少人在找这个还不存在的功能）——
  这是唯一能量化「该不该建」的数据。
- 门控页上「现在就能做的」替代入口的点击转化率。
  *不管的后果*：智慧校园专区每天被点 300 次，运营完全不知道，
  排期上一直排在最后。

**改得了**
- 每个专区的**开放状态**（未接入 / 灰度 / 已开放）与**逐终端**生效
  （某所学校谈成了就只对那个点位开）。
- 门控页文案（「不是坏了，是还没开通」的具体说明、开放前提清单、预计开放时间）。
- 替代入口的配置。
  *不管的后果*：一所学校已经签约接入，但开放范围是全网开关，
  要么全网开（其他点位看到空数据）要么不开（违约）。

**停得掉**
- 已开放的专区能退回未开放态（数据源出问题时优雅降级，而不是报错）。
  *不管的后果*：校园数据源断了，页面报 500，用户看到一堆技术错误，
  而不是「暂时接不通」。

**查得到**
- 开放状态变更流水（谁、何时、对哪些终端开的、依据是什么）。
  *不管的后果*：某天某个专区突然对全网开放并展示了不该展示的学校数据，
  查不出是谁改的。

### F28 我的资产与记录

**看得见**
- 各类资产的**数量分布**（人均简历数、文档数、订单数、收藏数）与增长趋势。
- **保留期到期与清理执行情况**：应清未清数量、清理任务成功率、最老一份文件的年龄。
- 用户主动删除的次数与删除失败次数。
- 待办任务（`pending-tasks`）的存量与年龄。
  *不管的后果*：清理任务失败三周没人发现，敏感文件全部超期留存，
  同时「我的」页面还在按承诺的天数向用户展示保留期——承诺与事实不符。

**改得了**
- 三档保留期（敏感 / 一般 / 离场即清）的天数，且**与屏幕展示的口径同源**。
- 各类资产的单用户上限（简历版本数、文档数）。
- 清理任务的调度频率与批量大小。
  *不管的后果*：保留期在两处分别配置，屏幕说 7 天、后台跑 30 天，
  哪一处都不算错，但合起来就是欺骗。

**停得掉**
- 暂停自动清理（排查问题时，但**必须有最长暂停时限**，不能无限期暂停）。
- 单账号资产冻结（涉诉时保全证据，但冻结本身要留痕并有期限）。
  *不管的后果*：为了排查一个 bug 把清理关了，然后忘了开，
  半年后才发现所有文件都没清过。

**查得到**
- 每份资产的生命周期流水：创建、被引用、签名链接签发、用户删除、系统清理。
- **管理员的每一次访问必须留痕并对用户可见**（§0.3 硬要求）。
- **资产内容 N 档**：后台列表只显示类型、大小、页数、时间、状态；
  文件名可能含姓名（「求职简历-王雷.pdf」），因此**文件名默认脱敏展示**。
  *不管的后果*：后台列表直接渲染原始文件名，运营随手一拉就看到一屏真实姓名——
  这是最容易被忽略、也最容易被截图外传的泄露口子。

### F29 权益与活动领取

**看得见**
- 活动的曝光、进入、领取量、领取成功率与失败原因（已结束/已领完/不符合条件/重复领取）。
- **权益核销情况**：发放了多少、用掉了多少、过期未用多少、**折算成本是多少钱**。
- 单账号领取次数分布（找刷子）。
- 活动库存余量与预计耗尽时间。
  *不管的后果*：一个免费打印活动的库存被脚本刷空，真实用户一张也领不到，
  运营看到的只是「领取量很好」。

**改得了**
- 活动的创建/编辑/上下架、有效期、库存、**资格判定规则**
  （设计口径是**确定性判定、零 LLM**，所以是规则表不是模型）。
- 单账号领取上限、单终端上限、每日总量上限。
- 权益的抵扣规则与叠加顺序（和 F10 价目联动）。
- 活动文案，**包括「谁出的钱」的披露**（设计口径要求明示资金来源）。
  *不管的后果*：库存改不了，活动效果好想追加只能新建一个活动，
  用户重复领取导致成本翻倍。

**停得掉**
- 单活动紧急下架（**已发放的权益是否同时失效必须是一个明确选项**，不能默认）。
- 单账号领取封禁。
- 全局领取熔断（发现被刷时）。
  *不管的后果*：活动规则写错导致每人可无限领，
  运营停不掉，一晚上发出去几千次免费打印——**这是直接的钱**。

**查得到**
- 每一次领取的流水：账号、时间、终端、活动、判定结果、判定依据（命中了哪条规则）。
- 每一次核销的流水（哪一单用掉了哪一份权益、抵扣了多少钱）。
- 活动配置变更流水（尤其是库存和规则的每一次修改）。
- **设计口径明确「不做签到积分抽奖邀请解锁」**，
  因此后台**不应存在**基于用户处境（失业时长、困难身份）做差异化投放的能力（见 §4）。
  *不管的后果*：财务对不上账——发出去的权益金额和打印收入的缺口无法解释。

### F30 消息通知

**看得见**
- 通知发送量（个人 / 广播分开）、到达率、已读率、删除率。
- 按通知类型的已读率（哪类通知没人看）。
- 广播通知的覆盖范围与实际触达人数。
  *不管的后果*：「您的打印单已可取件」这类关键通知发失败了没人知道，
  用户不知道东西好了，取件码到期作废。

**改得了**
- 通知模板（文案、变量、跳转目标）与版本。
- 各类通知的开关（哪些必发、哪些可关）。
- 广播的目标范围（全网 / 站点 / 终端 / 用户分群）与发送时间。
- 频次上限（防止对同一用户轰炸）。
  *不管的后果*：模板写死，节假日想发一条大厅休息公告要发版。

**停得掉**
- 撤回/停止一条正在发送的广播。
- 关闭某类通知。
  *不管的后果*：广播文案写错了日期已经发出去，撤不回，
  几千人按错误日期跑到大厅。

**查得到**
- 每条广播的发送流水：谁发的、何时、发给了谁、模板版本、审批人。
- **广播必须有审批**（这是唯一一个能主动向大量用户推送内容的通道）。
  *不管的后果*：任何一个有后台账号的人都能对全部用户群发任意内容，
  出事之后查不到是谁发的。

---

### F31 反馈工单

**看得见**
- 工单量、按分类分布、平均首次响应时长、平均关闭时长、未处理工单积压数与最老一单年龄。
- **按终端的工单密度**（某台机器工单特别多 = 那台机器有问题）。
- 与打印任务关联的工单占比（`relatedPrintTaskId`）。
- 用户重开/追问次数（一次没说清）。
  *不管的后果*：3 号机每天 5 张工单，全网平均是 0.2 张，
  没有按终端的视图就看不出这台机器已经坏了两周。

**改得了**
- 工单分类与表单字段、必填项。
- SLA 时限与超时升级规则、分派规则（按站点分给对应值守）。
- 自动回复模板。
  *不管的后果*：工单全进一个池子没有分派规则，
  某个站点的工单没人认领，积压两个月。

**停得掉**
- 关闭工单入口（滥用时），但**必须保留现场人工出口**——
  不能出现「既提不了工单又找不到人」的死路。
- 单账号提单封禁。
  *不管的后果*：有人恶意刷工单把队列淹掉，真实工单被埋。

**查得到**
- 工单全生命周期流水：提交、分派、每次回复、状态变更、关闭，含操作人。
- 用户在工单里附上的文件属于 **R 档**：处理期内可读，**关单后自动失效**，且访问留痕。
  *不管的后果*：工单附件永久可读，处理完的工单三年后还能被任何客服点开看到用户的简历。

### F32 账号、隐私与数据请求

**看得见**
- 数据请求量（撤回授权 / 删除 / 导出）与**执行成功率**、平均处理时长、失败积压数。
- 手机号换绑量与换绑失败原因、`step-up` 二次验证的通过率。
- 授权状态分布（有多少人授权了 AI、有多少人撤回过）。
- **删除请求执行失败的清单**——必须逐条可见、可重试、可上报。
  *不管的后果*：用户提交了删除请求，系统记了一条但执行失败，
  后台没有失败视图——对用户是「已删除」，对监管是「未履行」。

**改得了**
- 数据请求的类型清单与各类型的 SLA。
- 撤回授权后的连带行为（撤回 AI 授权是否同时删除已生成的报告——这必须是明确配置，
  且要和屏幕上的承诺一致）。
- 换绑的验证强度与冷却期。
- 隐私页展示的**保留期口径表**（必须与 F07/F28 的实际配置同源）。
  *不管的后果*：隐私页写「敏感 7 天 / 一般 90 天 / 离场即清」，
  实际清理任务按别的天数跑，页面成了一份不实声明。

**停得掉**
- 单账号封停（并使在场会话立即失效）。
- 关闭换绑功能（发现被用于账号劫持时）。
  *不管的后果*：有人通过换绑接管了别人的账号，
  运营只能等着一个个处理，堵不住口子。

**查得到**
- 每一条数据请求的完整链路：提交（含幂等键）→ 受理 → 执行 → 结果 → 通知用户，含失败原因。
- 每一次账号封停/解封/换绑的操作人与理由。
- **这一整条链路是监管取证材料，必须能按用户单独导出。**
- 设计口径明确「删除留日志但日志不含内容」——
  因此审计日志里**只记删了什么 ID、几条、什么时候，不记删掉的内容**。
  *不管的后果*：为了「万一要恢复」把删除前的内容备份进日志，
  于是「删除」变成了「换个地方存着」，用户的删除权在系统里从未真正生效。

## 3. 按后果严重度排序

排序原则：**直接损失钱 > 损失/泄露数据 > 用户已付费却拿不到服务 > 对用户/监管的承诺落空 >
运营看不见问题 > 处置手段不够细**。同级内按发生概率与波及面排。

## 4. 可能触碰合规边界的需求（提请判断，未自行删除）

以下需求在运营上有真实价值，但**都不同程度地靠近或可能越过**
「不是招聘平台 / 不收简历 / 不做候选人筛选」这条红线。按要求全部列出，不自行取舍。

| # | 需求 | 为什么有价值 | 为什么可能越界 | 我的倾向 |
|---|---|---|---|---|
| C1 | **招聘会签到数据回传主办方** | 主办方需要核对到场人数，也是合作的对价 | 若回传的是**人员名单**（姓名/手机号），等于本平台在向第三方提供求职者个人信息；若只回传**聚合人次**则安全 | 只允许聚合人次；名单一律不给 |
| C2 | **岗位外跳记录按企业维度统计并对外提供** | 能告诉来源机构「你的岗位被看了多少次」 | 「某人对某企业有兴趣」在语义上非常接近投递意向；一旦按人下钻或按企业导出名单，就是变相的候选人推荐 | 只允许企业维度**聚合计数**，禁止任何按人下钻与名单导出 |
| C3 | **给合作机构后台开放终端使用数据** | 机构要看自己的数据源效果 | 粒度一旦细到个人（谁看了、看了几次、什么时候），就跨过了「只做信息入口」 | 需明确粒度上限：只到「条目 × 日 × 聚合计数」 |
| C4 | **面试/匹配/评估结果的运营侧统计** | 衡量 AI 质量必须看结论分布 | 若统计能按人下钻、能排序、能导出，就构成事实上的候选人评分与筛选（且设计口径已明示「不评分不排名不预测」） | 只允许**无主体的分布统计**；禁止任何以人为行的表 |
| C5 | **AI 对话/简历内容的抽样质检** | 不看内容就无法评估模型质量、也无法发现有害输出 | 需要读用户原文，且用户是在求职焦虑下说的话 | 必须走 R 档：授权或匿名化 + 审批 + 目的登记 + 时限 + 用户可见；不得建立常态化可检索库 |
| C6 | **面试录音留存用于质检或纠纷举证** | 出现「AI 说了不当的话」的投诉时是唯一证据 | 语音是高敏感数据，公共场所录制且可能含第三人声音 | 默认转写后即删；留存必须单独取得授权且有硬上限 |
| C7 | **免登录用户的跨会话识别（用于限流）** | 不识别就无法防刷，AI 成本无法控制 | 用设备指纹/生物特征等方式识别未登录自然人，本身是个人信息处理行为 | 优先用「终端 + 时间窗」限流，避免建立跨会话个人标识 |
| C8 | **按用户处境的差异化权益投放** | 把有限的免费额度给最需要的人 | 需要判定「失业时长/困难身份」，且设计口径已明确「不拿你的处境换运营指标」 | 建议不做；如必须做，判定依据只能来自用户主动出示的官方凭证，且不入库 |
| C9 | **政策自查答案的留存与统计** | 分析政策覆盖面、优化题库 | 答案含户籍、低保、残疾、就业状态等敏感个人信息 | 只留结论分支 + 规则版本；答案原文不入库 |
| C10 | **待机屏广告按用户画像定向投放** | 提高广告价值 | 需要建立求职者画像，且在政府大厅场景下用求职者数据做商业投放极敏感 | 建议只按**终端/站点/时段**投放，不按人 |
| C11 | **手机号明文在后台可见（用于客服外呼）** | 处理工单时要能联系用户 | 手机号是核心个人信息，列表页明文展示等于批量可导出 | 列表掩码；解掩码走审批 + 单条 + 留痕 + 有效期 |
| C12 | **「已付费未出纸」的人工改单能力** | 回调永久丢失时这是唯一的兜底 | 能把任意订单改成已支付/已出纸，是内部作恶的最大口子 | 必须做，但要双人复核 + 全量留痕 + 金额上限 |
| C13 | **单账号封停会连带使在场会话失效** | 防刷必需 | 若封停判定错误，正在办事的用户会被当场中断，材料可能丢失 | 需要「封停但允许完成当前已支付订单」的选项 |

## 5. 本文的使用方式

1. 与 `admin-capability-inventory-2026-09-02.md`（后台现状盘点）**逐条交叉对比**，
   产出「已有 / 部分有 / 完全没有」三档差距表。
2. 差距表按 §3 的严重度梯队排优先级——**第一、二梯队的缺口是上线阻塞**，
   第五、六梯队可以进上线后 backlog。
3. §4 的 13 条待判定项需要产品与法务给结论，结论写入
   `docs/compliance/compliance-boundary.md`，不要留在本文。
4. 本文只是需求侧的一份输入，不构成排期，也不修改任何既有进度文档口径。
