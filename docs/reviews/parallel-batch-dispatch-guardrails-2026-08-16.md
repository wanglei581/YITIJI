# 并行批次派单护栏（2026-08-16）

> 本文记录 2026-08-16 一天内跑 12 个并行批次时**实际发生过**的失败，以及对应的派单约束。
> 每一条都有实例，不是预防性想象。写给后续任何做多批次协同的会话（含协调者本人）。

---

## 0. 为什么需要这份文档

这一天里，**协调者自己犯的错比批次多**，且错误类型高度集中：

- 把未经核实的推断当事实写进派单（3 次）
- 让多个批次共用同一份资源而不加隔离（3 次）
- 依据一份自己委托的、未与既有决定交叉核对的规格派单（1 次）

批次侧的产出质量普遍高于协调者的输入质量。**因此本文的主体是约束协调者，不是约束批次。**

---

## 1. 共享资源：三次实际碰撞

### 1.1 端口互杀

**发生了什么**：协调者在派单模板里写了「跑套件前先清干净端口」。多个批次并行时，A 批次的「清理」杀掉了 B 批次正在跑的 dev server，B 得到一批无意义的失败。

**根因**：防污染措施本身成了污染源。

**约束**：
- **不得在派单里写任何「清理端口 / kill 占用进程」的指令。**
- 需要独占时用 `/tmp/kiosk-browser-suite.lock` 的 `mkdir` 原子锁（`mkdir` 在同名目录存在时失败，天然互斥），跑完删除。
- 批次必须在跑套件前后各记一次 `foreign_before/after` 外部监听数，两次都为 0 才算干净窗口。

### 1.2 scratchpad 文件互相覆盖

**发生了什么**：两个批次都把运行脚本写成 `run-suites.sh`。B 批次覆盖了 A 批次**正在执行中**的脚本。zsh 会在运行过程中重读脚本文件，于是 A 批次执行到一半换了内容，产生无法解释的失败。

**根因**：共享目录 + 通用文件名。

**约束**：
- **scratchpad 里的一切临时文件必须带批次代号后缀**（`run-suites-s2-6.sh`），派单模板里明写。
- 这条比端口互杀更隐蔽：端口冲突会立刻报错，脚本被换会得到一个**看似合理但错误**的结果。

### 1.3 多个批次被指向同一个 worktree

**发生了什么**：协调者把两个批次指向同一个目录。第二个批次去用时，发现该目录**在它两次 git 调用之间换了分支、还长出了别人的未提交文件**。它没有在那里提交（否则会把自己的文件混进别人的 commit），自行另开了干净 worktree。

**约束**：
- **每个批次一个 worktree，从干净 `origin/main` 新建，不复用。**
- 派单时不要指定「去某某目录干活」，让批次自己开。
- 批次若发现所在目录有别人的在制品，**正确做法是另开，不是就地提交**。

## 2. 事实核实：协调者背景信息的正确用法

一天内批次纠正协调者 **5 次**，全部正确：

| 协调者说 | 事实 | 后果（若照抄） |
|---|---|---|
| Prisma 模型数 93 | 90（后又变 88） | 两个 job 继续红，报另一个错 |
| 四条 api 门禁放静态检查步 | 必须放在 `prisma generate` 之后 | `Cannot find module '../generated/prisma/client'` |
| PG schema 要手改 | 由 `sync-postgres-schema.ts` 机械生成，手改判漂移 | `db:pg:sync:check` 报红 |
| 到机核销在生产上断链 | 入口存在且可达，修复提交早两天 | 按紧急事故排期，浪费一刀 |
| 「用户侧退款端点缺失」是缺口 | 产品已封板不做，且有上线文案在说反话 | 推翻产品决定而不自知 |

**约束**：

- 派单模板必须包含这句：**「我给的背景可能有错。发现我说错了，直接指出并按事实做，不要将就我的措辞。」** 这句话今天挽回了 5 次。
- 涉及**数字**（计数守卫、阈值、基线）时额外加一句「**自己数，不要照抄我的**」。协调者当日在同一个模型计数上先后说出 87 / 93 / 90 / 88 四个值。
- 批次交付时必须给「**未验证项清单**」。今天所有高质量交付都带这个，且清单里的第一项往往正是后来 CI 报红的地方 —— 这说明清单是有效的风险预测，不是免责声明。

## 3. 「缺口」的判定：原型不是生产

**发生了什么（两次）**：

1. 一份补页规划把原型页上的「XX 页还没建」当成生产缺页。实际五条生产路由一直都在。
2. 一份能力盘点把「V6 原型没画码输入框」推成「生产上找不到输入口」，判为 P0 正在断链。实际生产入口存在、可达、且源码注释明写「合并 V6 时不得删除」，修复提交早于该盘点两天。

**根因相同**：取证基准（`origin/main`）是对的，但**推理方向从原型跨到了生产**。

**约束**：

- 任何「缺口」结论必须标明**缺在哪一侧**：原型缺稿 / 生产缺能力 / 两侧都缺。混写会让排期整体走歪。
- 生产侧「不存在」的结论，必须给出**穷举证据**（路由表 + 入口引用 + 后端端点三者都查过），不能只给关键词 0 命中。关键词覆盖率高不代表推理方向对 —— 上述第 2 例正是用四组关键词交叉验证后仍判错的。
- 同目录同日的其它文档如有相反结论，**必须先解释矛盾再下判断**。上述第 2 例与同目录 a3 规格 §5.2-8「状态 7 主链路已完整」直接矛盾而未察觉。

## 4. 派单前必须交叉核对既有决定

**发生了什么**：协调者依据一份**自己委托产出**的缺口规格派单，该规格把一条产品有意不做的事列为「后端缺口」。批次实现完成后才发现它在推翻五处已封板声明，其中一处是用户可见的上线文案。

**根因**：规格产出时没有交叉核对既有决定；派单时协调者又没有二次核对，把「我自己的文档」当成了权威来源。

**约束**：

- **自己委托的规格不构成产品授权。** 据它派单前，至少 grep 一次核心关键词，确认仓库里没有相反的显式声明（尤其是 `绝不`、`不提供`、`不做` 这类措辞）。
- 若发现矛盾：**停下来交给用户裁决，不要自行选一边**。产品边界不是技术细节。
- 批次若在实现中发现自己在推翻既有决定，**正确做法是收窄实现使其不正面冲突 + 显式上报**，而不是硬做或擅自放弃。今天的退款批次正是这么做的（只放行 5/72 种状态组合、刻意不覆盖游客单以保住上线文案为真），是范例。

## 5. 共享文件的并行冲突是设计信号

两个批次各往同一张 AI 功能位注册表加了一行，产生冲突。

**这不是坏事。** 它说明该表是**集中注册表**：新能力必须登记才会被 Admin 配置页看见、被用量统计算进去。若设计成分散注册，两批次会各写各的、互不冲突，然后留下一张**永远不全的表**。

**约束**：
- 遇到这类冲突，先判断它是「设计在起作用」还是「设计有缺陷」，再决定是消除冲突点还是保留它。
- union 合并两个对象字面量时**必须补回结构闭合符**，并在推送前跑 typecheck。今天这里漏了 `},`，靠 typecheck 拦下，否则会带着语法错误进 CI 浪费一整轮。

---

## 6. 计数守卫：收成单一常量

`verify-recruitment-p1-schema.ts` 原本用两处独立字面量分别校验 SQLite 与 PG 的模型数。这个形状留着一个失败模式：**改了一处、忘了另一处**，且改对一半时 CI 仍红，容易让人以为「数还不对」而再猜一个。

已收成单一 `EXPECTED_MODEL_COUNT`。**任何「两处必须永远相等」的常量都应如此处理**，让半改在结构上不可能发生。
