# 机构账号删除、换绑与管理员手机号安全转移 UX 完善设计

> 日期：2026-07-26  
> 状态：已获用户口头批准，待书面复核  
> 范围：Admin 既有机构账号管理与账号设置，不新增页面、菜单、接口或数据模型

## 1. 背景与根因

当前后台存在三条安全语义不同的路径：

1. **删除机构账号**：验证目标账号旧因子后，移除登录身份并释放手机号；不会把号码绑定给管理员；机构必须至少保留一个启用账号。
2. **普通换绑机构账号手机号**：验证目标账号旧因子，再验证一个未被任何账号占用的新手机号；手机号仍属于该机构账号。
3. **从机构账号安全转移手机号**：验证管理员当前密码和原手机号 OTP，原子地从机构账号释放号码并绑定给当前管理员，同时保留机构账号的用户名密码登录能力。

后端规则本身不存在冲突，但前端没有在用户决策点解释三条路径的差异。单手机号用户容易进入删除或普通换绑流程；目标账号密码若属于管理员创建、管理员重置或历史未证明状态，密码入口又会因安全设计禁用，最终形成“验证过但仍不能换号、也不能删号”的死路感受。

## 2. 设计目标

- 在用户开始高风险操作前说明正确路径。
- 把确定可预判的限制提前展示，避免完成短信验证后才失败。
- 对禁用操作给出原因和下一步，不保留无解释的灰色按钮。
- 保留全部现有安全边界：目标持有人证明、手机号唯一性、最后启用账号不变量、一次性 ticket 和短信验证均不变。
- 复用现有 `/account-settings` 与安全转移组件，不新增重复入口或第二套状态机。

## 3. 方案选择

### 方案 A：仅修改文案

优点是改动最小；缺点是用户仍可能进入错误流程，最后一个启用账号仍会在完成验证后才暴露删除限制。不能完整解决问题。

### 方案 B：完整路径引导（采用）

在机构账号区域加入单手机号场景说明和现有安全转移入口；提前禁用不可删除的最后启用账号；为不可用密码方式、删除授权和普通换绑补充准确说明。改动集中在既有 Admin 组件和专项门禁，不改变后端契约。

### 方案 C：合并三条流程为统一向导

入口统一，但会把两个独立安全状态机耦合起来，增加 ticket 撤销、焦点管理、错误恢复和权限边界风险，不适合上线前收口阶段。

## 4. 页面与交互设计

### 4.1 机构账号列表顶部

账号管理区域展示常驻的轻量提示：

> 只有一个手机号，且希望绑定到管理员账号？请勿删除机构账号或使用普通换绑。前往“账号设置”使用“从机构账号安全转移手机号”，机构账号仍可使用用户名和密码登录。

提供指向既有 `/account-settings` 的“前往安全转移”操作。它只是当前能力的上下文导航，不新增业务入口或页面。

### 4.2 最后启用账号的删除预判

前端根据当前已加载的机构账号列表计算启用账号数量：

- 目标账号已启用且启用账号总数仅为 1：删除按钮禁用；
- 目标账号已停用：只要机构仍有另一个启用账号，允许进入删除流程；
- 其他情况继续由后端在提交事务中做权威校验。

禁用位置就地说明：“该账号是机构最后一个启用账号，不能删除。请先创建并启用接替账号。”前端预判只减少无效操作，不替代后端不变量。

### 4.3 验证方式选择

短信和密码按钮继续由 `availableActionVerificationMethods` 控制。密码方式不在可用列表时：

- 按钮保持禁用，避免制造可绕过路径；
- 紧邻按钮说明：“该密码由管理员创建/重置，或尚未完成持有人证明，不能用于本次高风险操作。”
- 提供替代路径：“使用账号已验证手机号；若无法接收，只能走线下核验恢复。”

不向前端暴露 `passwordProofState` 枚举或内部原因明细。

### 4.4 删除流程

在旧手机号验证码页面和最终确认页明确：

- 当前验证码只授权删除目标机构账号；
- 删除会释放手机号，但不会自动绑定到管理员账号；
- 单手机号转给管理员应退出当前流程并前往账号设置使用安全转移。

最终确认仍保留账号、机构、用户名和不可逆影响说明。

### 4.5 普通换绑流程

在新手机号输入页明确：

- 新手机号必须是另一个未被任何账号占用的号码；
- 该流程只改变机构账号绑定手机号；
- 若要把机构账号当前手机号转给管理员，应退出并使用安全转移。

`PHONE_TAKEN` 的展示文案同步给出安全转移路径，避免只要求用户“换一个号码”。

## 5. 数据流与安全边界

本任务不新增 API 调用。列表仍使用现有账号 DTO；验证、删除、普通换绑和安全转移仍调用各自既有接口。

前端只新增以下派生状态：

- `enabledAccountCount`：当前机构列表中 `enabled=true` 的账号数量；
- `isLastEnabledAccount`：当前账号已启用且 `enabledAccountCount <= 1`。

手机号、密码、验证码、challenge、action ticket 和 rebind ticket 的内存清理规则不变；新增导航不得把敏感数据写入 URL、storage、日志或审计。

## 6. 错误与边界场景

- 多管理员并发启停或删除时，前端预判可能过期；后端 `LAST_ACTIVE_PARTNER_ACCOUNT_REQUIRED` 仍为事实来源，现有刷新行为保留。
- 账号列表为空时不显示针对某个账号的操作说明，但账号区域的安全转移提示可以保留。
- 密码方式不可用但短信可用时默认聚焦短信方式。
- 两种方式均不可用时继续禁用删除/换绑，并保留既有线下核验说明。
- 当前管理员已经绑定手机号时，账号设置中的安全转移组件不会出现；机构账号页的提示使用条件式语气，不承诺任何管理员都能执行转移。

## 7. 测试策略

采用 RED→GREEN：

1. 先扩展 `verify-partner-account-action-ui.mjs`，要求存在安全转移入口、最后启用账号预判、密码禁用原因、删除不转移说明、普通换绑未占用号码说明和 `PHONE_TAKEN` 下一步。
2. 运行门禁确认新断言失败。
3. 最小修改既有组件使门禁通过。
4. 回归运行：
   - Partner account action UI verifier；
   - Admin phone transfer UI verifier；
   - 既有状态机单元测试；
   - Admin typecheck；
   - Admin lint；
   - Admin production build；
   - `git diff --check`。

本任务不改后端，API 专项测试作为必要时的相邻回归，不重复执行真实短信、数据库写入或生产账号操作。

## 8. 完成定义

- 单手机号用户在机构账号列表即可找到正确的安全转移路径。
- 最后一个启用机构账号不会再进入注定失败的删除长流程。
- 密码按钮禁用、手机验证成功、普通换绑和最终删除均有准确、可执行的解释。
- 没有修改或弱化任何后端安全与唯一性规则。
- 所列专项门禁、类型检查、lint、构建和 diff 检查全部通过。
