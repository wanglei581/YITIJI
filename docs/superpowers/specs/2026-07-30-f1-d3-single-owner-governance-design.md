# F1 D3 单一负责人与机构双模式治理设计

## 1. 背景与目标

公司当前只有一位负责人。现有 F1 D3 治理模板要求机构、运维、安全三方具名签批，不符合真实
组织规模，也可能诱导填写虚构角色。

本设计把治理改成两种模式：

- `single-owner`：当前一人公司使用，由真实业主负责人承担业务、运维和安全决策责任；
- `institutional`：未来学校、政府、合作机构或团队扩张后使用，继续执行职责分离。

两种模式只改变“谁承担治理责任”，不改变 B1–B9 技术门槛、证据标准、状态词法或分层授权。
[managed 输入清单](../../device/f1-d3-managed-topology-inputs.md) 继续作为唯一技术 SSOT。

## 2. 方案比较与选择

### 方案 A：只保留三方职责分离

安全形式完整，但与当前只有一名负责人的事实不符，容易制造假签批，不采用。

### 方案 B：单一负责人和机构职责分离双模式

当前使用真实的单一负责人记录；未来机构项目无需重写标准即可切换多人职责分离。角色可以合并，
授权闸门、技术门禁和操作留痕不合并。**采用此方案。**

### 方案 C：强制外部顾问共同签批

可增加独立复核，但会给一人公司的每次只读核验增加不必要成本。仅在客户合同、法规或高风险现场
明确要求时使用，不作为当前默认条件。

## 3. 治理模式

每一条生产变更记录必须显式选择且只能选择一种治理模式。

### 3.1 `single-owner`

- 申请人、业务负责人、运维负责人和安全负责人可以是同一名真实自然人，统一称“业主负责人”。
- 禁止为了满足表格而虚构姓名、工号、部门或独立复核人。
- 业主负责人承担最终 GO / NO-GO 决策和生产后果；AI、自动化测试或 Git 提交都不是责任主体。
- 一个人仍必须使用不同的部署账户与 API 运行账户，B9 权限分离不因人员数量减少而取消。

### 3.2 `institutional`

- 沿用机构负责人、运维负责人、安全负责人和 D3 核验人的职责分离。
- 从 `single-owner` 切换为 `institutional` 时，新的机构记录必须重新签批；历史单人记录不能追溯
  认定为机构三方审批。
- 两种模式都只引用 B1–B9 字段 ID，不在治理包复制技术值或状态表。

## 4. 授权必须按动作分离

“同一人承担多个角色”不等于“一次授权所有操作”。以下动作必须分别建立单一用途、限时、具名的
变更记录：

1. `D3_READONLY_PRECHECK`：只读核验；允许的生产连接方式和只读命令白名单必须写入记录。
2. `RESIDUAL_LOCK_DISPOSITION`：发现 Genesis lock 或 activation lock 后单独处理；默认不得删除。
3. `D4_GENESIS`：仅在 D3 通过后另行授权平行 Genesis。
4. `D5_CUTOVER`：仅在独立切流前置证据齐全后另行授权负载层变更。
5. `D6_ACTIVATION`：仅在前序门槛关闭后另行授权稳态 activation。

上一动作通过不会自动授权下一动作。普通聊天中的“可以”“继续”“按推荐”等回复只能批准当前文档或
开发任务，不能自动解释为 SSH、生产 D3、删锁、Genesis、切流或 activation 授权。

## 5. 单一负责人模式的补偿控制

没有第二名人类复核人时，以下控制缺一即保持 NO-GO：

1. **先记录后执行**：变更记录必须在操作开始前生成，包含 RFC3339 起止窗口和单一动作类型；过期后
   重新记录，禁止扩展原授权。
2. **确定性门禁**：继续使用 release provenance、Genesis/activation fail-closed、路径类型、摘要和
   参数契约校验；聊天不能覆盖失败结果。
3. **带外原件与仓库摘要**：完整记录保存在仓库外受保护位置并备份，仓库只记录非秘密索引和
   SHA-256；执行账户不能删除唯一原件和全部备份。
4. **技术账户分离**：部署账户与 API 运行账户继续按 B9 分离，即使两个账户最终由同一自然人管理。
5. **分阶段证据**：每个动作结束后先形成脱敏结果和 NO-GO / PASS 结论，再申请下一动作。
6. **技术复核**：自动测试和 AI 可识别风险并触发 NO-GO；所有 Critical/High 或未解释的 Warning 必须
   在执行前解决或由业主负责人明确记为 NO-GO。

## 6. AI 技术复核的边界

AI 只能形成“只读技术核对意见”，用途等同于静态分析、测试和规则比对：

- AI 不进入任何签批人、批准人、负责人或执行人字段；
- AI 的 APPROVE 不会自动产生 GO，也不能替代业主负责人的具名决定；
- AI 发现不一致、秘密泄露、状态缺口或越权风险时，可以触发 NO-GO；
- 仓库只保存必要的技术复核引用和结论摘要，不保存包含秘密的完整对话。

固定声明：**AI 技术复核不构成生产审批，不是组织或法律责任主体。**

## 7. 最小生产变更记录

仓库外原件至少包含以下非秘密字段：

| 字段 | 规则 |
| --- | --- |
| 变更记录编号 | 唯一、可追溯 |
| 治理模式 | `single-owner` 或 `institutional`，二选一 |
| 动作类型 | 仅允许第 4 节五种动作之一 |
| 负责人 | 真实自然人身份；禁止使用 AI 或虚构角色 |
| 授权窗口 | RFC3339 开始和结束时间；过期失效 |
| 目标候选 | 完整 Git commit 与候选 CI / provenance 引用 |
| B1–B9 记录引用 | 指向唯一技术 SSOT 或仓库外受限记录，不复制秘密 |
| 技术复核引用 | 自动门禁与 AI 技术意见的非秘密引用；明确“非审批” |
| 操作前/后证据引用 | 只保存脱敏引用与结论，不保存日志正文 |
| 负责人结论 | GO / NO-GO、具名时间；只对该动作有效 |
| 原件 SHA-256 | 仓库外完整记录的 64 位小写摘要 |

完整原件保存在负责人控制的受保护本地目录或私有云盘，并至少有一份独立备份。Git 仓库只允许记录
变更编号、模式、动作、负责人非秘密身份引用、窗口、候选引用、证据引用、结论和原件 SHA-256。

禁止进入 Git：密码、token、私钥、OTP、环境变量值、连接串、Cookie、完整 PM2 dump、日志正文、
业务数据或个人隐私数据。

## 8. 硬停止条件

出现任一情况必须停止并保持 NO-GO：

- 使用普通聊天回复代替结构化生产授权；
- 虚构机构、运维、安全负责人，或把 AI 填入签批栏；
- 任一 B1–B9 门槛未关闭，或试图降低 managed / legacy 隔离要求；
- 生产变更记录缺失、过期、动作范围不明确或摘要无法比对；
- 试图用本地 CI、D2 fixture、旧 PM2 `online` 或 HTTP 200 冒充生产证据；
- 记录或证据包含秘密、日志正文或业务数据；
- 发现残留锁却没有独立处置记录；
- 用 D3 PASS 直接执行 D4、D5 或 D6。

## 9. 实施范围与验证

实施阶段只修改：

1. `docs/device/f1-d3-managed-topology-approval-package.md`：增加双模式、单人记录和补偿控制；
2. `docs/progress/current-progress.md`：记录治理模式真实化；
3. `docs/progress/next-tasks.md`：把下一步改为单一负责人生产记录与 D3 独立授权。

不修改 `docs/device/f1-d3-managed-topology-inputs.md`、生产代码、生产配置、部署脚本或真实生产值。

验证要求：

- `git diff --check`；
- 确认 managed 输入 SSOT 与所有代码文件零 diff；
- 扫描新增内容不存在秘密特征和虚构签批；
- 运行 release provenance 与 Genesis 离线门禁，证明文档变更未伴随代码回退；
- Claude 与 Antigravity 分别终审，Critical / High 必须为 0。

## 10. 当前状态

本设计只确定治理方式，不授权连接生产或执行任何 D3–D6 动作。正式实施完成后，production F1 仍为
NO-GO，直到单一负责人真实填写对应记录、B1–B9 全部满足，并对具体 D3 只读窗口作出独立明确授权。
