# 内容上线执行手册 —— 让三个信息库真的有东西（2026-08-17）

> **这不是工程任务,是运营任务。** 工程侧的管道已经端到端验通(27 PASS / 0 FAIL),
> 批量发布工具也做好了。**卡住的是没有人往里放内容。**
>
> 写给运营执行者,不需要懂代码。每步写明「做什么 / 怎么确认做对了 / 什么情况下停下来问」。

---

## 0. 现状(2026-08-17 线上实测,不是推断)

```
GET https://zyidai.cn/api/v1/jobs        → total: 0
GET https://zyidai.cn/api/v1/job-fairs   → total: 0
GET https://zyidai.cn/api/v1/policies    → total: 0
```

**一台「岗位信息 + 招聘会信息 + 政策服务」终端,三个核心库全空。**

用户走过来点开「岗位信息」,看到的是空的。页面做得再好,这一刻的产品价值是零。

### 但「空」不等于「没录过」

`total: 0` 是**前台可见数**,不是库里的行数。前台的过滤条件是:

```
reviewStatus = 'approved'  且  publishStatus = 'published'
```

有证据表明库里存着一批**已审核但未发布**的岗位:PR #611 的提交说明自述生产上有 **约 217 条** `approved` + `unpublished` 的岗位和 3 场招聘会。

> ⚠️ **这个数字没有被独立核实过。** 它来自一条提交说明,不是从生产库查出来的。
> 第一步就是把它查清楚 —— **不要拿它当既成事实去做决策。**

---

## 1. 第一步:先查清库里到底有什么(不许盲发)

**做**:在 Admin 后台,把岗位/招聘会/政策三类的审核队列各筛一遍,按 `reviewStatus` 分桶数一下。

**要得到的数字**:

| 类别 | pending | reviewing | approved+未发布 | 已发布 | rejected |
|---|---|---|---|---|---|
| 岗位 | | | | | |
| 招聘会 | | | | | |
| 政策 | | | | | |

**为什么必须先数**:后面每一步的决策都依赖这张表。而且工程侧发现过一个相关问题 ——
后台列表**只按 `reviewStatus` 分五桶**,`approved` 但未发布的会混在「已通过」里、没有任何聚合提示。
**这正是那批数据卡了很久没人发现的原因。**(接口层面区分得开,是列表页没展示这个维度。)

**停下来问的情况**:如果数出来的「approved+未发布」远小于 217,说明那个数字过时或有误 —— 先把差异搞清楚再往下走。

---

## 2. 第二步:审阅积压,不要整批直接发

**岗位会过期。** 那批数据在库里躺了一段时间,里面很可能有:

- 已经招满、已经下线的岗位
- 招聘会**日期已过**
- 政策**已失效或已被新政策替代**

**做**:逐条(或按来源机构成批)看一遍,至少确认三件事:

1. **时效** —— 招聘会开始时间是否已过?岗位发布时间是否太久远?
2. **来源仍然有效** —— `sourceUrl` 打开还在不在?来源平台是不是已经撤下?
3. **信息完整** —— 来源机构、外部ID、同步时间、外部链接是否齐全(这四项是合规要求,见 `CLAUDE.md` §10)

**判断口径**:

```
时效过期 / 来源已撤下  →  不发布(或直接 rejected)
信息不全              →  补齐再发,不要带着空字段上线
其余                  →  可发布
```

**为什么不能整批直接发**:一台终端上挂着一批过期岗位,比空着更糟 —— 空着是「还没有内容」,过期岗位是「给了用户错误信息」。

## 3. 第三步:发布

### 工具

PR **#637**(信息源批量发布)提供:**先预览 → 可筛选 → 逐条审计 → 部分失败逐条可见**。
一次上限 100 条,不包事务(全有或全无会让「部分成功」不可见)。

> 该 PR 截至本文成稿**尚未合入**。合入前只能在 Admin 里逐条点发布。

### 无论用哪种方式,必须确认

- [ ] **只发 `approved` 的**。`pending` / `rejected` 绝不能上线 —— 外部数据必须审核后才展示,这是合规红线(`CLAUDE.md` §18)
- [ ] 发布后**去前台看一眼**。`https://zyidai.cn/api/v1/jobs` 的 `total` 应该等于你发布的条数
- [ ] 前台随机点开 3 条,确认**来源机构 / 同步时间 / 外部ID / 外部链接**都显示得出来

### 已知的工程侧保障(已验证,可以放心)

工程侧独立验证过:造了 28 条 `approved` 未 `published` 的数据,**通过详情端点和全量列表遍历双向探测,0 泄漏**,并做了阳性对照确认探测方法真的能发现内容。

**所以「未发布的会不会漏出去」这件事不用担心,发布闸门是干净的。**

## 4. 第四步:持续供给(一次性推完不解决问题)

发完这批积压,库里的内容会随时间再次过期。**需要一个持续的入口。**

现有三条接入方式(合作机构后台,`apps/partner`):

| 方式 | 适合 | 现状 |
|---|---|---|
| **Excel 导入** | 人工整理好的批量数据 | 上传 → 字段映射 → 预览 → 确认,四步;上次映射规则会自动回填 |
| **Webhook** | 来源平台能主动推送 | HMAC 验签 + 5 分钟时间窗 + nonce 防重放 |
| **API 拉取** | 来源平台有开放接口 | BullMQ worker 定时拉 |

**建议**:先给 1–2 家真实合作机构开通 Excel 导入,跑通一轮完整的「机构自己录 → 平台审核 → 上线」,再考虑接 Webhook / API。

**不要一上来就接自动同步** —— 自动同步会把上游的脏数据也同步进来,而审核队列还没有人在看。

---

## 5. 政策申领条件:这一项是从零开始

**现状**:政策库里**一条真实申领条件都没有**。

后端已建(PR #631,已合入),Partner 录入界面已建(PR #645,待合)。但在有人录入之前:

- 用户点「政策条件核对」,系统一律返回 `no_recorded_conditions`(诚实空态,不是 bug)
- 而前台目前展示的「申领条件」是**硬编码模板**,内容是「符合当地政策」这类占位话术,**与那条政策毫无关系**

> ⚠️ **最后这一条是一处正在对用户展示的假内容。** 录入真实条件之前,它一直在那儿。

### 录入时的硬约束

- **条件必须逐条对应政策原文**,不要意译、不要归纳。系统会把原文摘录原样回传给用户
- **无法机器判定的条件**(比如「经街道办核实的困难家庭」)要标成**「需人工核对」**,
  **不要为了让系统能跑而硬塞一条可比对的规则** —— 那是在制造错误判定
- 判定结果只有三种:`符合` / `不符合` / **`无法判定`**。填不全就是「无法判定」,不是「不符合」

## 5A. 内容从哪来:按机构类型组织的接入候选清单(2026-09-08 补)

> 上面第 4 节讲的是「怎么接」(Excel / Webhook / API 三条通道),这一节讲的是
> **「能接谁」**。两者缺一不可:通道再顺,没有合法来源也发不出一条内容。

### 先记住一个约束:接入资格由机构类型决定,不是由我们想接谁决定

`services/api/src/jobs/partner-capabilities.ts` 的能力矩阵已经把这件事钉死了。
谈合作之前先对表,免得谈成了系统不让配:

| 机构类型 | 可声明的来源种类 | 能发岗位 | 能发招聘会 | **能发政策** | 企业资料范围 |
|---|---|---|---|---|---|
| `school_employment_center` 高校就业中心 | `school` / `manual` | ✅ | ✅ | ✅ | 不限 |
| `public_employment_service` 公共就业服务机构 | `aggregator` / `manual` | ✅ | ✅ | ✅ | 不限 |
| `licensed_hr_agency` 持证人力资源服务机构 | `hr_company` / `job_platform` / `aggregator` / `manual` | ✅ | ✅ | ❌ | 受限 |
| `fair_organizer` 招聘会主办方 | 见矩阵 | 视配置 | ✅ | ❌ | 仅本场关联 |
| `enterprise_source` 用人单位 | 见矩阵 | 视配置 | — | ❌ | 仅本企业 |

**政策只有前两类能发**(`assertPolicyCapableOrgType`)。理由写在代码注释里:
政策属官方性质,商业机构不得冒名发布。所以「找个 HR 公司帮我们录点政策」这条路
从工程上就是堵死的,不要浪费时间去谈。

另外两道闸门,谈合作时要一起讲清楚,否则对方录完发不出去会以为是系统坏了:

1. **机构必须先被标为「内容可信」** —— Admin 在后台执行,且**必须填核验依据**
   (授权书 / 合同 / 公开声明编号),这条依据会进审计日志。未标记时任何发布动作
   一律 `ORG_CONTENT_TRUST_REQUIRED` 拒绝。
2. **数据源 endpoint 不能带凭证** —— `?token=` `?apikey=` `?appsecret=`
   以及 `https://user:pass@host/` 全部拒收,凭证走独立的鉴权配置字段。

### 候选来源:按「拿到什么授权就能接什么」排

下面按**落地难度**排序,不按数据量排。**第一列的授权文件是准入条件,不是可选项** ——
没有它,这条来源就不该进审核队列。

| 优先级 | 来源类型 | 对应机构类型 | 需要的授权 | 走哪条通道 | 为什么排这个位置 |
|---|---|---|---|---|---|
| **P0** | 本地高校就业指导中心 | `school_employment_center` | 校方书面合作函 / 共建协议 | Excel 起步 | 唯一能同时供岗位+招聘会+政策的类型;校招季内容天然充足;一体机若落在校园,内容与场景天然对齐 |
| **P0** | 市/区级公共就业服务机构(人才交流中心、就业促进中心) | `public_employment_service` | 官方合作文件或数据使用授权 | Excel 起步,稳定后 API | **政策的唯一权威来源**;招聘会主办方通常也是它;其内容自带公信力 |
| **P1** | 本地招聘会主办方 | `fair_organizer` | 单场次授权即可,门槛最低 | Excel / 手工 | 一场招聘会能一次带来几十家参展企业与展位信息,是**冷启动性价比最高的一次性投入** |
| **P1** | 持证人力资源服务机构 | `licensed_hr_agency` | 对方的人力资源服务许可证复印件 + 数据授权 | Excel / Webhook | 岗位量大;**但发不了政策**;必须查验对方许可证,否则等于借道无证经营 |
| **P2** | 用人单位直供 | `enterprise_source` | 企业营业执照 + 岗位真实性承诺 | 手工 / Excel | 单家产出低、维护成本高;适合本地重点企业专区,不适合铺量 |

### 明确不能做的取数方式

- **不抓取第三方招聘平台**。`compliance-boundary.md` §383 已写死:不得把用户粘贴的
  外部 URL 自动抓取后当已审核岗位入库。同理不得爬取平台列表页。
  即便技术上可行,没有授权的抓取在岗位数据上同时踩数据权益与不正当竞争两条线。
- **不做「聚合再分发」的二次搬运**。`aggregator` 这个 sourceKind 指的是
  「对方本身就是聚合型官方机构」,不是「我们去聚合别人」。
- **不接受只给数据不给授权的合作**。来源四要素里 `sourceName` / `sourceUrl` 要对外展示,
  展示一个没授权的来源,风险比空着大。

## 5B. 冷启动最低门槛:给数字,不给形容词(2026-09-08 补)

第 7 节的验收条件写的是「total 都不为 0」。**那是下限不是门槛** —— 1 条也满足,
但小程序过审和一体机现场都撑不住。下面这组数字的依据写在每一行里。

### 微信小程序提交审核的门槛

审核员会逐个点开 Tab,「功能不完整 / 空白页面」是明确驳回项。

| 内容 | 最低条数 | 依据 |
|---|---|---|
| 岗位 | **≥ 30 条** | 列表 `PAGE_SIZE = 20`(`pages/jobs/jobs.js:5`)。低于 20 条翻不出第二页,审核员看到的是一个不能翻页的短列表;30 条能翻到第二页并证明分页真的能用 |
| 岗位的行业/区域分布 | **≥ 3 个区域 × ≥ 3 个行业** | 关键词检索一搜就空,比列表短更像坏功能 |
| 招聘会 | **≥ 3 场,其中 ≥ 1 场是未来 14 天内** | 首页那张卡片只显示「进行中 / 即将开始」。一场未来场次都没有,首页卡片就是空的 —— 那是**首屏**,审核员第一眼就看到 |
| 政策 | **≥ 8 条,4 个人群分类每类 ≥ 1 条** | 分类是 `all / graduate / flexible / startup / hardship`(`pages/policies/policies.js`)。任一分类点进去是空的,就是「功能不完整」 |
| 政策申领条件 | **≥ 1 条政策录入真实条件** | 否则「政策条件核对」永远返回 `no_recorded_conditions`,那个功能等于不存在 |

> 合计:**30 岗位 + 3 招聘会 + 8 政策**。这是**提交审核**的门槛,不是运营目标。

### 一体机现场不空的门槛(比过审高)

一体机是 27 寸竖屏,一屏能显示的条目更多,且现场用户是带着具体目的来的
(「我要找本区的仓储岗」),一筛就空的体验比小程序更刺眼。

| 内容 | 最低条数 | 依据 |
|---|---|---|
| 岗位 | **≥ 50 条** | 现场按「区域 + 行业」两级筛完仍要有结果;50 条是两级筛后每格仍有 1–2 条的下限 |
| 招聘会 | **常年保持 ≥ 1 场未来场次** | 现场「招聘会」入口空着,等于这台机器少了一个业务域 |
| 政策 | **≥ 8 条** | 与小程序同 |

### 持续供给的下限

一次性推完会再次过期(第 4 节已说明)。补一条数字口径:

- **岗位过期率 > 30% 时必须补充**。过期岗位比没有岗位更糟(红线第 2 条)。
- **招聘会「未来场次」归零前必须补进下一场**,否则首页卡片空窗。

## 5C. 内容到位之前,空态本身就是交付物(2026-09-08 补)

在拿到第一批授权内容之前,三个 Tab **一定会是空的**。空态不是「等内容来了再说」的
临时状态,**它就是那段时间用户唯一看得到的东西**,必须能交付。

判据只有一条:**用户看完能知道「为什么空」和「接下来能做什么」。**

| Tab | 不合格的空态 | 合格的空态 |
|---|---|---|
| 岗位 | 纯白页 / 只有一个灰色图标 / 「暂无数据」 | 说清是**本机尚未上架来源**还是**筛选条件太窄**,后者给「清除筛选」 |
| 招聘会 | 「暂无招聘会」 | 「本机尚未接入招聘会来源」+ 说明招聘会信息来自第三方或官方主办方 |
| 政策 | 「暂无政策」 | 「政策信息来自官方来源,本机尚未接入」+ 指向线下经办窗口 |

三条硬约束:

1. **不许伪造条目占位**。哪怕标了「示例」也不行 —— 用户不会读那个标。
2. **不许把「来源尚未授权」写成「系统错误」**。前者是诚实状态,后者会让用户以为
   刷新一下就好,反复重试。
3. **区分「本机没上架」与「筛选筛空」**。这两种空态的补救动作完全不同,
   合成一句话等于两种都没说清。

> ⚠️ **岗位那一格已有人在做**(#976「岗位空态分清本机没上架和筛选筛空」),
> 招聘会与政策两格尚未认领,不要与 #976 重复。

## 6. 红线(违反了比空着更糟)

1. **不发未审核的数据。** `pending` / `rejected` 上线是合规事故。
2. **不发过期数据。** 给错信息比不给信息糟。
3. **不补空字段。** 来源机构 / 外部ID / 同步时间 / 外部链接缺一项就不发,不要随手填一个。
4. **政策条件不许意译。** 判定依据必须能追回入库原文。
5. **不做投递闭环。** 岗位和招聘会只能是第三方来源信息入口;按钮文案走白名单(「查看岗位」「去来源平台投递」「扫码投递」),
   **禁止「一键投递 / 立即投递 / 平台投递」**(`CLAUDE.md` §2)。

## 7. 做完之后怎么算数

```
[ ] 三个库在 https://zyidai.cn 上 total 都不为 0
[ ] 前台随机抽 5 条,来源四要素齐全、外部链接能打开
[ ] 至少一家合作机构走通了一轮「自己录 → 审核 → 上线」
[ ] 至少一条政策有真实录入的申领条件,且核对页不再返回 no_recorded_conditions
[ ] 审核队列里没有积压超过一周没人看的 pending
```

**前两条不满足,产品就不具备对外服务条件** —— 这不是文档口径,是交付章程门槛②「有内容」。
