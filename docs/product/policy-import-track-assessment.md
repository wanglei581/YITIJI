# 政策导入轨：建不建？成本评估（2026-09-09）

> **这份文档只给判断依据，不做决定。** 一期要不要保留内容板块尚未拍板，
> 现在建管道可能白建 —— 所以先把「建它要多少钱」量出来，让决策有数字可依。

## 结论先说

| 问题 | 回答 |
|---|---|
| 要多少工作量 | **约 1 个工作日**（含门禁与实测），不是从零造轮子 |
| 走哪一轨 | **Excel**。API/Webhook 至少贵 3 倍，且政策来源不具备推送能力 |
| 一期砍掉内容板块的话，这份评估作废吗 | **不作废，但会降级** —— 见末节 |

## 为什么便宜：这条轨已经是参数化的，不是岗位专用

`dataType` 从一开始就是个参数，不是硬编码在岗位里：

```
FieldMappingRule  唯一键是 sourceId_dataType         ← 天然支持第三种
ImportBatch       带 dataType 列
BulkPublishKind   已经是 'job' | 'fair' | 'policy'   ← 发布侧已经认政策
```

**发布侧已经支持政策**（`BulkPublishKind` 里就有），缺的只有「把 Excel 解析成政策行」
这一段。所以不是新建一条轨，是给已有的轨加第三个分支。

## 具体要改哪些地方（实数，不是估算）

按 `grep 'dataType === ...'` 数出来的分支点：

| 文件 | 现有分支点 | 要做的事 |
|---|---|---|
| `services/api/src/jobs/excel-template.ts`（168 行） | 6 处二元三目 | 新增 `POLICY_TEMPLATE_FIELDS`，6 处三目改三分支 |
| `services/api/src/jobs/jobs-excel.service.ts`（597 行） | 7 处 | 落库分支加 `policyPost` 一支；校验/去重/预览各加一支 |
| `apps/partner/src/routes/sources/ExcelImportModal.tsx`（537 行） | 2 处 | 数据类型选择项加「政策」 |
| `partner-capabilities.ts` | 1 处 | `assertPartnerDataTypeCapability` 的签名放开到三值 |
| 类型声明 `'job' \| 'fair'` | **全仓 40 处**（已排除生成产物） | 收敛成一个具名类型再加 `'policy'`，否则漏一处就是运行时炸 |

**那 40 处是主要成本，也是主要风险。** 它们分散在 api / shared / partner 三处，
现在靠字面量重复。加第三个值之前应该先把它收敛成 `PartnerImportDataType`，
否则改漏一处不会有编译错误（字面量联合各写各的），只会在运行时按 `else` 分支
把政策当招聘会处理。

## 字段映射：政策比岗位复杂，这是唯一的实质新工作

| 数据类型 | 可映射字段数 |
|---|---|
| 岗位 | 19 |
| 招聘会 | 13 |
| **政策（PolicyPost 模型）** | **31 个字段** |

但 31 个里不是都要开放给 Excel。真正需要人工录的核心字段大约 10 个
（title / summary / content / audience / category / externalUrl / publishedAt /
sourceName / externalId / kind），其余是系统派生或审核流字段。

**一个必须提前决定的事**：政策的「申领条件」是结构化数据（见
`content-onboarding-runbook.md` §5 「条件必须逐条对应政策原文，不要意译」），
Excel 的一行一格装不下多条带原文摘录的条件。所以：

- **本轨只导政策正文与元数据**，申领条件仍走 Partner 后台逐条录入
- 不要为了「一次导完」把条件塞进一个单元格再切分 —— 那等于把「不许意译」这条
  红线交给一个分隔符去保证

## 为什么选 Excel 而不是 API / Webhook

| 轨 | 成本 | 适配性 |
|---|---|---|
| **Excel** | 约 1 天 | ✅ 政府公开政策通常是网页或 PDF，人工整理成表是现实路径 |
| API 拉取 | 3 天+ | ❌ 需要对方有开放接口。人社局/就业中心一般没有 |
| Webhook | 3 天+ | ❌ 需要对方**主动推**。公共机构不会为我们建推送 |

API/Webhook 贵的不是接入本身，是**没有对端**。政策来源方是政府机构，
不会为一个第三方终端开接口。Excel 是唯一与来源方能力匹配的轨。

## 如果一期砍掉内容板块，这份评估作废吗

**不作废，但价值降级。** 分三种情况：

1. **一期保留内容板块** → 这条轨是必需项。没有它，政策只能在 Partner 后台一条条手建，
   而 §5B 定的过审门槛是 **8 条政策、4 个人群分类每类 ≥1** —— 手建 8 条可以硬扛，
   但持续供给扛不住（政策会过期，`content-onboarding-runbook.md` §4 已说明）。
2. **一期砍掉内容板块，二期再做** → 这份评估**继续有效**，因为成本结构不会变：
   参数化基础已经在，40 处字面量收敛这件事早做晚做工作量一样。
3. **永久不做内容板块** → 作废。但那时要一并砍掉的不止这条轨 ——
   岗位/招聘会的 Excel 轨、审核流、内容信任闸门都会变成无主代码，
   那是一次单独的清理决策，不是本文范围。

**给决策者的一句话**：这条轨的成本（1 天）远低于「内容板块要不要保留」这个决策的分量。
不要因为管道便宜就顺手建，也不要因为决策未定就把它当阻塞 —— 它随时可以建，
一天就够，**不构成排期风险**。

## 建议的执行顺序（如果决定要建）

1. 先把 40 处 `'job' | 'fair'` 收敛成具名类型（**独立一个 PR**，零行为变更，可单独回滚）
2. 再加 `POLICY_TEMPLATE_FIELDS` 与落库分支
3. Partner 侧数据类型选项加「政策」
4. 门禁：现有 `verify:partner-source-capabilities` 加政策用例；
   **必须包含一条反向断言** —— 非 `school_employment_center` /
   `public_employment_service` 的机构导入政策要被拒
   （`assertPolicyCapableOrgType`，政策属官方性质，商业机构不得冒名发布）

第 1 步单独成 PR 是有意的：那 40 处改动面最大、行为变更为零，
和有行为变更的第 2–3 步混在一个 PR 里，review 时分不清哪些是重构哪些是新逻辑。
