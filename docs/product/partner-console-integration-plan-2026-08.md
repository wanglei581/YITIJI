## 第一部分 · 诊断：Partner「功能少」的真正原因

**不是页面少。** Partner 有 13 个页面，覆盖了 CLAUDE.md §9A 声明的大部分模块。
真正的问题是——**机构做的事，有一大半产生不了价值**，因为数据关联断在 8 个地方。

### 1.1D 前端新增的两类内容，后台没跟上（2026-08-11 追加）

> 产品所有者补充：前端岗位信息页里已经加了**线上招聘平台**与**线下招聘公司**。
> 核查结果：**这两类内容前端在展示，后台的管理能力却是缺的。**

#### 事实

两类内容**都挂在 `Organization` 上**（`schema.prisma:437-438`）——
即它们本来就是「某个合作机构自己的档案」：

```prisma
model Organization {
  offlineAgencyProfile      OfflineAgencyProfile?                              // 1:1
  onlinePlatformDirectories OnlinePlatformDirectory[] @relation("PlatformDirectoryOrg")  // 1:N
}
```

| 内容 | 数据归属 | Admin | **Partner** | Kiosk |
| --- | --- | :---: | :---: | :---: |
| **线下招聘机构** `OfflineAgencyProfile` + `OfflineAgencyBranch` | `Organization` 1:1 | ✅ 完整管理页（`AgencyForm` / `JobsDrawer` / `ReviewDialog`） | ❌ **无入口** | ✅ `OfflineAgenciesPage` |
| **线上招聘平台** `OnlinePlatformDirectory` | `Organization` 1:N | ❌ **无管理页** | ❌ **无入口** | ✅ `OnlinePlatformsPage` |

**线上平台目录全局只有 2 处引用**：`prisma.service.ts`（client）与
`recruitment-content-read.service.ts`（**只读**）——
**两个后台都没有写入口，数据只能靠 seed 或直接改库**。
这与 `console-plan §6` 登记的「G1A 线上招聘平台目录——Admin 治理待建」一致。

#### D9 · 线下招聘机构：机构自己管不了自己的门店

**这是 D3（招聘会子实体）的同一类问题——权责错配。**
一家人力资源公司在终端上被展示为「线下招聘机构」，
它的**地址、营业时间、服务项目、门店分支**却只能由平台管理员维护。
改个营业时间要打电话找平台。

**修法**：给拥有 `OfflineAgencyProfile` 的机构（主要是 `licensed_hr_agency`）
开放本机构档案与门店的自助维护，仍走 pending 审核。

#### D10 · 线上招聘平台：两个后台都管不了

**但这条的修法与 D9 不同——不能简单给 Partner 开放。**

线上平台目录的性质是**平台向求职者推荐哪些第三方招聘平台**，
这个推荐权属于平台的编辑责任，**不能让机构自己往目录里加**
（否则任何机构都能把自己的平台塞进推荐位）。

而且这张表的字段本身就带治理意图：
`operatorLegalName`（运营方法定名称）· `officialDomainsJson`（官方域名白名单）·
`evidenceFileId`（资质证据文件）· `neutralDescription`（**中立描述**）——
`neutralDescription` 这个命名说明设计上就要求平台保持中立，不做倾向性推荐。

**修法（分两层）**：

| 层 | 谁 | 能做什么 |
| --- | --- | --- |
| **Admin 治理页**（新增，必需） | 平台 | 收录 / 审核 / 排序 / 上下架 / 维护官方域名白名单 / 存证据文件 |
| **Partner 侧**（可选，受限） | 该平台的运营方机构 | **只能申请收录与提交更新**，不能自行发布；不能改 `displayOrder` |

**⚠️ 合规提示**：官方域名白名单（`officialDomainsJson`）与政策的「官方入口」（PL2）
是同一类问题——**都关系到用户从终端跳到哪里去**。
建议统一用一套域名校验机制（可复用百宝箱已有的域名白名单）。

### 1.2 一句话总结

> 机构在后台做的动作，**有 8 条路径最后没有走到求职者面前，或者走到了但和机构以为的不一样**。
> 这才是「功能少」的体感来源——**不是没得做，是做了没用**。
>
> **所以顺序必须是：先打通数据关联 → 再补功能 → 最后加 AI。**
> 在断裂的链路上加 AI，只是让错误的数据更快地产生更多错误的建议。

## 第二部分 · 三端数据关联总图

### 2.1 四条链的关联现状

```text
                 Partner 提交        Admin 审核/运营        Kiosk 展示
岗位 Job          9~17 字段  ──→   审核发布(看11项)  ──→   列表+详情(缺5字段) ⚠️
招聘会 JobFair    主表10字段  ──→   主表+5个子Tab    ──→   详情+企业+导览+资料 🔴
  └ 10个子实体    ❌ 管不了    ──→   ✅ 全归Admin      ──→   ✅ 全展示
政策 PolicyPost   8 字段     ──→   审核发布          ──→   四Tab展示  ✅
企业 CompanyProfile 20字段   ──→   审核发布+关联岗位  ──→   找企业列表+详情 ⚠️
  └ FairCompany   ❌ 管不了    ──→   ✅ Admin管        ──→   参会企业页（另一份数据）🔴
  └ FairCompanyBooth ❌       ──→   ✅ Admin管        ──→   展位/签到（企业名是字符串）🔴
```

**✅ 政策链是四条里最干净的**：模型 20 字段，业务字段 8 个 Partner 全能填，三端一致。
**🔴 招聘会与企业链最乱**：子实体机构管不了 + 同一份数据存多份且不同步。

### 2.2 企业数据的三份拷贝（最严重的一处）

| 表 | 字段数 | 谁能管 | 谁在读 | 关联 |
| --- | --- | --- | --- | --- |
| `CompanyProfile` | 35 | Partner 20 项 + Admin | Kiosk **「找企业」页** | — |
| `FairCompany` | 14 | **仅 Admin** | Kiosk **「招聘会参会企业」页** | **无 `companyProfileId`** |
| `FairCompanyBooth` | 9 | 仅 Admin | 展位图 / 签到 | **`companyName` 是字符串，不是外键** |

**三处冲突**：

| 概念 | 存了几份 | 格式 |
| --- | --- | --- |
| 展位号 | `CompanyProfile.boothNo` + `FairCompanyBooth.boothNumber` | 两个字段，无同步 |
| 企业荣誉 | `CompanyProfile.honorTags` + `FairCompany.honorTags` + `FairCompanyBooth.honors` | 前两个逗号分隔，第三个 JSON 数组 |
| 企业名 | 三处各存一份 | `FairCompanyBooth.companyName` 改不了源头 |

**后果**：同一家企业，求职者在「找企业」页和「招聘会参会企业」页看到的是**两份独立数据**。
机构改一处，另一处不变，而且**机构不会知道**。

### P1 · 打通回路（让机构做的事产生价值）

| # | 修什么 | 做法 | 前置 |

3. **AI 建议必须人工采纳才生效**——不自动改内容、不自动提审。

## 第八部分 · C10 机构 AI 助手（新增能力）

> 产品所有者提议：「机构端要不要增加一个 AI 助手，就像腾讯云那样，做问题解答和查找反馈？」
> **结论：要做，而且这是机构端性价比最高的 AI 功能。**

### 8.1 为什么机构端的 AI 助手比 C 端更容易做好

| 条件 | 机构端 | 求职者端 |
| --- | --- | --- |
| 领域范围 | **封闭**：就这 13 个页面的操作 | 开放：简历、面试、政策、职业规划… |
| 用户画像 | **非技术人员**（高校就业老师、人才市场工作人员、HR），怕操作错 | 差异极大 |
| 问题类型 | **大部分是「查我的数据 + 引导操作」**，不是生成 | 大量需要生成 |
| 数据敏感度 | **只碰机构自有内容**，不碰求职者隐私 | 涉及简历等敏感数据 |
| 正确性可验证 | ✅ 答案来自数据库，可复现 | 多为主观建议 |

**结论**：这个助手**主体是 L1 查询 + L2 聚合，只有少部分是 L3 生成**——
成本低、准确率高、故障面小。

### 8.2 一个关键洞察：**助手可以先于数据修复上线**

我们审查出的断裂点，**恰恰就是机构最常打电话问的问题**：

| 机构会问 | 背后是哪个断裂 | 助手能立刻回答 |
| --- | --- | --- |
| 「我的岗位为什么终端上看不到？」 | 审核中 / 未发布 / 已过期 / 已归档 / 资质过期 | ✅ 查状态即可给准确答案 |
| 「为什么被驳回了？」 | D5 岗位链 `rejectReason` 不回传 | ✅ 助手可以直接读到（后端有数据），**在 DTO 修复前就能回答** |
| 「我改了企业简介，招聘会那边怎么还是旧的？」 | D4 三张表不同步 | ✅ 说明原因 + 指路 |
| 「我的校招岗位怎么变成全职了？」 | D7 `campus` 映射 bug | ✅ 说明是已知问题 + 怎么改回来 |
| 「我填的学历要求去哪了？」 | D1 前端不展示 | ✅ 诚实说明「已保存，当前终端版本暂未展示」 |
| 「怎么批量导入？手工和 Excel 有什么区别？」 | D1 录入路径差异 | ✅ 引导到 Excel 模板并说明多 8 个字段 |

> **所以助手有双重价值**：正常期降低客服成本；**修复期充当「解释层」**——
> 在数据关联修好之前，至少让机构知道发生了什么，而不是打电话问。

### 8.3 形态

**常驻右下角悬浮入口 → 点开为右侧抽屉**（不占页面主区，不打断操作）。

| 要素 | 设计 |
| --- | --- |
| 入口 | 每页右下角悬浮球；**页面上下文自动带入**（在岗位页问「为什么没显示」，助手知道是问岗位） |
| 输入 | 自由文本 + **常见问题快捷入口**（非技术用户更常点按钮而不是打字） |
| 输出 | 回答 + **可执行的跳转按钮**（「去看这 3 条」「打开 Excel 模板」） |
| 边界提示 | 涉及跨机构、求职者数据、平台配置的问题，**明确回答「这个我查不到」并给工单入口** |

### 8.4 能力分层（决定成本与准确率）

| 层 | 能力 | 实现 | 占比预估 |
| --- | --- | --- | --- |
| **L1 查询** | 查我的岗位/招聘会/企业/政策的状态、审核结果、驳回原因、数据源同步情况、资质到期日 | **直接查库，模板化回答** | ~50% |
| **L1 诊断** | 「为什么终端看不到」的决策树：审核态 → 发布态 → 有效期 → 归档 → 机构资质 → 终端投放，**逐层给出卡在哪一步** | **规则决策树**，不调模型 | ~20% |
| **L2 聚合** | 「我这个月效果怎么样」「哪些内容没人看」 | SQL 聚合 + 模板 | ~10% |
| **L3 生成** | 操作指导问答、字段含义解释、把驳回原因翻成改法、开放问题 | 调模型 + **知识库检索** | ~20% |

**关键设计**：**先走 L1 决策树，走不通才升级到 L3**。
用户问「岗位为什么看不到」时，答案应该是确定的诊断结论，不是模型猜的。

### 8.5 「为什么终端看不到」决策树（L1 核心能力）

```text
查这条内容 →
  ① reviewStatus != approved  → 「还在审核中/已驳回：<原因>」+ 跳转
  ② publishStatus != published → 「审核通过了但未发布」+ 说明发布规则
  ③ archivedAt 非空            → 「已归档」
  ④ validThrough 已过          → 「已过截止日 <日期>」+ 引导改期或下架
  ⑤ 机构资质 expired           → 「机构资质已过期，本机构内容已暂停展示」+ 跳资质页
  ⑥ 该内容未投放到任何在线终端 → 「已发布，但当前无在线终端展示」+ 跳终端覆盖
  ⑦ 以上都正常                → 「已在 N 个点位展示，本周被浏览 X 次」+ 跳效果页
```

**这棵树覆盖了机构 80% 的疑问**，且**每一步都是确定性判断，不调模型**。

### 8.6 硬边界（必须写进实现）

| 红线 | 说明 |
| --- | --- |
| **只答本机构的数据** | 服务端强制 `orgId` 过滤；问「别的机构怎么样」→ 明确拒答 |
| **不碰求职者数据** | 不回答任何涉及具体求职者的问题；效果数据只给聚合 + 最小样本抑制 |
| **不生成招聘承诺** | 与 Admin 共用违禁词库，输出过安全闸 |
| **不代替执行** | 助手可以**引导到**操作页面，**不直接改数据**（不自动下架、不自动提审） |
| **不编答案** | 查不到就说查不到 + 给工单入口，**不猜** |
| **E3 输出标注** | 操作指导类回答标「AI 判断，仅供参考」；L1 查询类标 E1 不标 AI |

### 8.7 与现有 C1–C9 的关系

**助手不是第 10 个独立功能，而是这些能力的统一入口**：

| 用户在助手里问 | 实际调用 |
| --- | --- |
| 「我这批岗位有什么问题」 | C1 内容质检（L1） |
| 「这条会被驳回吗」 | C2 提交前预审 |
| 「帮我把这段描述改好」 | C3 内容改写（**结果仍需人工采纳**） |
| 「这个月效果如何」 | C6 效果解读 |
| 「数据源为什么失败」 | C8 同步失败归因 |
| 「企业信息哪里不一致」 | C9 跨端一致性 |

**助手 = 对话入口 + 决策树 + 知识库**，能力复用已有的 C1–C9，不重复造。

### 8.8 知识库来源（L3 那 20% 的依据）

| 来源 | 内容 |
| --- | --- |
| 页面职责文案 | 总方案 §9.4 的 16 条「本页内容出现在前台哪里」 |
| 字段说明 | Excel 模板的 `guide` 字段（`excel-template.ts` 每个字段都有填写指引） |
| 权限矩阵 | `partner-permission-matrix.md`（回答「我为什么没有这个菜单」） |
| 已知问题 | **本方案 §1 的 D1–D8 + PL/CO/FA 系列**——修复前作为「已知问题」诚实告知 |
| 合规边界 | 「为什么不能收简历」「为什么没有投递功能」这类问题的标准答案 |

### 8.9 分期

| 期 | 内容 | 依赖 |
| --- | --- | --- |
| **A1** | 悬浮入口 + **L1 决策树**（§8.5）+ 快捷问题 | **无 AI 依赖**，纯规则，可先于 ai-core 上线 |
| **A2** | L1 查询（状态/驳回/同步/资质）+ 跳转 | 无 |
| **A3** | L2 聚合（效果问答） | P1-3 归因 |
| **A4** | L3 知识库问答 + 复用 C1–C9 | 总方案 S1 内核 |

**A1+A2 不调用任何模型，却能覆盖约 70% 的机构疑问**——建议先做这两期，
验证真实问题分布后再决定 L3 投入多少。

### 8.10 Admin 侧要不要也有助手

**建议暂不做。** 理由：
- Admin 用户是内部运营，熟悉系统，问题密度低；
- Admin 的核心诉求是「批量处理」和「看得全」，不是「问答」；
- Admin 已有 §3.4 的「AI 每日要点」承担主动提示的职责。

若未来运营团队扩大、新人多，再评估。
