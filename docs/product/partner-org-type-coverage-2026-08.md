## 零、先说三个已核实的事实

| # | 事实 | 证据 |
| --- | --- | --- |
| **F1** | **系统只有 5 类机构，没有「园区」** | `admin-orgs.service.ts:88-140` 只定义了 school / public_employment / licensed_hr / fair_organizer / enterprise_source |
| **F2** | **`fair_organizer` 与 `enterprise_source` 的 `allowedModules` 是空数组、`sceneTemplate` 为 null** | `admin-orgs.service.ts:132-139` |
| **F3** | **两套矩阵有 1 条自洽、2 条硬冲突** | 见下 |
| **F4** | **终端模块矩阵目前「写了但没接」** | Kiosk 配置响应根本没读 `sceneTemplate/enabledModulesJson`（`terminals-admin.service.ts:612`、`terminal-config.types.ts:23`），所以空数组当前**不会**让终端什么都没有 |
| **F5** | **政策写接口不校验机构类型** | 文档禁止 HR/主办方/企业管理政策，但 `policies.service.ts:135,310` 只检查账号挂靠与机构启用——**五类实际上都能创建政策** |
| **F6** | **Admin 新建机构默认组合会被服务端拒绝** | 默认类型人社、场景为空，保存条件不要求选场景（`partners/index.tsx:128,155`），提交即撞 `ORG_TYPE_MATRIX_VIOLATION` |
| **F7** | **UI 无法把运营机构改成 source-only** | 编辑时场景选空写成 `undefined` → JSON 省略该字段 → 服务端保留旧值（`partners/index.tsx:369`、`admin-orgs.service.ts:348`） |
| **F8** | **共享类型与真实数据不兼容** | `PartnerSceneConfig.sceneTemplate` 要求非空（`partner.ts:68`），但两个 source-only 类型真实值就是 `null` |

### F3 的正确解读（**修正版**——原判断过于乐观）

> ⚠️ **2026-08-11 修正**：本节初稿写的是「不是 bug，逻辑自洽」。
> Codex 独立复核后证明**只有 1 条自洽，另外 2 条是硬冲突**。原判断错误，已改写。

两套矩阵管的是**不同的东西**（`console-plan §6.5` 已裁定「二者不可互换」）：

| 矩阵 | 管什么 |
| --- | --- |
| `ORG_TYPE_MATRIX.allowedModules` | 该机构**名下终端**能开哪些 Kiosk 模块 |
| `partner-permission-matrix.md` | 该机构**在后台**能管什么内容 |

**但这个区分只解释得了 1 条：**

| 条目 | 判定 | 说明 |
| --- | :---: | --- |
| **人力资源公司**：终端有 `job_fair`，后台招聘会权限全 ❌ | ✅ **自洽** | 「看别人办的会，自己不办会」——两个维度，不矛盾（`admin-orgs.service.ts:119`） |
| **人力资源公司**：终端允许 `print_scan`，文档 sceneConfig 对 `print_material_service` 标 ❌ | 🔴 **口径冲突** | 两者边界从未定义（`admin-orgs.service.ts:121` vs `partner-permission-matrix.md:118`） |
| **招聘会主办方**：服务端强制空模块，文档 sceneConfig 却允许岗位展示/招聘会/数字会务/资料打印/API 导入/统计 | 🔴 **硬冲突** | 同一维度上直接打架（`admin-orgs.service.ts:132` vs `partner-permission-matrix.md:115`） |
| **企业来源方**：服务端强制空模块，文档 sceneConfig 允许岗位展示/文件导入/统计 | 🔴 **硬冲突** | 同上（`admin-orgs.service.ts:136`） |

**结论修正**：不是「设计自洽只是没写下来」，而是**权限矩阵文档的 sceneConfig 一节本身就与服务端矩阵矛盾**。
必须先裁定哪一边是事实源（建议：**服务端 `ORG_TYPE_MATRIX` 为准，文档改写**），再谈界面说明。

### F4 的含义：这套矩阵现在是空转的

`ORG_TYPE_MATRIX` 只在**创建/编辑机构时**做校验（`admin-orgs.service.ts:635` 抛 `ORG_TYPE_MATRIX_VIOLATION`），
但**下发给终端时根本没用它**。当前 Kiosk 配置只下发智慧校园和百宝箱配置。

连带后果：
- 两个 source-only 类型**技术上仍可绑终端**——设备预创建/重绑只检查机构存在与启用，不看类型（`terminals-admin.service.ts:178,305`）
- 它们提交的内容经 Admin 审核发布后，**可显示在任意机构乃至未绑定机构的终端上**——公开查询只看审核/发布状态（`jobs-kiosk.service.ts:48,130`）

> **这意味着「机构类型 → 终端能力」这条链目前是断的。** 在补 capability 投影之前，
> 先把这个事实写清楚，避免误以为矩阵已经在生效。

### F2 的意图：已编码的假设，未确认的决策

验证脚本明确称二者为 `source-only`（`verify-admin-orgs.ts:339`），说明**不是手误**；
但 `next-tasks.md:783` 又要求产品确认是否漏配。
→ 定性为**「已编码的假设、未最终确认的产品决策」**，仍需拍板。

## 一、逐类业务覆盖度

> 图例：✅ 已有 · ⚠️ 部分/未开放 · ❌ 完全没有 · 🚫 合规上不该做

### 1.1 人社 / 公共就业服务机构 `public_employment_service`

| 典型业务 | 覆盖 | 说明 |
| --- | :---: | --- |
| 发布就业政策与补贴指引 | ✅ | 政策公告管理 |
| 组织公共招聘会 | ✅ | 招聘会管理（主表） |
| 归集辖区岗位信息 | ✅ | 岗位管理 + 数据源 |
| 本机构服务数据 | ⚠️ | `/stats` 是空壳，端点已存在未接 |
| **辖区多网点管理** | ❌ | 一个人社局下辖多个街道服务站，现在只能建成**多个互相独立的机构**，数据不汇总 |
| **全辖区数据汇总** | ❌ | 权限矩阵写了「✅ 全辖区」，但**没有实现**——没有机构层级/父子关系模型 |
| **向上级报送统计** | ❌ | 无导出、无报表模板 |
| **对辖区人力资源机构的监管视图** | ❌ | 人社对辖区 HR 机构有监管职责，系统无此角色 |
| 就业困难人员帮扶台账 | 🚫 | 涉及个人身份与帮扶记录，**平台定位不做**（CLAUDE.md §2） |

**最大缺口：机构层级**。人社是唯一有「辖区」概念的类型，现有模型是扁平的。

> 补充证据：共享类型**已经声明**了辖区、行政级别、政府编码（`partner.ts:58`），
> 但 `Organization` 表（`schema.prisma:410`）**没有这些列，也没有父子关系**——
> 即「接口上承诺了、库里没有」。权限矩阵写的「全辖区统计 / 辖区推送」同理，
> 统计始终只按当前 `orgId`（`partner-stats.service.ts:64`）。
> 辖区 HR 机构监管视图只存在于**平台 Admin** 的读取接口（`admin-recruitment-content.controller.ts:22`），人社 Partner 无对应功能。

### 1.2 高校就业中心 `school_employment_center`

| 典型业务 | 覆盖 | 说明 |
| --- | :---: | --- |
| 校招信息发布 | ✅ | 岗位管理 |
| 校园招聘会 | ✅ | 招聘会 + `campus` 主题 |
| 智慧校园 / 迎新 | ⚠️ | **只有终端开关，内容 CMS 未开放**（`OrientationPanel` 预留未填实） |
| 校企合作 | ⚠️ | 有 `campus_corp` 主题，**无管理界面** |
| **毕业生就业数据统计** | ❌ | **高校最核心的 KPI，完全没有** |
| **就业质量报告** | ❌ | 同上 |
| **分院系 / 专业维度** | ❌ | 现有统计只到机构，无组织维度 |
| **生涯指导活动 / 课程** | ❌ | 无活动管理 |
| **招聘会子资源**（参会企业/展区/资料/导览） | ❌ | 权限矩阵写了 ✅（`partner-permission-matrix.md:66`），但 Partner 只有主表 CRUD，子资源全在 Admin 接口（`jobs.controller.ts:405` vs `admin-fairs.controller.ts:97`）——**文档承诺 ≠ 实现** |

> ⚠️ **「就业率统计」有合规边界**：真实就业率需要知道「谁就业了」，
> 那是求职者个人数据，**平台不做**（CLAUDE.md §2、§10）。
> 高校侧能做且合规的是：**本校岗位被浏览多少次、多少人打开来源平台、招聘会到场人次**——
> 这些是聚合行为数据，属于 §4.3 效果层的范围。
> **做之前必须跟高校说清楚：这是「信息服务效果」，不是「就业率」。**

### 1.3 人力资源公司 `licensed_hr_agency`

| 典型业务 | 覆盖 | 说明 |
| --- | :---: | --- |
| 岗位信息发布 | ✅ | |
| 资质管理（HR 服务许可证） | ⚠️ | 模型已有，**审核状态机与到期降级未实现** |
| 数据源接入 | ✅ | API / Excel / Webhook 三轨 |
| 招聘会 | ❌ 设计如此 | 终端可展示他人的会，自己不办（见 F3） |
| **多客户企业管理** | ❌ | **HR 公司服务多家客户企业，系统无「客户」概念**——所有岗位混在一起，无法按客户分组 |
| **按客户维度的效果数据** | ❌ | 无法回答「A 客户的岗位这个月效果如何」 |
| 服务台账 / 结算 | ❌ | |
| 派遣 / 外包用工场景 | 🚫 | 涉及用工关系，超出「信息入口」定位 |

**最大缺口：客户维度**。HR 公司的业务单元是「客户企业」，现有模型只有「机构 → 岗位」两层。

> 资质那条要说得更准：模型存在（`schema.prisma:2241`），但**只有 Admin 只读接口**
> （`admin-recruitment-content.controller.ts:56`）——机构**无法自助提交、无法续期、看不到审核状态**，
> 也没有到期自动降级流程。对一个靠许可证经营的机构，这是硬缺口。

### 1.4 园区 / 开发区管委会 —— **类型不存在** ❌

| 典型业务 | 现有能否支撑 | 说明 |
| --- | :---: | --- |
| 入驻企业名录 | ⚠️ | 可用 `CompanyProfile`，但**没有「园区归属」概念** |
| 园区专场招聘会 | ⚠️ | 需要 `fair_organizer` 的能力 |
| 园区人才政策 / 补贴 | ⚠️ | 需要 `public_employment_service` 的政策能力 |
| **入驻企业用工需求汇总** | ❌ | 园区管委会要向上汇报「园区企业缺多少人」 |
| **园区配套信息**（通勤 / 住宿 / 食堂 / 子女入学） | ❌ | 这是园区招工的核心卖点，无对应内容类型 |
| 企业入驻服务 | ❌ | |

**园区是混合型**：政策（像人社）+ 招聘会（像主办方）+ 企业名录（像企业聚合）。
现有 5 类**没有一类能完整覆盖**。

### 1.5 企业来源方 `enterprise_source`（补充）

合规范围内的岗位与企业资料 CRUD 已有，**不需要新增核心页面**。但有一处缺失：

| 缺口 | 证据 |
| --- | --- |
| **缺单主体校验** | 文档称「仅本企业岗位」，代码只锁定**来源机构**（`jobs-partner.service.ts:218`、`companies.service.ts:492`）——岗位里的企业名称与 `CompanyProfile` 数量**都没绑定唯一法人主体**，一个企业来源方可以发布任意多家公司的内容 |

## 二、「园区」该不该单列？

### 结论：**应该单列，但不是现在**

**理由**：

1. **能力组合确实不同**——园区同时需要政策、招聘会、企业名录三类能力，
   而这三样分散在 `public_employment_service`（政策+会）与 `enterprise_source`（企业）里，
   现有任何一类都不完整。
2. **但现有 5 类本身还没理清**：
   - 两个空数组的意图未确认（F2）
   - 两套矩阵的关系从没写进界面（F3）
   - **Partner 前端目前对 5 类机构零差异化**（同一套侧栏）
3. **在没理清的地基上加第 6 类，混乱翻倍。**

### 正确顺序

```
① 确认 F2（空数组是有意还是漏配）      ← 产品拍板
② 服务端 capability 投影（唯一事实源）  ← 已在总方案 §4.6
③ Partner 前端真的按类型差异化
④ 界面上说清两套矩阵的关系（F3）
⑤ 再加「园区」类型
```

### 过渡期怎么办

在园区类型落地前，可以用 **`public_employment_service` + 手工配置** 临时支撑：
它已有政策、招聘会、岗位、统计四项能力，缺的只是「入驻企业名录」与「园区配套」。
**但必须在机构档案里标注真实性质**，不要让园区在系统里显示成「公共就业服务机构」——那是伪造机构性质。

## 三、跨类型的共性缺口（4 类都需要但都没有）

| # | 缺口 | 为什么四类都需要 |
| --- | --- | --- |
| **X1** | **机构层级 / 父子关系** | 人社有辖区网点、高校有院系、HR 公司有客户、园区有入驻企业——**四类都需要第二层组织维度**，现有模型是扁平的 |
| **X2** | **按第二层维度的效果数据** | 「哪个网点/院系/客户/入驻企业的内容效果好」——现在只能看机构总数 |
| **X3** | **对外报表导出** | 四类都要向上级/客户/管委会汇报，现在没有任何导出 |
| **X4** | **多人协作与分工** | 子账号方案有了但未实现；四类机构都是多人办公。`/account` 是空壳（`account/index.tsx:5`），无子账号、无细粒度 RBAC、无本机构审计日志 |
| **X5** | **Partner 前端对 5 类机构零差异化** | **登录态里根本没有 `orgType`**（`auth/index.ts:14`、`auth.controller.ts:249`）——布局层没有可分支的数据。侧栏 12 项是固定数组（`PartnerLayoutWrapper.tsx:39`）、路由无 guard（`routes/index.tsx:18`）、四个「新增」按钮无条件出现。唯一真实差异是数据源向导按服务端 capability 过滤（`sources/index.tsx:75,328`），**但 Excel 导入弹窗仍固定给「岗位/招聘会」两个选项，没用 `canImportJobs/canImportFairs`**（`ExcelImportModal.tsx:104,269`） |
| **X6** | **逐台终端状态对 Partner 未开放** | `terminals/index.tsx:5` 空壳 |

> **X5 是 ①②③④ 顺序能否往下走的前提**：没有 `orgType` 下发，前端连"按类型差异化"的输入都没有。
> 后端目前也只对岗位/招聘会导入和智慧校园做了类型兜底（`partner-capabilities.ts:85`、`smart-campus.service.ts:210`），
> **政策、企业资料接口完全没有按类型授权**（这正是 F5 的根因）。

> **X1 是最根本的**：它一个模型改动能同时解决四类机构的核心诉求。
> 建议作为 Partner 侧的下一个大结构改动来评估——但**必须先完成 §二 的 ①②③④**。
