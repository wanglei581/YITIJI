# 隐私遮挡：实现方案决策（2026-08-09）

> 本文是决策记录，不是待办清单。实现按本文口径执行；与本文冲突的旧口径以本文为准。
> 关联红线：CLAUDE.md §9「不伪造能力」、§11「文件安全要求」。

---

## 一、要修的是什么

用户在界面上逐项勾选「遮挡身份证号」，看到反馈，但后端 `pii_redact` 恒返回
`resultFileCreated: false` / `redactedFileId: null` —— **不生成任何新文件，
打印用的仍是含完整证件号的原件**。

页面有一行诚实警示（「当前版本不生成新文件」），所以不构成欺骗。
但这台机器在公共场所、输出是实体纸、纸会被别人看到或捡走，
整个遮挡交互等于白做，而用户以为做了。

---

## 二、三个技术事实（2026-08-09 实测，不是推断）

### 2.1 文字层 PDF 的坐标是免费的

`pii-scan.util.ts` 已经在用 `unpdf.getDocumentProxy()` —— 那是 pdfjs 的 document proxy。
`page.getTextContent()` 每个 item 自带 `transform[4]/[5]`（x/y）与 `width`/`height`。

实测（595×842 页面）：

```
"Name: Wang Lei"          x=60.0 y=760.0 w=89.4  h=12.0
"ID: 110101199003078515"  x=60.0 y=730.0 w=138.8 h=12.0
"Phone: 13800138000"      x=60.0 y=700.0 w=114.8 h=12.0
```

坐标一直在手里，`extractTextForPiiScan` 只返回 `{pageNumber, text}` 时丢掉了。
**这条路径不需要新依赖、不需要换计费接口。**

### 2.2 扫描件/图片的坐标要花钱

`baidu-ocr.provider.ts` 调的是 `accurate_basic`，**basic 版不返回 location**。
要坐标必须换 `accurate`（带 location），那是不同计费接口。

→ 这是花钱决策，不在本文范围内决定。见 §六。

### 2.3 画黑条盖不掉文字

`pdf-lib` 只能在页面上叠图形，底层文字流仍在 ——
**打印出的纸没问题，但存进「我的文档」的那份 PDF 里，证件号仍可复制、可搜索、可解析。**

要真删只能栅格化。可用能力已具备（`unpdf.renderPageAsImage` + `@napi-rs/canvas@1.0.0`，均已安装）。

## 三、决策

### 3.1 遮挡产物：受影响页栅格化，未受影响页保留原样

| 方案 | 判定 |
|---|---|
| pdf-lib 叠黑条 | ❌ 纸面可以，但存档件仍可提取原文。「已遮挡」这句话不成立 |
| 全文档栅格化 | ❌ 没有必要，白白牺牲无关页的清晰度与体积 |
| **只栅格化有遮挡的页** | ✅ **采用** |

约 300 DPI，黑条烧进像素后该页不可逆。未受影响的页保持矢量文字（更小、更锐、可选中）。
打印与「我的文档」统一使用同一份派生件 —— 不做「打印用一份、存档用另一份」，
两份会分叉，且用户扫码带走的必然是错的那份。

派生件按既有 `print-sign.service.ts` 的模式落 `FileObject.sourceFileId` +
`assetCategory: 'derived'`，血缘字段现成。

### 3.2 子串定位：宁可多盖，不可漏盖

`getTextContent` 的 item 常是整行（`"ID: 110101199003078515"`），
要只盖数字段需要子串位置。按 `matchIndex / str.length` 比例估算 + 两侧留白。

误差可控的原因：证件号、手机号、银行卡号**全是数字**，
而绝大多数字体的数字是等宽的（tabular figures 是排版惯例），数字段本身估得准；
误差来自前缀（`"ID: "`）是比例字体。留白后可覆盖。

**规则：估算偏大而不偏小。**多盖是看得见的、安全的；漏盖是看不见的、危险的。
多盖由用户在预览里发现并可回退（改成「保留」重来），漏盖用户发现不了。

### 3.3 「已遮挡」这句话的天花板

**机器复检 + 人眼确认，两道都要，缺一不可。**

- **机器复检**：在派生件上重新跑一遍 PII 扫描。发现的是「黑条盖错位置」。
- **人眼确认**：用户看原尺寸预览并确认。发现的是「压根没检出」。

为什么机器复检不能替代人眼：同一个检测器扫两遍，系统性漏检两遍都漏。
OCR 漏字、证件号被拆成多个 item、旋转页、低清扫描 —— 这些都表现为「检出为 0」，
复检同样报 0，看起来干干净净。**所以复检通过不等于干净，只等于「我盖的地方盖住了」。**

（这一条是 Codex 评审指出的，我原方案低估了检出完整性，只想着黑条本身。）

允许的文案：

| 状态 | 文案 |
|---|---|
| 复检通过 | 已遮挡你确认的 N 处 · 请核对预览 |
| 复检有残留 | 仍检出 N 处未盖住 · 不建议打印 |
| 拿不到坐标 | 这份是扫描件，本机还不能在上面定位遮挡 |
| 任何情况 | ❌ 已遮挡 / ❌ 已无隐私信息 / ❌ 隐私已保护 |

**永远不说「这份文件已无隐私信息」——本机没有能力做这个承诺。**

### 3.4 后端给出「可以说什么」，前端不许自己编

响应里带一个 `claim` 字段，前端按它选文案，不做自己的判断：

```ts
POST /materials/:fileId/pii-redact
→ {
  ok: boolean
  redactedFileId: string | null
  redactedFileUrl: string | null        // 见 §3.5：只有 id 在匿名路径上取不到文件
  items: Array<{
    id: string
    type: 'id_card' | 'phone' | 'bank_card' | 'address' | ...
    pageNumber: number
    requested: 'redact' | 'keep'
    applied:   'redacted' | 'kept' | 'failed_no_position'   // 逐项真实结果
  }>
  reverify: {
    ran: boolean
    remainingCount: number                    // >0 = 没盖干净
    method: 'text_layer' | 'ocr' | 'skipped'
  }
  claim: 'redacted_verified'      // 生成成功 + 复检 0 残留
       | 'redacted_unverified'    // 生成成功 + 复检没跑成
       | 'partial'                // 部分项 failed_no_position
       | 'not_supported'          // 拿不到坐标，未生成任何文件
  notSupportedReason?: 'scanned_no_position' | 'encrypted' | 'too_many_pages'
}
```

把「能说什么」放在 API 边界上强制，而不是靠前端自觉。
今天这个缺陷正是靠前端自觉没守住 —— 后端返回 `resultFileCreated:false`，
前端照样让用户走完了整个遮挡流程。

### 3.5 派生件必须直接带可访问 URL

**本条是实现中发现的规格错误，已修正。**

§3.4 初稿只给了 `redactedFileId`。但 `/files/:id/preview-url` **要求登录**，
而一体机是匿名使用的 —— 匿名用户拿到 id 也取不到文件，
遮挡功能在真实使用路径上整个不可用。

响应必须直接带 TTL 受限的签名 URL（参考 `fair-company-print.service.ts` 的
`FilesService.upload` → HMAC 签名链接，TTL 1h）。

推论：返回 `claim: 'redacted_verified'` 的同时必须保证派生件**真的可取**。
前端对此做了 fail-closed —— claim 说成功但拿不到文件时降级为「本机无法确认这次遮挡的结果」，
因为那种情况下打印的还是原件，「已遮挡」就是假的。

同理 `reverify.remainingCount` 不可省略：省略解析为 `null` 而非 `0`，
**「没报告残留」不等于「零残留」**。

## 四、交互契约（四步，第 3 步不可跳过）

1. **检出并逐项列出** —— 第几页 / 类型 / 片段（本身掩码显示，不在屏幕上重现完整证件号）
2. **逐项裁决** —— 默认全部遮挡；「保留」需单独点。与 `09-transform` 的逐项裁决同一套语法，用户学一次通用
3. **强制预览** —— 原尺寸可读，遮挡处标出。**这一步不能跳过、不能折叠、不能默认收起**
4. **确认「我核对过」才解锁打印**

第 3 步是这个功能唯一真正的安全阀（理由见 §3.3）。
任何以「少一步更顺」为由砍掉它的改动都不接受 —— 砍掉后这个功能就回到今天的状态：
用户以为做了，其实没有保证。

## 五、本次做什么 / 不做什么

**做（一级 · 文字层 PDF）**：零新依赖、零新计费，覆盖用户上传的 born-digital 简历
（智联 / BOSS / Word 导出，预计是多数）。

- `extractTextForPiiScan` 保留位置信息
- `PiiFinding` 增 bbox 字段（页码 + x/y/w/h + 页面尺寸，用于跨 DPI 换算）
- 遮挡：黑条 → 受影响页栅格化 → 重组 PDF → 落派生件
- 复检：在派生件上重跑扫描，结果如实回传
- `claim` 字段 + 前端按 claim 选文案
- 拿不到坐标时返回 `not_supported`，**不生成半成品文件**

**不做（二级 · 扫描件 / 图片）**：需要换百度 `accurate` 计费接口。
在此之前，扫描件走 `not_supported`，界面如实说明并给出路径：
① 用手机改好再传 ② 只打印不遮挡（用户确认）③ 换文字版简历。

值得注意：图片本身就是栅格，一旦有了坐标，遮挡反而比 PDF **更简单**（画个矩形重编码即可），
没有文字层残留问题。**卡点只在坐标，不在遮挡。**

**不做（已否决）**：按识别文本用 PDFKit 重排一份「隐私版」。
对简历不可接受 —— 版式是简历的一部分，重排等于毁掉用户的排版。
（此方案对纯文本材料成立，但那不是本功能的主要场景。）

**是否为扫描件/图片启用百度 `accurate`（带 location）接口。**

- 影响：一体机的纸质简历扫描件路径能不能真遮挡

- 不启用的后果：扫描件路径永远停在「如实告知做不了」——诚实，但功能缺一半

## 七、验收

| 项 | 判据 |
|---|---|
| 派生件文字层 | 用 `pdftotext` / `unpdf.extractText` 提取，**提不出被遮挡的号码** |
| 未受影响页 | 仍是矢量文字，可选中，未被栅格化 |
| 复检 | 派生件重跑扫描，`remainingCount` 与实际一致 |
| 逐项结果 | `applied` 反映每一处真实结果，不是笼统成功 |
| 拿不到坐标 | 返回 `not_supported`，**不产出任何文件**，不出现「已遮挡」字样 |
| 血缘 | 派生件 `sourceFileId` 指向原件，`assetCategory: 'derived'` |
| 文案 | `verify:compliance-copy` 覆盖 §3.3 的禁用词 |
| 预览步骤 | 无法跳过（无 skip 入口、不默认折叠） |
