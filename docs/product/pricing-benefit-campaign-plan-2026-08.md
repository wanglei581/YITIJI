## 一、必须先处理的两项 🔴

### R1 全额抵扣漏洞（接前端之前必须堵）

```ts
// benefit-redemption.service.ts
discountCents: order.amountCents   // 抵扣额 = 订单全额
```

而 `BenefitGrant`（`schema.prisma:1683-1699`）**没有面值、没有最高抵扣额、
没有服务范围、没有页数上限**。后果：

> 一张「免费打印 1 次」的券，可以抵掉一个 200 页彩打订单。
> `coupon` / `free_quota` / `package_entitlement` 任意一种只要还剩 1 份余量，
> 就能全额覆盖**任意金额**的本人打印订单。

**现在没出事，只因为前端没接。一旦接通即为资损。**

附带缺陷：活动允许可核销类型的 `quantityTotal=null`，
这种券能被领取，却会在核销时以「无可核销额度」失败（用户视角是"领了个假券"）。

### R2 活动页承诺了做不到的能力 ✅ 已修（2026-08-11）

活动详情页第 2 步原文「进入对应服务，**优先抵扣免费额度**」，
但 **Kiosk 全端 0 处引用 `benefitGrantId`**（后端 41 处）——
打印报价不查权益、确认页不能选券、收银页不调 `/orders/:id/redeem`。
用户领券后仍需全价支付。

→ 已改为「权益已记入账户；**抵扣功能尚未开放**，开放后可在下单时选择使用」，
并在代码注释中写明恢复条件。

## 三、四件事的真实难度

| 产品所有者的说法 | 现状 | 要做什么 | 难度 |
| --- | --- | --- | :---: |
| 优惠活动 / 权益活动 | ✅ `BenefitActivity` 已有 | 补规则字段 + 收窄核销 | 🟡 中 |
| **卡券包** | ⚠️ 表达不了异构组合 | 新增 2 张模板表 | 🟠 较大 |
| **补贴** | ❌ 只有一个 `sourceType='gov'` 标签 | 新增资金项目 + 结算模型 | 🔴 大 |
| 前端对接 | ❌ 零对接 | 报价返可用权益 + 确认页选券 + 收银页核销 | 🟡 中 |

### 3.1 卡券包：先分清是哪一种

| 理解 | 需要新模型吗 |
| --- | --- |
| 「我的券集中展示页」 | ❌ **不需要**——`/me/benefits` 已能按类型展示多条 Grant |
| 「一种权益有 N 次额度」 | ❌ **不需要**——Grant 的 `quantityTotal/Remaining` 就是 |
| **「2 次打印券 + 1 次 AI 优化券」组合** | ✅ **需要**——`package_entitlement` 只是一个字符串类型加数量，表达不了异构组合 |

若要做可配置、可售卖、可版本化的组合包：

- 新增 `BenefitPackage` / `BenefitPackageItem` 作为**模板**
- 领取或购买包后 → **原子生成若干 `BenefitGrant`**
- **Grant 继续作为唯一余额，`RedemptionRecord` 继续作为唯一核销账本**

> ⚠️ **不要建一套与 `BenefitGrant` 并列的「卡券余额」**——
> 那会形成两套额度、两套退款口径，对账时无法收敛。

现有阻碍：一次 Activity 领取只创建一条 Grant，且被 `BenefitClaim` 的 `activityId+endUserId` 唯一约束绑定，
**无法原子发放多个包内权益**（`benefit-activities.service.ts:184-208`）。

### 3.2 补贴：现有模型答不出四个关键问题

| 问题 | 现有模型能答吗 |
| --- | :---: |
| 补给谁 | ✅ Grant 有 `endUserId` |
| 还剩几次 | ✅ Grant 有 `quantityRemaining` |
| **谁出资**（哪家人社、哪个项目） | ❌ `sourceType='gov'` 只是类别标签 |
| **预算多少 / 还剩多少** | ❌ 无 |
| **怎么结算**（机构应付多少） | ❌ `RedemptionRecord.amountCents` 是订单抵扣额，不是机构应付 |
| **怎么对账** | ❌ 现有对账把 discount 排除在实收资金外，无按出资方的应收与结算单 |
| **凭什么给他**（困难人员资格） | ❌ Activity 对所有会员公开，无人群条件 / 名单 / 资格凭证 |

最小需要：`FundingProgram`（出资机构外键 + 预算 + 有效期 + 资格规则）、
发行批次、`SettlementEntry` + `Reversal`；
`Grant` 增 `programId`/`issuanceBatchId`，核销时记录**资金方承担金额、结算期、对账状态**。

> **对外表述红线**：只能说「某机构提供的**打印服务额度**」，
> **不能**把服务券包装成「政府现金补贴到账」。

#### 4.3.1 双面为什么必须单独设价

**现状：双面完全不影响价格。** 计价口径是 `单价 × 内容页数 × 份数`
（`pricing.service.ts:56-90`），代码注释写明：

> duplex / pagesPerSheet 影响的是**物理纸张而非计费内容页**，不改本批单价；
> 按张/双面折扣属**后续定价规则扩展**（`price-config.seed.ts:19-20`）

后果：10 页文档单面双面都算 10 页、价格一样，**用户没有任何动力选双面**——
只省纸不省钱，平台白白多耗纸。

**修法：加两个 serviceKey 按 duplex 分流单价，不改计价模型。**
仍是「单价 × 内容页 × 份数」，只是 `serviceKey` 的选取从
`colorMode` 一维变成 `colorMode × duplex` 二维。

**为什么是八折而不是半价**：打印成本 = 墨粉（按内容页）+ 纸张（按物理张），
**双面省的是纸不是墨**。八折既让用户看得懂「双面更便宜」，
又不会低到诱使用户把不该双面的材料（要交上去的表格、需骑缝章的文件）也印成双面。

#### 4.3.2 页数上限：只有补贴场景需要

| 场景 | 是否限页数 | 理由 |
| --- | :---: | --- |
| **自费打印** | ❌ **不限** | 用户自付，打得多反而是好事；限制只会赶走客人 |
| **免费 / 补贴打印** | ✅ **必须限** | 不限即财政被薅 |

**结论：「页数上限」是补贴策略的属性，不是打印功能的属性。**
把它做进 `PriceConfig` 是错的——那会误伤自费用户。

超额处理：**免费额度用完自动转自费**，且必须在**出纸前**于屏幕上明示：
> 「前 20 页由 XX 项目支付，超出 8 页需付 ¥4.00」

另建议加**单次打印张数上限**（如 100 页）——
但那是**运营限制**（防误操作打 500 页、防卡纸、防后面排队），
**不是计费限制**，不要和补贴额度混在一起。

#### 4.3.3 已知假能力字段

`PriceConfig.effectiveFrom` **是摆设**：`PricingService` 只读 `active`，
**从不按生效时间切换价目**（`price-config.seed.ts:24-26` 自陈
「生产写入时不要依赖该列做排期改价」）。

→ 「下月 1 号起调价」这类**排期改价当前做不到**，需单独实现。
在实现前，Admin 价目页**不应展示生效时间输入框**，否则是伪造能力。

**绝对不可计价（第二类 · 许可红线）**

- 岗位浏览 / 岗位详情 / 招聘会查看 / 政策查询
- 外部投递或预约入口的跳转
- 任何按**曝光量 / 跳转量**的计费

**永久红线（无论何种包装）**

- 按候选人数 / 投递量 / 面试量 / Offer 量 / 入职量 / 简历数计费或返利
  （`compliance-boundary.md:299-307`）

> ⚠️ 现有活动文案正则**不覆盖**「投递量、到面率、入职量、推荐成功抽成」等表达
> （`benefit-activities.service.ts:22-23`）——**关键词过滤不能当合规门禁**，需人工审核兜底。

## 四点五、按场景 + 功能限定的补贴策略（政府采购场景）

> 触发：产品所有者提出「政府采购整机、政府买单、想给用户免费，
> 但机器里有打印功能也能当普通打印机用，**不能全部免费**——
> 补贴和免费要能做场景限定或功能限定」。
> 本节结论基于已查证的一手事实；Codex 独立审查结果回来后再校验补充。

### 4.5.1 ⚠️ 重要更正：场景维度**不能直接用**

> **初稿写的是「好消息：场景维度已经存在，不用新造」——那是错的。**
> Codex 无范围限制复核后证明：`FileObject.purpose` **不可信，且现有映射本身就是错的**。
> 本节已按一手证据改写。

**错在三层：**

**① `purpose` 不是枚举，契约已经漂移。**
数据库层只是必填 `String`（`schema.prisma:820-888`），不存在可穷举、不可漂移的取值集。
应用层声明 18 个值，其中 `contract_upload` **重复声明**，
而招聘内容代码又读取**未纳入该联合类型**的 `qualification_evidence`
（`packages/shared/src/types/file.ts:17-39`、`recruitment-content-readiness.ts:119-127`）。

**② 简历打印入口实际写的是 `print_doc`，不是 `resume_upload`。**

| Kiosk 入口 | 实际 purpose | 能否识别场景 |
| --- | --- | :---: |
| 简历打印（`/print/upload?source=resume`） | **`print_doc`** | ❌ `source` 只留在浏览器状态，**后端拿不到** |
| 打印扫描上传 / 手机扫码 / 照片打印 | `print_doc` | ❌ |
| U 盘（通用打印页） | `print_doc` | ❌ **与 AI 简历导入组件的 `resume_upload` 口径不一致** |
| 扫描件 | `resume_scan` / `id_scan` / `print_doc` | ⚠️ **用户自选分类，非内容核验** |
| 招聘会资料（bridge） | `fair_material` | ✅ **当前少数可信来源**——服务端校验审核/发布/allowPrint 后生成 |
| 招聘会参会准备单 | **`print_doc`** | ❌ 业务上属招聘会场景，却被误归普通文档 |
| 政策材料 | `print_doc` | ❌ 只跳通用上传，无政策场景 |

**③ 匿名接口可直接声明任意 purpose。**
Kiosk 上传接口由**调用方提交** purpose，后端只校验白名单、MIME、扩展名和魔数，
**不验证「文件是否真的是简历」**（`files.controller.ts:104-149`）。
→ **把 purpose 当财政补贴凭证，可以换入口、也可以直接调接口绕过。**

**④ 报价与建单请求根本没有场景字段。**
`PrintConfirmPage` 的报价与建单都不含 `source/scenario/purpose`
（`PrintConfirmPage.tsx:144-150,246-264`、`create-print-job.dto.ts:64-89`）。
建单服务虽能从签名 URL 解析 `fileId` 并读 purpose，
但**只用于安全门禁（contract 拒绝、PII 扫描判定），不参与计价**
（`print-jobs.service.ts:211-222,469-512`）。

### 4.5.2 正确做法：服务端推导 + 来源可信分级

**最小改动不是「把 `source` 传给后端」**——那仍是客户端自报。
应新增**服务端推导并固化**的三元组：

```
scenarioKey        场景（服务端判定，不接受客户端直接指定）
provenanceType     来源可信级别
sourceRefId        溯源引用（哪场招聘会 / 哪个扫描任务 / 哪份简历）
```

**来源可信分级**（决定补贴敢不敢给）：

| provenanceType | 含义 | 举例 | 政府补贴 |
| --- | --- | --- | :---: |
| `verified_material` | 服务端校验后生成 | 招聘会资料 bridge | ✅ 最可信 |
| `system_generated` | 平台自己生成 | 求职信、参会准备单、自我探索报告 | ✅ |
| `scan_declared` | 本机扫描 + 用户选分类 | 扫描简历 / 证件 | ⚠️ 可接受，配小额度 |
| `user_declared` | 用户上传时自报 | 上传文件、U 盘导入 | ⚠️ **风险最高** |

→ **政府规则可以只补可信来源，或对 `user_declared` 明确接受小额度自报风险。**
这比「试图识别文件是不是真简历」现实得多。

**且报价、建单、订单、打印任务必须共用同一份不可变上下文**——
不能报价时判一次、核销时再判一次，否则用户会看到免费却在收银页变全价。

### 4.5.2b 另外四个必须知道的约束

| # | 事实 | 影响 |
| --- | --- | --- |
| **C1** | **`PriceConfig.serviceKey` 全局唯一**，不能按终端设不同价（`schema.prisma:326-338`） | ❌ **不能靠「把政府终端的 PriceConfig 改成 0」实现补贴**。PriceConfig 永远算公开原价，补贴在原价之后抵扣 |
| **C2** | 已有 `gov-enterprise-edition-design.md`，其中「整机 `billingEnabled=false`」 | ⚠️ **会让私人打印一起免费，与本需求直接冲突**，应被场景化策略取代 |
| **C3** | `Terminal` 只有 `orgId`、位置、生命周期，**没有采购方/出资方/运营模式**；`govOrgCode` 只在共享前端类型，**没有 Prisma 持久化** | 「哪台机器由谁采购、谁承担费用」当前**无法表达** |
| **C4** | 复印**尚无任务与计价闭环**（capability key 有，正式任务类型只有 print/scan/document_process）；扫描创建 `ScanTask` 但**不关联 Order/PriceConfig/serviceKey** | §4.3 的 `copy_*` / `scan_*` 价目项**需要先补履约计量**才能启用 |

### 4.5.3 策略模型：独立建模，不要扩 BenefitActivity

**Codex 裁定：应新建独立的 `FundingProgram` + `SubsidyRule`，
不应把 `BenefitActivity`/`BenefitGrant` 扩成政府资金项目**——
后两者分别是「活动领取」与「个人权益」，**不具备预算与结算语义**。

```
FundingProgram（资金项目）
  出资机构 · 资金性质 · 项目/合同编号 · 总预算 · 有效期
  · 状态 · 优先级 · 预算耗尽降级方式

SubsidyRule（补贴规则）
  terminal/org 范围 · scenarioKeys · serviceKeys
  · 来源可信级别（provenanceType）· 人群条件
  · 每单最高抵扣 · 页数上限 · 个人周期额度 · 是否允许部分补贴
```

**`Order` 必须固化决策快照**：原价、平台优惠、第三方补贴、个人应付、
scenario/provenance、**规则版本**、FundingProgram
——避免事后按已变化的配置重算（`schema.prisma:269-308`）。

**政府资金需要独立流水**：`SubsidyReservation` / `SettlementEntry` / `Reversal`。
> 它**不是第二套卡券余额**，而是**第三方应收 + 预算预占 + 冲正账本**。
> 现有 `RedemptionRecord` 可继续作为券/权益核销的唯一事实源，
> 但其语义明确是**平台 credit**，不能直接充当政府结算流水（`schema.prisma:1753-1777`）。

**三者账务上不是同一件事**：

| | 含义 |
| --- | --- |
| 真正 0 元服务 | **没有应收** |
| 平台赠送 | **平台优惠**（收入减项） |
| 政府买单 | **对出资方应收** |

### 4.5.4 补贴策略 vs 权益券：两套机制，一个账本

| | 补贴策略 | 权益券 `BenefitGrant` |
| --- | --- | --- |
| 触发 | **自动生效**（符合条件即免费，用户无感） | **用户持有并主动使用** |
| 来源 | 出资方项目 | 活动领取 / 发放 |
| 配置位置 | 补贴资金项目 | 权益活动 |

**但两者共用同一套额度扣减与核销账本**（`RedemptionRecord`），
否则会出现「补贴扣了、券也扣了」的重复抵扣。

### 4.5.5 匹配、预占与降级

**匹配顺序**（Codex 建议，可直接采用）：

```
服务端场景解析 → 有效期 → 终端/机构 → serviceKey
→ 来源可信级别 → 人群 → 个人额度/项目预算
```

同优先级冲突时**按更具体规则、再按稳定 ID 取一条**；
**首期禁止叠加**，并在 Admin 保存时**拒绝同优先级同范围的重叠规则**，
避免运行时随机命中。

**预算必须预占，不能只在核销时扣**：

| 阶段 | 动作 |
| --- | --- |
| 报价 | **只做预览**，不预占 |
| 建单 | **同一事务内重新校验并预占预算**（`SubsidyReservation`） |
| 履约完成 | 结算（`SettlementEntry`） |
| 失败 / 取消 / 超时 / 退款 | **释放或冲正**（`Reversal`） |

> **核销只能消费建单时保存的决策快照**，不能重新判场景——
> 否则用户会看到免费却在收银页变全价，或预算被重复占用
> （`order-quote.service.ts:30-47`、`print-jobs.service.ts:392-412`）。

**降级规则**：

| 问题 | 处理 |
| --- | --- |
| 预算耗尽 | **默认转自费并要求用户重新确认**；仅当政府合同禁止现场收费时才按策略配置为拒绝。**绝不静默扣全价** |
| 预占失败（并发抢完） | 回到自费并重新提示 |
| 对账区分 | `Order` 与结算流水必须记录**出资方**，否则分不清「平台自送」与「政府买单」 |

**现有对账把所有 discount 排除在资金流之外**（`reconciliation.service.ts:121-129`），
既形不成政府应收，也分不清平台赠送与政府承担——**这是补贴上线前必须改的**。

**资金事件不能只靠审计日志**：`AuditService.write` 失败会被吞掉
（`audit.service.ts:23-35,80-104`），预占、结算、冲正必须用**事务内账本**或 required audit / outbox。

### 4.5.6 人群限定：首期建议不做

政府可能只想补贴特定人群（已做失业登记、本地户籍）。
**但这类身份信息一旦采集，就超出了本平台「不收集求职者身份档案」的边界**
（CLAUDE.md §2、§10）。

**Codex 的补充判断**：按人群限定**不是绝对不能做**，
但当前系统**没有采集目的、资格核验、撤销、保存期限和授权链**，
未经专项隐私设计不应上线。且 `EndUser` 只有手机号、openid、昵称、状态
（`schema.prisma:542-579`），**没有任何资格属性**。

**建议第一版只做「终端 × 场景 × 功能 × 额度」四维，不做人群限定。**
需要人群区分时，让出资方在**发码环节**控制——他们按自己的名单发码，我们只负责核销。

若将来必须做，**首选方案是资格断言而非原始材料**：
由政府侧核验并签发**一次性码或签名资格断言**，
平台只保存**资格类型、签发方、有效期、外部引用哈希**，
**不保存户籍证明或失业登记原件**（`compliance-boundary.md:155-164`）。
身份证、社保卡等高敏材料**不得长期落库**。

## 五、机构出资的结算口径（同一笔钱，口径不同性质就变）

| 结算方式 | 性质 | 可否 |
| --- | --- | :---: |
| 按**实际消费**结算（打了多少页、用了几次 AI） | 第一类 · 工具与耗材 | ✅ |
| 按**岗位曝光量 / 跳转量**释放预算 | 第二类 · 须先过许可审查 | ⚠️ |
| 按**招聘成果**（投递 / 到面 / 入职）释放预算或返利 | 效果付费招聘中介 | ❌ **红线** |

另：赞助机构**不得**获得个人领取人名单、简历或行为明细，
只能取得必要的履约对账数据与满足最小样本阈值（N≥5）的聚合统计
（`compliance-boundary.md:330-341`）。

## 六、资金合规现状（Codex 风险识别，非法律意见）

- **当前没有**充值钱包、提现、转让或用户购买套餐，`BenefitGrant` 定义为平台 credit
  → **目前不构成明显的用户预付沉淀资金池**
- **一旦允许用户付费购买长期额度**，须按单用途预付消费场景评估：
  备案、资金管理、余额退款、有效期、消费者权益义务
- **若支持跨商户通用 / 转让 / 提现 / 代收付**，支付牌照风险显著上升
  → **不应把 `BenefitGrant` 演化成通用钱包**

> 正式发行付费券或机构补贴前，应由法务按经营主体、使用范围和属地规则复核。

### 补贴策略的 MVP（Codex 建议，可直接采用）

**首期收窄为**：

> 指定政府项目 + 指定终端 + **已登录用户** + 简历场景 + **黑白打印**
> + 可配置页数/周期上限 + 总预算；**普通 `print_doc` 始终自费**

配套必做：

| # | 任务 |
| --- | --- |
| **S-1** | 新增服务端可信 `scenarioKey` / `provenanceType` / `sourceRefId`，
并**修正现有场景映射**：简历上传、U 盘、扫描、招聘会参会准备单、政策材料（§4.5.1 表） |
| **S-2** | 新增 `FundingProgram` + `SubsidyRule` + `SubsidyReservation` / `SettlementEntry` / `Reversal`；
**不把普通审计日志当资金账本** |
| **S-3** | 报价接口补 terminal、登录态与文件上下文；**建单事务重新校验并预占**；变价或预算耗尽必须要求重新确认 |
| **S-4** | `Order` 固化决策快照（原价/平台优惠/第三方补贴/个人应付/scenario/provenance/规则版本/program） |
| **S-5** | 对账改造：discount 不能一律排除在资金流外，须能形成**政府应收**并区分平台赠送 |
| **S-6** | E2E：并发预算、换入口绕过、部分补贴、支付竞态、任务失败释放、退款冲正、政府对账 |

> ⚠️ **`gov-enterprise-edition-design.md` 中的「整机 `billingEnabled=false`」与本需求冲突**
> （会让私人打印一起免费），应被本节的场景化策略取代。

### 可以后做（W1+）

- 异构卡券包模板（`BenefitPackage` + `Item`）、包版本、购买订单、一包多 Grant 原子发放
- 权益类通知（扩 `MemberNotification` 关联类型）
- Partner 侧活动配置与赞助对账

### 不该做

- ❌ 把 `BenefitGrant` 做成通用钱包（跨商户 / 转让 / 提现）
- ❌ 建第二套与 Grant 并列的「卡券余额」
- ❌ 任何按招聘成果的计费、返利或预算释放
- ❌ 在补贴对外表述中使用「政府现金补贴到账」
- ❌ 把关键词正则当作合规门禁的唯一手段
