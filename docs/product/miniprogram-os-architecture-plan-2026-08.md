## 一、决策摘要

小程序不做“一体机缩小版”，也不做独立招聘平台。正式定位是：

> **AI 求职操作系统的随身端：帮助用户在手机上完成求职准备、材料管理、AI 决策和打印下单，再到一体机完成安全、可靠的实体履约。**

一体机与小程序共同完成一条服务链，但各自承担不可替代的部分：

```text
小程序：持续关系 + 私密准备 + AI 编排 + 下单支付 + 到机提醒
                                  ↓
                         材料包 + 到机码
                                  ↓
一体机：现场核验 + 设备能力确认 + 队列释放 + 打印扫描 + 异常兜底
```

本方案拍定以下原则：

1. 小程序负责“准备、决策、管理、提醒”，一体机负责“现场、硬件、交付、兜底”。
2. AI 是全局交互层，不只是一个聊天页面或单独 Tab。
3. 手机可以下单和支付，但不得从公网直接驱动打印机出纸；到机确认后才释放打印任务。
4. “材料包”是跨端核心交接物，“到机码”是履约凭证，“统一账号”是长期经营基础。
5. 岗位、招聘会、企业信息只做第三方或官方来源入口，不形成平台内投递、预约或招聘闭环。
6. 新源码只保留一份，目标目录为 `apps/miniapp/`；不再维护独立 `~/WeChatProjects/zhiyida` 副本。
7. 旧分支和高保真原型只能选择性复用，不直接复活落后主干的旧实现。

## 三、商业定位

### 3.1 产品本质

本项目出售的不是“招聘结果”，而是三类可交付服务：

1. **数字求职工具**：AI 简历、模拟面试、职业规划、材料整理、信息理解。
2. **实体履约服务**：打印、扫描、复印、材料包、现场服务。
3. **场景运营能力**：学校、人社大厅、招聘会和服务机构的终端部署、内容配置、权益运营与设备运维。

小程序的商业价值不是多一个入口，而是解决一体机无法解决的持续关系：用户离开点位后仍能准备材料、管理订单、接收提醒并再次到机履约。

### 3.2 目标用户

> **履约形态 overlay（2026-09-05）**：下表五类是**处境**，不是阶层。功能取舍另加且只加两个值：`hall_paper`（现场纸质履约，口头「蓝领」）与 `phone_digital`（数字迭代准备，口头「白领」）。完整需求、空转清单、12 个月可长 / 不长见 [audience-growth-space.md](./audience-growth-space.md)。本文不维护阶层画像，避免与处境表并列成两套用户。


| 用户 | 核心问题 | 小程序价值 | 一体机价值 |
|---|---|---|---|
| 应届毕业生 | 简历经验少、准备链路长 | AI 引导、版本管理、面试练习 | 校园现场打印与扫描 |
| 临时求职者 | 时间紧、材料散 | 快速上传、诊断、下单 | 就近立即出纸 |
| 招聘会参会者 | 不知道带什么、现场易遗漏 | 行前清单、材料包、到机码 | 会场打印、导览、补打 |
| 公共就业服务用户 | 数字能力差异大 | 手机提前准备、家人协助 | 大屏引导、工作人员兜底 |
| 长期求职者 | 多版本、多岗位、反复修改 | 任务持续、资产沉淀、权益复购 | 关键节点交付成品 |

### 3.3 北极星指标

不以页面数、点击量或单纯小程序 DAU 作为核心成功指标。北极星指标是：

> **每台有效终端每天完成的跨端真实履约订单数。**

配套指标：

- 小程序准备任务完成率。
- AI 结果进入材料资产的比例。
- 材料包创建到下单转化率。
- 支付成功到到机释放率。
- 到机释放到真实出纸完成率。
- 首次履约后 30 天复购率。
- AI 单次服务毛利、打印单毛利、退款率和异常订单率。

## 四、一体机与小程序差异化

| 维度 | 微信小程序 | 一体机 |
|---|---|---|
| 核心角色 | 随身准备与决策端 | 现场服务与实体交付端 |
| 使用时长 | 多次、碎片化、跨天 | 单次、集中、尽快完成 |
| 使用环境 | 私密、个人设备 | 公共、多人轮换 |
| 优势输入 | 摄像头、微信文件、语音、定位、扫码 | ADF 扫描、U 盘、扫码器、大屏触控 |
| AI 深度 | 多轮修改、历史版本、长期任务 | 快速诊断、现场补齐、四步完成 |
| 文件管理 | 长期资产入口，按用户授权和 TTL 保存 | 临时会话处理，离场必须清场 |
| 打印 | 组装、报价、支付、选择服务点、查看状态 | 核验、释放、排队、出纸、异常处理 |
| 岗位/招聘会 | 碎片时间浏览、收藏、外部来源跳转 | 现场导览、官方二维码、材料打印 |
| 主动触达 | 微信订阅消息与站内消息 | 无法离场后触达 |
| 商业重点 | AI 服务、会员、材料包、复购 | 打印扫描、现场套餐、设备与点位服务 |

明确不做两端重复：

- 小程序不复制一体机的设备控制台、扫描仪控制、U 盘流程和公共终端帮助流程。
- 一体机不承载长时间私密面试训练、复杂版本管理和持续消息运营。
- 两端都不提供平台内投递、候选人推荐或企业收简历。

## 五、AI 求职操作系统设计

AI 操作系统不是“大模型聊天框”，而是六层可治理能力。

### 5.1 交互层：AI 主动但不打扰

AI 出现在三个位置：

1. **今天页**：基于真实状态给出 1 至 3 个下一步任务。
2. **全局小青入口**：用户随时用文字或语音表达意图。
3. **页内建议**：在简历、材料包、订单和招聘会页面给上下文建议。

不保留独立“AI 功能墙”。全屏对话页仍可存在，但它是深入处理方式，不是唯一入口。

### 5.2 意图层：说人话直达任务

示例：

| 用户表达 | 系统动作 |
|---|---|
| “帮我看看这份简历” | 打开最近简历，缺文件时进入上传 |
| “我要参加明天的招聘会” | 打开已收藏活动，生成行前材料清单 |
| “把我的简历打印五份” | 预选最近简历和份数，进入报价确认 |
| “练一下产品经理面试” | 创建本人模拟面试任务 |
| “比较这两个 Offer” | 进入受控 Offer 对比微应用 |

意图只映射到白名单动作。模型不能自由生成路由、外链、支付动作、打印指令或企业数据操作。

### 5.3 任务层：从功能入口升级为可恢复任务

任务类型首期包括：

- 准备简历。
- 准备面试。
- 准备招聘会。
- 整理求职材料。
- 到机打印。
- 处理订单异常。

每个任务必须具备：来源、当前步骤、真实状态、下一动作、关联资产、关联订单、过期时间和本人归属。第一阶段可以用现有业务对象聚合出任务视图；出现跨天恢复、多人协作或复杂编排需求后再评估独立 `JobTask` 模型，不能先建大而全任务平台。

### 5.4 资产层：所有结果都有归宿

AI 输出不能停在一次性结果页，必须进入以下一种本人资产：

- 简历版本。
- 我的文档。
- AI 报告。
- 材料包。
- 打印订单。
- 收藏与浏览记录。

AI 生成内容必须标注“AI 生成 / 仅供参考”，支持本人查看、继续处理、打印和删除；文件访问使用短时签名 URL，并执行保存期限策略。

### 5.5 能力层：受控微应用与技能

优先复用百宝箱 manifest 治理能力，为 manifest 增加 `surfaces` 和 `launchBySurface`，支持 `kiosk` 与 `miniprogram`。小程序通过公开、只读、按已发布状态实时过滤的目录接口获取可用能力，不建第二套脱离熔断机制的应用商店。

首批适合手机的低风险技能：

- Offer 对比。
- 薪资谈判话术。
- HR 常识问答。

合同审查、法律风险、试卷打印和外部技能继续受现有法务、版权、安全和发布 Gate 约束，不能因小程序重建而提前开放。

### 5.6 资源层：权益、成本和配额统一

每次 AI 调用必须明确：服务类型、模型、用户、任务、输入预算、输出预算、成本、是否收费、使用哪项权益、失败是否退回。运营日志不能直接作为计费账本。

权益分为：

- 数字权益：AI 次数、导出、模板、长期保存。
- 终端权益：打印页数、扫描次数、现场材料包折扣。
- 跨端权益：指定服务点、有效期和使用条件明确的赠送额度。

### 5.7 调度层：规则优先，模型兜底

“今天页”先用确定性规则生成任务卡：

| 真实状态 | 建议 | 主操作 |
|---|---|---|
| 没有简历 | 先建立第一份简历资产 | 上传或拍照 |
| 有简历、无诊断 | 检查影响投递准备的主要问题 | AI 诊断 |
| 有诊断、未优化 | 优先修正最重要的三处问题 | 继续优化 |
| 有待打印材料 | 材料已经可以下单 | 组装材料包 |
| 已付款、未到机 | 到机码尚未使用 | 出示到机码 |
| 权益即将过期 | 有权益将在七天内到期 | 查看权益 |

模型只在规则无结果时生成描述，且必须经过恒定合规守卫。按钮来自服务端白名单，模型不得生成按钮文本和执行参数。

## 六、小程序信息架构

### 6.1 四个底部 Tab

| Tab | 用户问题 | 核心内容 |
|---|---|---|
| 今天 | 我现在最该做什么 | AI 下一步、进行中任务、待到机订单、快捷提问 |
| 材料 | 我有哪些可以使用的成果 | 简历、文档、AI 报告、材料包、到机码 |
| 发现 | 我还能获得哪些机会和服务 | 岗位、招聘会、政策、线下机构、受控微应用 |
| 我的 | 我的账号和服务状态是什么 | 订单、权益、消息、反馈、设置、隐私与协议 |

“打印”和“AI”不单独占 Tab：打印是材料上的履约动作，AI 是覆盖全局的交互环境。

### 6.2 首页首屏

首屏保持工作台密度，不做营销落地页：

1. 当前问候与全局 AI 输入。
2. 最重要的一个下一步任务。
3. 进行中的订单或 AI 任务。
4. 最多两个次级建议。
5. 无真实状态时展示稳定基础动作，不生成假数据。

### 6.3 页面控制原则

- 首发不追求恢复 57 屏，围绕 8 至 12 条真实流程组织页面。
- 同一个业务对象只保留一个列表和一个详情入口。
- “我的”只做账户与服务入口，不重复聚合所有资产明细。
- 加载、空、错、无权限、待支付、待到机、处理中、已完成和异常状态必须完整。
- 手机触控目标不少于 48px，主操作不少于 56px。

## 七、功能规划

### 7.1 P0：首发必须形成的真实闭环

#### 身份与安全

- 微信一键登录，失败时支持短信验证码登录。
- 用户协议、隐私政策和版本化同意记录。
- 登录会话刷新、退出、敏感操作二次验证。
- 账号数据导出、注销和授权撤回沿用现有安全执行边界，不做前端假完成。

#### AI 简历与材料

- 从微信聊天文件、手机文件、相册或相机导入简历。
- PDF、DOCX、图片的真实解析和 OCR。
- AI 诊断、优化、前后对比、本人确认、模板预览和成果导出。
- 简历版本、我的文档和 AI 报告真实列表。
- 从本人资产组装打印材料包。
- 每个 AI 结果提供明确下一步：继续修改、加入材料包、下载或打印。

#### 手机下单与到机打印

- 选择单文件或材料包。
- 展示安全预览、页数、份数、单双面、纸张和当前终端真实支持的颜色能力。
- A4 是当前明确能力；不得假设 A3。
- 彩色能力由后端和 Agent 返回的终端能力决定，不硬编码打印机型号或未知 `mode` 值。
- 选择服务点或目标终端；没有真实坐标、在线状态或队列数据时不展示距离、空闲或预计等待时间。
- M2 首发服务点选择只读取 Admin 管理的终端名称、`terminalCode`、`locationLabel`、启用状态和真实心跳；`locationLabel` 为空的终端不得进入公开选择列表。未建立终端经纬度或终端与线下机构关系前，不按“附近”排序。
- 服务端报价、权益抵扣、优惠券、微信支付和 0 元订单统一落库。
- 支付成功后生成到机码，进入“已付款，待到机释放”。
- 到机后扫码或输入到机码，核验本人订单、支付状态、文件有效期、终端能力和幂等状态。
- 现场确认后才创建或释放可被 Agent claim 的 `PrintTask`。
- 手机端查看待到机、已释放、排队、打印中、已完成、失败、取消和退款状态。
- 订单异常可从原订单发起反馈，不新增孤立售后系统。

#### 公开信息与合规跳转

- 岗位、招聘会、企业、政策和线下服务机构的公开列表与详情。
- 来源名称、更新时间、外部 ID 和来源说明完整展示。
- 仅使用“去来源平台投递 / 扫码投递 / 去来源平台预约 / 扫码预约”。
- 只记录本人浏览、收藏和打开来源入口，不记录投递、预约或第三方处理结果。

#### 会员服务

- 我的订单、我的权益、消息通知、意见反馈、账户设置。
- 订单与权益空态必须诚实，不用 mock 伪造资产。
- 管理端继续复用现有 Admin，不新建一套“小程序后台”。

### 7.2 P1：形成手机独占价值

- 微信订阅消息：AI 任务完成、到机码待使用、订单状态变化、退款结果；逐场景单次授权，不做营销轰炸。
- 定位与导航：优先支持已有真实坐标的招聘会和线下服务机构；终端位置模型完成后再开放“附近终端”。
- 私密语音模拟面试：麦克风授权、ASR、分轮反馈、报告沉淀。
- 招聘会行前助手：展位、时间、材料清单、导航和官方来源入口。
- 职业规划、岗位匹配参考和求职任务连续推进。
- 首批低风险 AI 微应用在小程序投放。
- 小程序付费 AI 服务赠指定终端打印额度；终端首次履约赠数字诊断权益。

### 7.3 P2：规模化运营候选

- 经安全评审的 follow-me：在允许范围内选择任一服务点释放，不默认开放跨终端。
- 真实排队人数与预计等待时间。
- 材料包模板、招聘会现场服务包、校园就业季套餐。
- 会员订阅、家庭协助准备和授权分享。
- 更完整的 AI 资源管理、成本路由和运营实验。
- 合作机构聚合运营统计，但不给个人行为明细或简历数据。

## 八、手机下单到一体机打印的目标闭环

### 8.1 订单与任务必须分层

远程订单不能直接创建 `status=pending` 的打印任务，因为 Agent 会自动 claim 目标终端的 pending 任务，可能导致用户未到场就出纸。

推荐状态模型：

```text
手机草稿
  → 服务端报价
  → 待支付
  → 已支付、待到机释放
  → 到机核验
  → 已释放/已创建 PrintTask
  → 排队
  → 打印中
  → 已完成
```

异常分支：

```text
待支付 → 超时关闭
待到机释放 → 用户取消/自动过期 → 退款或权益返还
已释放 → 设备失败 → 人工核查/按规则退款
任意支付回调 → 幂等收敛，禁止重复扣款或重复出纸
```

M2 正式选择“到机前只有 Order 和材料资产，到机核验事务中再创建 PrintTask”，不采用“提前创建 `awaiting_release PrintTask`”方案。原因是现有 Agent 以 `pending + terminalId` 自动 claim，提前建任务会扩大误出纸风险。

该选择需要一组 additive Order 履约字段或等价的一对一履约记录，至少表达：`fulfillmentStatus=awaiting_release|released|expired|cancelled`、`releaseExpiresAt`、`releasedAt`、`releasedTerminalId`、`pickupCodeUsedAt`。`Order.printTaskId` 现已允许为空，可用于到机前订单；到机核验必须在一个事务中完成 pickupCode CAS、支付/退款状态复核、履约状态变更、目标终端绑定、PrintTask 创建和 Order 关联。SQLite/PostgreSQL schema、migration、共享类型、Admin、退款和 verify 必须同步，不能只改小程序或 controller。

### 8.2 到机核验

核验至少包括：

- 到机码存在、未过期、未使用。
- 订单属于本人或满足明确的匿名安全凭证规则。
- 支付状态允许履约，退款中和已退款绝不放行。
- 文件仍有效且哈希、归属、签名 URL 可重新生成。
- 当前终端启用、在线、生命周期为 active。
- 当前终端支持订单参数。
- 同一到机码并发只允许一次成功。

跨系统失败必须按以下补偿口径收敛：

- 材料包锁定、页数/价格快照和远程 Order 创建任一步失败时，不产生可支付订单，材料包恢复可编辑或明确进入可重试状态。
- 支付成功后若文件过期、材料包损坏或终端能力不满足，不能创建 PrintTask；履约进入可审计失败态并按真实渠道退款或返还权益。
- 到机 release 事务失败时保持 `awaiting_release`，pickupCode 不得标记已使用；用户可在同一终端幂等重试。
- PrintTask 已创建但响应丢失时，以 Order/pickupCode 幂等键返回同一个任务，禁止重复创建和重复出纸。
- 已进入打印中的硬件失败不得自动换终端重派，必须根据 Agent 的真实出纸证据进入人工核查。

### 8.3 等待与状态体验

小程序必须把“等待”设计成可理解、可恢复的状态：

| 状态 | 用户文案 | 允许操作 |
|---|---|---|
| 待支付 | 完成支付后生成到机码 | 支付、取消 |
| 待到机 | 已付款，尚未打印 | 查看到机码、导航、取消规则 |
| 已释放 | 已在本机确认，等待进入队列 | 查看当前终端、联系客服 |
| 排队中 | 前方任务数以真实数据为准 | 查看状态，不重复提交 |
| 打印中 | 终端正在处理 | 保持等待、查看帮助 |
| 已完成 | 终端已回传出纸完成 | 查看订单、再次发起、反馈 |
| 异常 | 需要核查，未确认出纸 | 反馈、退款说明 |

第一版使用有条件轮询即可；只有确有实时性收益时再引入 SSE 或 WebSocket。没有真实队列数据时只显示阶段，不伪造分钟数。

M2 首发时间规则固定为：

- 待支付订单 15 分钟未完成支付则关闭，不生成到机码。
- 已支付待到机订单默认 24 小时有效；页面在支付前明确展示到期时间和“尚未打印、需到机释放”。试点期只允许 Admin 在 2 至 48 小时内配置，不允许前端决定。
- 订单关联的敏感文件必须按本次明确履约目的获得用户确认，并至少保留到 `releaseExpiresAt`；到期后进入既有文件清理策略，不能因复制文件而降低敏感等级。
- 未释放前用户主动取消或到期时，真实支付原路全额退款，权益订单原路返还权益，0 元订单直接关闭；所有动作幂等、落库并可对账。
- 到机已释放后不允许自动取消或自动退款；若未确认出纸或设备失败，进入售后核查，再按真实打印事件和退款规则处理。

## 九、商业模式与产品包装

### 9.1 B2C 收入

| 产品 | 收费对象 | 说明 |
|---|---|---|
| 单次 AI 服务 | 诊断、优化、模拟面试、职业规划 | 收工具与成果服务费，不收招聘结果费 |
| 成果导出 | PDF、图片、结构化文档、长期保存 | 同一未修改成果不重复扣同一导出权益 |
| 打印订单 | 页数、份数、单双面、真实颜色能力 | 由服务端计价，支付与任务状态分离 |
| 求职材料包 | 多份材料准备与一次到机履约 | 比单文件打印更能体现求职服务价值 |
| 会员权益 | 数字权益与终端权益组合 | 必须有明确额度、期限和退款规则 |
| 招聘会现场包 | 行前清单、材料包、现场打印 | 不包含投递或录用承诺 |

### 9.2 B2B2C 收入

- 终端设备服务费、点位服务费和运维费。
- SaaS 账号与运营模块订阅。
- AI 工具用量和打印耗材结算。
- 学校、人社大厅和招聘会的现场材料服务包。
- 企业赞助打印券或品牌露出，但企业不得获得简历、个人画像或投递结果。

在取得必要许可和法务确认前，不对岗位、招聘会、招聘内容曝光、外部投递跳转或招聘效果收费。

### 9.3 免费与付费边界

建议采用“免费建立信任，付费获得成品和履约”：

- 免费：公开信息浏览、来源跳转、基础简历检查预览、订单与资产管理。
- 付费或权益：深度优化、完整报告、成果导出、长期保存、材料包和打印。
- 所有价格由后台配置和服务端报价决定，本方案不写死具体金额。

### 9.4 单位经济必须可见

后台至少能核算：

- AI 服务收入、模型成本和毛利。
- 打印收入、耗材估算、支付通道费和退款损失。
- 每个点位的订单数、完成率、异常率和单机贡献毛利。
- 小程序获客到到机履约的转化漏斗。
- 权益预占、履约、提交和返还，不使用 best-effort 日志计费。

### 9.5 获客、留存与双向导流

首发不购买泛流量，优先依托已有实体场景获取高意向用户：

- 一体机完成服务后，用户扫码把本人简历、订单或报告存入小程序；公共终端不得在未授权时自动绑定。
- 学校、人社大厅、招聘会主办方通过官方服务通知、现场物料和工作人员引导进入小程序。
- 小程序用户完成 AI 准备后获得明确的“到指定服务点打印”动作，把数字服务导向实体履约。
- 打印完成后只基于本人服务状态推荐下一步，例如保存成果、再次打印或继续面试准备，不推送投递和招聘结果内容。

留存机制不是签到和无关积分，而是四个真实理由：资产还在、任务可继续、订单可追踪、权益可使用。微信订阅消息只承担用户明确订阅的服务通知，不用作无差别营销渠道。

### 9.6 首发市场与试点方法

建议先选一个城市、一个主要场景和 1 至 3 台稳定终端验证，不同时铺学校、人社大厅和招聘会三种运营模型。

推荐首发顺序：

1. **校园就业服务点**：用户密度高、简历和打印需求明确，便于观察跨端转化。
2. **招聘会现场**：需求强但波峰明显，适合验证材料包和设备吞吐，不适合单独判断长期留存。
3. **人社或公共就业服务大厅**：社会价值高、用户结构复杂，须在流程稳定和工作人员培训完成后扩展。

每个试点至少连续观察 4 周，并在扩点前回答：

- 小程序是否显著减少一体机现场操作时长。
- 付款后不到机比例是否在可接受范围内，取消和退款规则是否清晰。
- 每台终端的真实完成订单和贡献毛利是否增长。
- AI 成本、支付费、耗材、退款和人工售后相加后是否仍有正毛利。
- 用户是否因为必须到机而感到受骗；下单前是否充分说明“尚未打印、需到机释放”。

未形成正向证据前，不扩大硬件采购、不铺设大量点位、不上线复杂会员年卡。

## 十、安全、隐私与合规

### 10.1 招聘合规

- 不开发平台内一键投递、收简历给企业、候选人筛选、面试邀约、Offer 管理、候选人推荐或企业直收简历。
- 岗位和招聘会只能是已审核的第三方或官方来源信息入口。
- 不记录外部投递、预约、签到或第三方办理结果。
- AI 可以帮助本人理解岗位和准备材料，但不能代投、承诺录用或向企业回传结果。

### 10.2 文件与个人信息

- 简历、扫描件、证件材料和 AI 报告默认私有。
- 文件访问使用短时签名 URL；高敏材料执行更短 TTL。
- 微信 OpenID、手机号、会员 ID 和文件归属只在服务端绑定。
- 小程序不得把用户简历放进日志、埋点、客服消息或第三方分析 SDK。
- 用户可查看保存期限，并按现有能力申请导出、删除和撤回授权。

### 10.3 支付与打印

- 微信支付 AppSecret、商户密钥和证书只存服务端。
- 报价、优惠、权益和最终应付金额以服务端为准。
- 支付、退款、权益核销和到机释放都必须幂等、可审计、可对账。
- 打印机名称来自终端配置 `printerName`，禁止硬编码型号。
- 不假设 A3，不假设奔图开放 API 的彩色 `mode` 值。

### 10.4 微信平台

- 小程序类目、隐私保护指引、用户协议、服务内容和支付商品描述必须一致。
- request、uploadFile、downloadFile 和 web-view 域名必须使用备案 HTTPS 域名并在公众平台配置。
- 订阅消息逐场景申请，用户拒绝后不阻断主流程。
- 正式 AppID、AppSecret、商户凭证和私钥不得进入 Git。

## 十一、技术方案

### 11.1 前端选型

> **⚠️ 本小节已失效（2026-09-02 补注）。**下面这段技术选型是当时的**方案候选**，已被
> [Gate 0 决策确认单](./miniprogram-gate0-decision-confirmation-2026-08-07.md) **D3**「原生微信小程序渐进演进，
> 不迁移 Taro 4」否决。现行口径：`apps/miniapp/` 为原生微信小程序，纯 JavaScript / WXML / WXSS，无构建，
> 运行时零 npm 依赖（依据 `apps/miniapp/package.json` 无 `dependencies`，以及
> `apps/miniapp/scripts/verify-miniapp-static.mjs` 中锁死空依赖的静态门禁）。
> 原文保留，是为了留下当时选 Taro 的理由；**不得据此开发或做依赖审计计划**。
> 末段「Taro 依赖必须重新审计」一并失效——当前没有 Taro 依赖树可审计，对应的约束已由静态门禁承担。

采用 Taro 4 + React + TypeScript，微信小程序首发，暂不承诺支付宝同步发布。理由：

- 与现有 React/TypeScript 团队和共享契约一致。
- 旧 Wave 0 分支已有可审查的工程基线。
- 可复用 `packages/shared` 类型、状态机和纯函数。
- 比重新维护一套原生 JavaScript 更容易实施 CI、类型检查和跨端契约治理。

Taro 依赖必须重新审计，旧分支曾有 CLI 间接依赖风险，不能直接复制旧 lockfile 或把旧审计结论视为当前结论。

### 11.2 API 原则

- 复用现有业务 API，不为小程序复制第二套支付、文件、AI 或会员服务。
- 小程序需要不同响应形状时，新增薄 BFF/adapter 或共享 view DTO，不在前端拼装敏感状态。
- 跨端状态机和能力枚举放 `packages/shared`。
- 所有写操作由服务端根据本人身份和真实对象补齐，不信任前端传入价格、文件归属、来源信息或终端状态。

### 11.3 需要复核或新增的服务能力

| 能力 | 当前判断 | 开发动作 |
|---|---|---|
| 微信登录 | 后端已存在 | 复核生产配置与真机授权 |
| 会员资产 | 已有多组 `/me/*` API | 建小程序 adapter，补页面契约测试 |
| AI 简历/OCR/面试/规划 | 后端主体已有 | 按小程序输入方式接线，统一用量与权益 |
| 支付退款 | 代码底座已有 | 补 JSAPI 小程序下单参数与生产商户验收 |
| 材料包 | 仅基础表 | 重做本人材料包模型、服务、报价与版本快照 |
| 远程待释放订单 | 现有建单路径同时创建 Order + PrintTask | 采用 Order-only 待释放路径，新增 additive 履约字段/记录和 migration，到机事务才创建 PrintTask |
| 到机码 claim | 文档与当前代码存在漂移，当前 `services/api/src` 无实现 | Gate 0 从干净 main 复核；仍缺失则作为 M2 必做端点新增，不再列为模糊复核项 |
| 终端位置 | 当前终端模型不具备可靠坐标关系 | 先显示服务点，后补位置模型与真实导航 |
| 微信订阅消息 | 未形成闭环 | 新增授权记录、模板发送、频控和退订边界 |
| AI 下一步引擎 | 未实现 | 规则优先聚合接口，模型仅作受控兜底 |
| 微应用投放面 | 当前偏 Kiosk | manifest 增量支持 miniprogram surface |
| 统一权益分账 | 现有权益维度不足 | 出现首个跨端套餐时再做最小增量模型 |

## 十二、运营后台

在现有 Admin 内增加或复用以下能力，不新建“小程序管理后台”：

- 小程序发布配置：版本、开关、最低支持版本、法务版本。
- 首页任务规则与合规文案配置，但恒定红线不能被后台关闭。
- AI 服务定价、模型、配额、成本和熔断。
- 材料包与套餐配置。
- 远程订单、到机释放、打印进度、异常与退款。
- 微信订阅消息模板、发送结果和频控。
- 小程序微应用投放面和熔断。
- 转化漏斗、点位履约和单位经济指标。

Partner 只能看到本机构对象和满足最小样本阈值的聚合统计，不得看到个人简历、AI 报告、用户行为明细或“谁看过岗位”。

## 十三、分阶段开发路线

### Gate 0：事实冻结与工程恢复

- §十七的产品名称、四 Tab、首发阶段、选定终端履约和微信主体五项必须由用户明确确认；未确认不能通过 Gate 0 或开始 M0 页面开发。
- 等当前生产混合版本故障恢复完成，从干净 `main` 建 `codex/` 分支或独立 worktree。
- 盘点旧 Taro 分支、原型、主干 API 与生产端点，只选择性提取资产。
- 精确核验 `claim-pickup`、远程 Order-only 建单、JSAPI 支付、材料包和终端服务点数据源；把缺失项写入 M2 契约清单。
- 冻结小程序 P0 路由、共享契约、状态机和文件预算。
- 在 `apps/miniapp/` 建唯一源码，接入 workspace、CI、lint、typecheck、test、build 和合规门禁。
- 对 Taro CLI、构建链和新增依赖重新执行依赖树审查与 `pnpm audit`；旧分支的 lockfile、override 和审计结论不得直接继承。
- 现有合规门禁必须显式扫描 `apps/miniapp/src`，并加入小程序专用来源按钮、AI 生成标识、外链白名单和“无真实回流不显示已打印”负向用例。
- 在 M1 期间先提交微信订阅消息模板和隐私声明材料，等待平台审核；代码接线仍留在 M3，避免到 M3 才开始等待外部审批。
- 发布前不接真实生产密钥，不修改生产数据库。

### Phase M0：可登录的真实 Shell

- 四 Tab、全局错误边界、环境配置和发布守卫。
- 微信登录、短信降级、协议与隐私。
- 公开岗位、招聘会、政策和来源跳转。
- 我的订单、权益、消息和反馈只读闭环。

验收：开发者工具、真机预览、合法域名、登录授权、空错态、合规文案和生产构建守卫全部通过。

### Phase M1：AI 操作系统 MVP

- 今天页规则引擎。
- 全局小青意图入口与按端路由映射。
- 简历上传、OCR、诊断、优化和成果资产。
- 材料页与 AI 结果下一步。

验收：上传到诊断不超过 3 个主步骤；已有简历说一句话可直达目标流程；所有成果进入本人资产。

### Phase M2：下单到到机打印

- 材料包拆为四个可独立验收的子任务：本人材料包与条目快照模型；创建/编辑/删除/锁定 API；服务端页数与价格快照；与远程订单、到机 release 和文件 TTL 的事务集成。
- JSAPI 微信支付：服务端使用本人 OpenID 获取 `prepay_id`，生成小程序 `wx.requestPayment` 所需签名参数；验证 AppID 与商户号绑定、回调验签、查单、退款和 1 分钱 live 冒烟，不复用 Native/H5 支付参数冒充小程序支付。
- Order-only 待到机释放状态、24 小时默认有效期、到机码、Kiosk 核验页和原子 release；对应 additive migration、双 schema、共享类型和 Admin 必须同批完成。
- 若 Gate 0 确认主干仍无 `POST /print/jobs/claim-pickup`，本阶段新增端点并覆盖限流、枚举防爆破、CAS 并发、支付/退款门控、过期、错终端、重复使用和审计。
- Agent 安全 claim、真实状态回流、异常、取消和退款。
- 一台 Windows 主机与真实奔图设备完成端到端真机验收；证据清单固定记录 Windows 版本、Agent 构建/提交、驱动与固件版本、网络拓扑、Admin 终端 ID、配置项 `printerName`、系统实际识别的打印队列名称、订单/任务 ID 和回流事件。代码仍只使用可配置 `printerName`，不得硬编码型号；彩色 mode 未经厂家确认前不得在验收脚本中假定为 `"color"`。

验收：JSAPI 真实小额支付与原路退款通过；手机下单付款后绝不提前出纸；并发输码只成功一次；到机确认后打印；完成状态来自 Agent；待到机到期自动退款/返还权益；失败不重复扣款、不自动重复出纸。

### Phase M3：手机独占能力

- 订阅消息、定位与导航。
- 私密语音模拟面试。
- 招聘会行前助手。
- 跨端权益激励。

### Phase M4：微应用与商业运营

- 小程序 surface、低风险 AI 技能货架。
- 会员产品、现场套餐和单位经济看板。
- 在法务、安全和真实运营数据支持下逐项扩展，不一次上线全部候选能力。

## 十四、验收标准

### 产品

- 用户不理解系统结构也能从“今天”完成下一步。
- 小程序没有复制 Kiosk 设备控制入口。
- 8 至 12 条核心流程全部有加载、空、错、取消、恢复和完成状态。
- AI 结果、订单和文件都有明确归属，不产生孤立结果页。

### 商业

- 可以按服务和点位核算收入、成本、毛利、退款和异常。
- 小程序到到机履约漏斗可观测。
- 免费、单次、材料包和会员权益边界清晰。
- 不以招聘结果或招聘内容曝光收费。

### 技术

- 小程序只有一个正式源码目录。
- typecheck、lint、unit test、微信 build、合规 verify 和发布配置守卫进入 CI。
- API、共享契约、数据库 migration、Kiosk、Agent 和真机验证按风险分层完成。
- 不读取生产密钥做本地构建，不将真实用户文件写入测试夹具。
- `apps/miniapp/src` 已进入合规、依赖安全和发布配置门禁；JSAPI、订阅消息和远程履约不能只靠 mock 或静态测试宣称完成。

### 履约

- 远程订单在到机前不可被 Agent claim。
- 到机释放、支付回调、退款和状态回传全部幂等。
- 没有真实 Agent 回流不显示“已打印”。
- 没有真实位置、在线和队列数据不展示“附近、空闲、预计等待”。

### 合规与隐私

- 合规按钮与来源展示通过静态和浏览器门禁。
- 不存在平台内投递、简历回传企业或候选人管理接口。
- 文件签名 URL、TTL、本人隔离、管理员访问审计和删除策略通过验证。
- 微信登录、支付、订阅消息和隐私授权通过真机与平台审核要求。

## 十五、主要风险与止损条件

| 风险 | 预防措施 | 止损条件 |
|---|---|---|
| 再次出现双源码 | `apps/miniapp/` 唯一真源，CI 与发布均从主仓生成 | 发现独立副本产生功能提交时暂停发布并收敛 |
| 付款后不到机 | 下单前明确到机要求，设置有效期、取消和退款规则 | 不到机率长期过高时暂停预付，改为到机后支付试验 |
| 远程误出纸 | 到机前不创建 Agent 可 claim 的任务 | 出现任何未到机出纸事件立即关闭远程下单 |
| AI 成本失控 | 配额、预算、缓存、模型路由和独立计费账本 | 单项服务持续负毛利且无法提价时下架或降级 |
| 设备吞吐不足 | 真实队列、耗材告警、点位容量和异常 SOP | 高峰失败率超过试点门槛时停止引流并先扩容/修复 |
| 招聘合规越界 | 来源治理、恒定文案守卫、法务 Gate | 出现平台收简历、结果回流或无许可招聘收费立即下线 |
| 隐私泄露 | 本人隔离、短签名 URL、TTL、审计和最小埋点 | 发生高敏文件或身份泄露时停止相关服务并进入事件响应 |
| 页面堆砌 | 以真实流程和对象为单位，首发 8 至 12 条流程 | 新页面无数据、无状态机、无商业或履约价值时不开发 |

## 十六、明确不做

- 不恢复全部旧原型页面作为首发目标。
- 不维护独立于 monorepo 的第二份小程序源码。
- 不接微信云开发作为第二套后端。
- 不做公网远程直控打印机。
- 不在没有真实终端坐标时展示假距离。
- 不把 AI 自由文本直接变成支付、打印、外链或数据写入动作。
- 不新建第二套支付、会员、订单、文件、通知或运营后台。
- 不开发任何招聘闭环功能。
- 不在生产故障恢复与统一部署完成前并行修改生产环境。

## 十七、立项前需要用户确认的决策

1. 产品名称是否继续使用“职易达 / 智达”，还是统一为现有终端品牌名称。
2. 首发是否接受四 Tab：“今天 / 材料 / 发现 / 我的”。
3. 首发商业范围是否按 M0 至 M2，先完成 AI 简历、材料包、支付和到机打印，再上语音与位置能力。
4. 到机履约首发是否只支持下单时选定终端；跨终端 follow-me 保持 P2。
5. 小程序首次发布主体、正式 AppID、微信支付商户号和类目是否已经具备。

上述五项是 Gate 0 的前置阻塞条件。未确认前只能继续做只读 API 审计和旧资产盘点，不能建立正式路由、Tab、AppID 配置或进入 M0 页面开发。

一句话结论：

> **小程序负责让用户随时准备好，一体机负责在关键地点交付成果；AI 负责把两端能力编排成一条可理解、可支付、可履约、可复购的求职服务链。**
