# 小程序功能重构方案:从「一体机缩小版」到「AI求职操作系统随身 Shell」

- 文档状态:**方案草案,待用户确认**(2026-08-01)
- 上游依据:`docs/product/miniprogram-vs-kiosk-differentiation-strategy-2026-07.md`、`docs/product/miniprogram-phase-a-prototype-changelist-2026-07.md`、`docs/product/toolbox-micro-app-platform.md`、`docs/compliance/compliance-boundary.md`
- 小程序代码位置:`~/WeChatProjects/zhiyida`(独立 repo,分支 `feature/miniapp-proto-pages`)

## 0. 必须先说清的一件事

**「AI求职操作系统」这个定位目前不存在于本仓库任何文档中。** 我全文检索过 `docs/`,所有「操作系统」命中都指 Windows OS,`求职操作系统` / `求职 OS` / `JobOS` 零命中。

所以本方案**不是**对既有规格的复述,而是从**已落地资产**反推出的定位定义。如果方案通过,第一件事应该是把 §1 的定位写进 `docs/product/feature-scope.md` 与 `CLAUDE.md §1`——否则下一个模型/设备接手时仍会按「AI求职打印服务终端」理解项目,产生系统性偏差。

**第二件事(2026-08-01 修订新增)。** 本方案 v1 通篇在讲「AI 怎么驱动」,却始终没有回答一个更基础的问题:**为什么这件事必须在手机上做?** 如果小程序做的每一件事一体机都能做,它就只是缩水版终端,再多的 AI 也救不回来。核验证实这不是假想的风险,而是当前的事实——**全仓 334 次 `wx.*` 调用里 81.1% 是导航和 toast,手机最值钱的四个能力(定位 / 订阅消息 / 扫码 / 麦克风)一个都没接**。新增的 §4.5 专门回答这个问题,tabBar 与路线图的结论都建立在它之上。

## 1. 定位升级的实质:两个内核,不是一个

「AI求职操作系统」有两层内核,缺任何一层都不成立:

| | 交互内核(用户视角) | 治理内核(后台视角) |
|---|---|---|
| 回答的问题 | 用户**怎么用** | 能力**怎么管** |
| 内容 | AI 主动开口 / 意图直达 / 步骤压缩 / 优雅收尾 | 装载 / 授权 / 调度 / 下架 |
| 现状 | ❌ **几乎为零**(仅有被动意图路由) | ✅ **已建完**(百宝箱平台) |

**这是本方案最重要的判断:你缺的不是治理内核,是交互内核。**

治理内核已经很完整(§2.1),但它是给管理员的。用户打开小程序时感受不到任何"操作系统"——看到的还是一堆功能卡片,得自己想清楚要干什么、自己找入口、自己一步步点。

### 1.1 交互内核:AI 原生的四条判据

一个真正 AI 原生的求职 OS,必须同时满足:

**① AI 主动开口** —— 不是等用户找 AI,是 AI 先说话。用户不知道做什么时,系统给出**基于真实状态**的下一步,而不是一句"请问有什么可以帮您"。

**② 意图直达** —— 用户说人话,系统直接到位,不让用户在菜单里翻。「我想打印简历」应该直接进到可打印状态,不是先教他"请点打印 → 再点上传 → 再选参数"。

**③ 步骤压缩** —— 用最少的步骤做最多的事。能预填的不问、能批量的不逐个、能一次授权的不反复确认、能后台跑的不让用户等。

**④ 优雅收尾** —— 结果要好看、可用、可带走。不是给一堆原始输出让用户自己整理,而是交付成品:排好版的 PDF、可直接打印的材料包、一句话说清结论的报告。

### 1.2 由此推出的四层变化

| 维度 | 打印服务终端 | AI求职操作系统 |
|------|-------------|---------------|
| 产品单位 | 功能模块(简历/打印/岗位/招聘会) | **对象**(任务 / 资产 / 权益 / 微应用) |
| 交付方式 | 用户进入功能页,自己操作 | **AI 主动调度能力**去达成用户目标 |
| 扩展方式 | 加页面、加入口 | **加微应用**(manifest 描述 → 审核 → 投放) |
| 小程序角色 | 一体机的移动版 | OS 的**随身 Shell** |
| AI 的位置 | 一个功能 tab | **交互层,无处不在** |

最后一行是本次修订的核心:**AI 如果是一个 tab,用户就必须先想到"我要找 AI",那仍然是菜单式产品。** AI 必须是环境,不是目的地。

## 2. 现状核验:哪些已经是 OS,哪些还不是

以下结论均经源码核验(非文档转述)。

### 2.1 已经是 OS 内核的部分 ✅

**百宝箱微应用平台 = 事实上的 OS 内核。** 它不是一个页面,是一套受控能力装载机制:

- 数据层:`ToolboxApp` / `ToolboxAppVersion`(带 `snapshotJson` manifest 快照 + `@@unique([appId, version])`)/ `ToolboxAllowedHost` / `ToolboxLaunchEvent`(匿名)+ `TerminalToolboxConfig`
- manifest 类型:`packages/shared/src/types/toolboxMicroApp.ts` —— 5 种 `entryType`(`internal_route` / `web_app` / `qr_code` / `mini_program_qr` / `ai_skill`)、11 项 `permissions`、4 级 `riskLevel`、8 种 `status`、`dataPolicy`
- 治理:`toolbox-governance.ts` 真状态机 + 双人复核强制 + 14 条发布阻断原因;`toolbox-policy.ts` 合规正则带 **NFKC 归一化**(防同形字绕过)
- 投放与安全:`publishVersion` 按终端增量 upsert(mutex 保护);`evaluateToolboxHost` 强制 https + 阻断内网 IP;`suspendApp` 熔断后从**所有**终端移除
- 审计:`admin-toolbox.controller.ts` 13 个端点全部写 AuditLog diff;7 套 verify 脚本进 CI

**其它已真实的底座:** 78 个 Prisma 模型覆盖 20 个业务域;支付域 C5-1~C5-6 + W-A/W-B/W-C 全部合入 main,7 套支付 verify 进 CI;到机码真实可用(`Order.pickupCode @unique` + CAS 唯一生成 + `pickupCodeVisibleFor` 可见性门控 + Kiosk `PickupCodePanel.tsx`);AI 层有 `AiProvider` 抽象 + 7 个按功能的模型配置 + **确定性正则意图路由**(非模型路由)。

### 2.2 还不是 OS 的部分 ❌

**a. 货架是空的。** 7 个内置微应用 `status` **全部是 `planned`**——平台建好了,一个应用都没上架。其中 5 个是 `ai_skill`(offer-compare / salary-negotiation / hr-qa / legal-risk-check / contract-review),1 个 `qr_code`(exam-paper-print),1 个 `mini_program_qr`(english-mock-practice)。

> 注意这 5 个 `ai_skill` **全是纯数字能力、手机就能用**。货架的天然首发地是小程序,不是一体机。

**b. 整条发布链是「按终端形状」建的,小程序面没有投放目标。** 这比"缺一个字段"严重,核验如下:

- manifest 只有 `entryType`,无 `surfaces`
- 投影函数就叫 `snapshotToKioskToolboxItem`——名字本身说明它只面向 Kiosk
- `TerminalToolboxConfig.terminalId @unique`,一终端一行;`publishVersion:343` 靠 `for (const terminalId of targetTerminalIds)` 遍历投放
- **手机不是终端**,所以小程序面在现有模型里根本没有落点

结果:小程序侧零微应用,且不是"没做",而是"没有可投放的地方"。

**c. 微信登录:前端已备好,后端零实现。** 后端所有 `wechat` 命中都是微信**支付**;会员认证只有短信 OTP + 扫码(`services/api/src/member-auth/member-auth.controller.ts` 11 个端点)。

小程序侧其实已经接线到位:`utils/auth.js` 有 `wx.login` 封装,`utils/api.js:67-76` 已把 `POST /auth/wx-phone` 写进 facade 且注释明确「绝不在前端解密手机号」,`pages/launch/launch.js:23` 留 TODO 等后端。当前卡在 `utils/config.js` 的 `USE_MOCK: true` + 占位 `baseUrl: 'https://api.example.com'`。

**即:缺口是纯后端的一个端点,前端不需要重做。**(原写「+ 一个备案域名」已更正 —— `zyidai.cn` 早已备案上 HTTPS 并在服务,见 §10.1。)

**d. 材料包 Bundle 是空表。** `PrintMaterialPack` 由迁移 `20260717151246_foundation_batch0` 建出,**业务代码零引用**,Admin 标 `implemented: false`,只活在原型 `05b-bundle.html`。而它正是差异化策略三机制里的核心产品对象。

**e. 权益分账维度缺失。** `BenefitGrant` 只有 `benefitType`,**没有** scope / channel / terminal / digital 任何一个字段。「数字权益 vs 终端权益分账」只做了一半。

**f. 交互内核:意图直达有地基,主动开口零实现。** 对照 §1.1 四条判据逐项核验:

| 判据 | 现状 | 证据 |
|------|------|------|
| ① AI 主动开口 | ❌ **零实现** | 全仓 `recommend`/`nextAction`/`proactive` 无一命中主动引导;`suggestion` 命中全是内容级(如 `llm-job-fit.service.ts:74` 的简历差距建议),不是 UI 引导 |
| ② 意图直达 | ⚠️ **有地基,仅被动** | `llm-chat.service.ts:39-68` 有 `INTENT_ROUTES`(意图→可点 route)+ `INTENT_RULES`(5 条正则)+ `SKILL_ACTIONS`;但必须用户先开口才触发 |
| ③ 步骤压缩 | ⚠️ 局部有 | 简历四步流、材料包(未实现)是压缩思路;但无跨功能预填、无批量、无一次授权 |
| ④ 优雅收尾 | ⚠️ 局部有 | 简历 PDF / 职业规划 PDF 有成品导出;但多数 AI 结果仍是原始文本 |

值得注意的好消息:manifest 的 `ai_skill` 已经带 `assistantIntent` 字段(`toolboxMicroApp.ts:165`,5 个内置技能各有其值如 `offer_compare` / `salary_negotiation`),且 `verify-toolbox-micro-app-platform.ts:150` 强制校验「`ai_skill` 必须配 `assistantIntent`」。**也就是说微应用天生就是"可被 AI 调起的能力",接线基础已经在了。**

小程序侧 `pages/ai/ai.js` 目前只是工具网格 + 聊天入口(`tapTool` / `tapChat` / `tapRecord`),没有主动引导。

**g. AI 用量三线各自为政。** `AiServiceLog` 只有 3 个 service 在写——`mock-interview` 和 `career-plan` **消耗真实模型但不记账**;配额只有 job-ai 一条(Redis 三维 member20/terminal100/ip60);计费在 AI 层之外。**OS 缺一个资源管理器。**

### 2.3 最大的战略错配

小程序 57 屏 = 功能菜单平铺,本质是一体机的等比缩小。tabBar 现状最能说明问题:

```
首页 / 打印 / 求职 / AI / 我的
       ↑                ↑
   设备 I/O 动作      技术实现名
```

**「打印」和「AI」都不是 OS 对象**——一个是设备 I/O 动作,一个是技术栈。Shell 应该暴露对象,而不是暴露实现。

**而且"等比缩小"不只是信息架构层面的判断,在代码层面已经成立:** 81.1% 的 `wx.*` 调用是导航与 toast,手机独占能力接线率接近零(§4.5.1)。也就是说,当前小程序**在技术上真的只是一层把 Kiosk 功能表搬到手机的跳转壳**。这一条是 §4.5 存在的直接理由。

## 3. 设计原则(六条,后续所有取舍以此为准)

0. **AI 是交互层,不是功能模块。**(最高优先级,与其它原则冲突时以此为准)每个页面都应回答"AI 在这里能替用户省掉什么",而不是"这里要不要加个 AI 按钮"。AI 主动开口优先于用户主动寻找。
1. **小程序是 Shell,不是 App。** 职责是:暴露 OS 对象、调度任务、管理配额。不为每个功能做一个入口。
2. **信息架构从对象模型推导,禁止沿用一体机菜单。** 这是对 2026-07 差异化策略已识别误区的直接修正。
3. **渠道分工不动摇。** 小程序负责把用户「准备好」,一体机负责在关键地点、关键时刻「交付成果」。任何让小程序自成闭环、绕开一体机的设计一律否决——那会让一体机退化成低频低毛利的普通打印机。
4. **新能力优先做成微应用 manifest,而不是小程序专属页面。** 一次投入,多端复用,自动继承审核/白名单/熔断/统计。
5. **不伪造能力优先于视觉完整。** 没有真实回流不显示「已打印」,没有真实设备数据不显示「设备正常」。

## 4. 对象模型:小程序该暴露什么

| OS 概念 | 本项目对象 | 当前状态 |
|---------|-----------|---------|
| 进程 / 任务 | **求职任务**(准备简历 / 备面 / 发现机会 / 到机履约)——长周期、可恢复 | ❌ 无模型,首页仍是板块并列 |
| 文件系统 | **求职资产**(简历版本 / 文档 / AI 报告 / 材料包) | ⚠️ 文件与 AI 结果有,**材料包缺** |
| 权限 / 配额 | **统一权益账本** | ⚠️ 有表,**缺分账维度** |
| 应用层 | **百宝箱微应用** | ⚠️ 平台完整,**货架全空** |
| 设备 I/O | **一体机履约**(到机码 / 出纸 / 扫描) | ✅ 到机码真实可用 |
| Shell | 一体机=现场 Shell,小程序=随身 Shell | ⚠️ 小程序仍是菜单 |
| 调度器 | 通知 / 提醒 / 复访 | ⚠️ 7 张通知表,未按任务编排 |

## 4.5 手机独占能力:小程序凭什么独立存在

> 本章为 2026-08-01 三模型并行评审后新增。此前本方案通篇在讲「AI 怎么驱动」,**没有回答「为什么这件事必须在手机上做」**——如果小程序做的事一体机都能做,它就只是缩水版终端,没有独立存在理由。

### 4.5.1 硬证据:小程序目前技术上就是一体机的缩小版

不是"感觉像",是 API 普查的结果。全仓(`pages/` + `utils/` + `components/` + `app.js`)`wx.*` 调用 **334 次**,分布如下:

| 类别 | 次数 | 占比 |
|------|------|------|
| 导航 + 提示(`showToast` 95 / `navigateTo` 66 / `switchTab` 59 / `navigateBack` 51) | **271** | **81.1%** |
| 其余全部(含手机独占能力) | 63 | 18.9% |

第 5 名开始就掉到 `getWindowInfo`(11 次)——那是取状态栏高度的样板代码,不是功能。

**手机独占能力的实际接线情况**(全仓核验):

| 能力 | API | 现状 |
|------|-----|------|
| 摄像头采集 | `wx.chooseMedia` | ✅ 已用 —— `pages/scan-doc/scan-doc.js:17,21` 分别取 `['camera']` / `['album']` |
| 微信聊天文件 | `wx.chooseMessageFile` | ✅ 3 处 —— `resume-upload.js:18`、`scan-relay.js:17` |
| 分享 | `onShareAppMessage` | ✅ 20 个文件 |
| 微信支付 | `wx.requestPayment` | ⚠️ 仅 1 处 |
| **定位** | `getLocation` / `chooseLocation` / `openLocation` | ❌ **零处** |
| **订阅消息** | `requestSubscribeMessage` | ❌ **零处** |
| **扫码** | `scanCode` | ❌ **零处**(但按钮白名单里有「扫码投递 / 扫码预约」) |
| **录音 / 音频** | `getRecorderManager` / `createInnerAudioContext` | ❌ **零处**(模拟面试的语音能力在手机端不存在) |
| 保存到相册 / 文件 | `saveImageToPhotosAlbum` / `saveFileToDisk` | ❌ 零处 |
| 剪贴板 | `getClipboardData` / `setClipboardData` | ❌ 零处 |

**结论:手机最值钱的四个能力(定位 / 订阅消息 / 扫码 / 麦克风)一个都没接。** 这是"缩小版"的技术根因。

### 4.5.2 能力盘点:手机独占 vs 一体机独占

**手机能做、27 寸一体机做不到的:**

| 手机独占 | 一体机为何做不到 | 求职场景真实价值 | 地基现状 |
|---------|---------------|----------------|---------|
| **主动触达**(订阅消息) | 用户离场即断连,屏幕留不住人 | **AI 主动开口的唯一物理通道** | ❌ 前后端全零(见 4.5.4) |
| **私密环境**(麦克风) | 公共场所,练面试 / 谈薪会被旁人听到 | 模拟面试口头练、薪酬推演——这是**体验级硬差异**,不是便利差异 | ❌ 零音频 API |
| **定位** | 一体机知道自己在哪,不知道用户在哪 | 找最近服务点、招聘会导航、判断通勤距离 | ⚠️ 见 4.5.4 陷阱一 |
| **随手采集**(摄像头) | 摄像头固定在场地,用户得跑过去 | 路上看到招牌 / 纸质简历 / 证书随手拍进系统 | ✅ 已接线 |
| **微信生态**(聊天文件 / 支付 / 分享) | 无微信上下文 | HR 微信发来的 JD 直接取用、材料分享给朋友看 | ⚠️ 部分接线 |
| **碎片时间** | 必须到场 | 通勤看岗位、睡前改简历、等叫号时练面试 | 天然具备 |
| **扫码** | 有扫码枪但用户不带着走 | 招聘会现场扫企业码 / 岗位码 | ❌ 零处 |

**一体机能做、手机做不到的(必须同时写清,否则会滑向"小程序自成闭环",违反设计原则 3):**

| 一体机独占 | 价值 |
|-----------|------|
| **物理出纸** | 彩色激光、A4、自动双面——手机永远打不出纸 |
| **ADF 批量扫描** | 50 页连续进稿,手机逐张拍摄不可替代 |
| 复印 | 证件、材料原件即时复制 |
| 大屏并排比对 | 27 寸竖屏可同屏对照多版简历 |
| 到机码核销出件 | 物理履约的终点 |
| 无需自带设备 | 用户没手机 / 没流量 / 手机没电时的兜底 |

**分工不变:手机 = 准备层 + 决策层 + 提醒层;一体机 = 物理履约层。投递不在任何一端闭环(合规红线)。**

### 4.5.3 AI × 手机能力融合矩阵

每条都标注用的是**已有能力**还是**需新建**,避免把方案写成许愿单。

| 功能 | 触发时机 | AI 做什么 | 省掉的步骤 | 用到的手机独占能力 | 依赖 |
|------|---------|----------|----------|-----------------|------|
| **随手拍纸质简历直接诊断** | 手上有纸质简历,不在一体机旁 | 百度 OCR(已有)→ 6 维诊断(已有)落库 | 原需专程到一体机 ADF 扫描 → 现在拍照即可 | 摄像头 | ✅ 全部已有,只需接线 |

### 4.5.4 三个实现陷阱(核验发现,三方评审都未完整覆盖)

**陷阱一:「看附近终端」现在不可实现——本方案 §7.1 规则表里就有这个洞。**

需要两个条件,**都不满足**:

| 条件 | 现状 |
|------|------|
| 手机侧取用户位置 | ❌ `getLocation` 全仓零处 |
| 后端有终端坐标 | ❌ `Terminal` 模型(`schema.prisma`)**只有 `locationLabel String?` 文本标签,无经纬度** |

而 `pages/print-store/print-store.js:7` 已经在展示 `dist: '1.2km'` —— **硬编码假距离**。`pages/home/home.js:56` 的 `tapTerminalAll` 是 `wx.showToast({ title: '终端地图即将上线' })` 占位。

处理口径:
- **可以先做的**:「最近的招聘会」「最近的线下服务点」—— `JobFair` 与 `OfflineAgency` 已有坐标,只缺手机侧 `getLocation`
- **需要 schema 改动才能做的**:「最近的一体机」—— 须给 `Terminal` 加坐标(或建 `Terminal` → `OfflineAgency` 关联,当前两者**零关联**)
- **接真之前**:`print-store` 的距离必须隐藏,不能显示假的 `1.2km`(§9 不伪造能力)
- 因此 §7.1 规则表中「有待打印文件 → 看附近终端」这条,**第一版主按钮应降级为「查看服务点」(不含距离)**,或等 `Terminal` 加坐标后再启用

**陷阱二:`INTENT_ROUTES` 的值是 Kiosk Web 路由,小程序不能直接用。**

`llm-chat.service.ts:39-46` 实际内容:

```
resume: '/resume/report' / '/resume/source'    print: '/print/upload' / '/scan/start'
job:    '/jobs'          fair: '/job-fairs'    policy: '/renshi'
```

这些是 Kiosk 的 Web 路由。小程序用 `pages/xxx/xxx`,`wx.navigateTo('/resume/report')` **会直接失败**。且小程序 `utils/api.js` 目前**零意图 / 助手 facade**,`utils/` 下也无任何路由映射层(已核验 8 个文件)。

所以 §7.2「复用已有 `INTENT_ROUTES`」必须补一层**面向端的路由映射**:后端按调用方 surface 返回对应路由,或在 `packages/shared` 维护 `intent → { kiosk, miniprogram }` 映射表。**这是复用的前置条件,不是可选优化。**

**陷阱三:小程序已在展示伪造的设备状态——这是当前最严重的合规违规,优先级高于任何新功能。**

CLAUDE.md §9 明文禁止:「没有真实数据、真实接口、**真实硬件状态**或真实保存结果时,页面不得展示已完成、已保存、已投递、已打印、**设备正常**等结论。」核验结果,小程序**四处违反**:

| 位置 | 伪造内容 | 严重度 |
|------|---------|-------|
| `pages/home/home.wxml:101` | 「距你 {{item.dist}} · **出纸正常**」—— 硬编码的**设备健康结论** | 🔴 直接违反「不得展示设备正常」 |
| `pages/home/home.wxml:104-105` + `home.js:21-22` | `online: true` 硬编码 → 渲染「● 在线」 | 🔴 伪造设备在线状态 |
| `pages/print-store/print-store.js:6-7` + `.wxml:35` | `idle: true` 硬编码 → 渲染「**机器空闲**」 | 🔴 伪造设备可用性 |
| `pages/print-store/print-store.js:6-7` | `dist: '320m'` / `'1.2km'` | 🟠 伪造距离(`getLocation` 零处,不可能算出来) |
| `pages/print-pickup/print-pickup.js:5` | `code: 'T7 9 4 2'` | 🟠 伪造到机码 |

**最讽刺的一处**:`print-store.wxml:22` 的提示文案写着「门店状态**以终端实时上报为准**」,而同页 `:35` 渲染的是硬编码 `idle: true`。**免责声明和伪造数据同时出现在一屏上,比单纯的假数据更糟**——它主动向用户承诺了数据是实时的。

后果(Codex 独立指出,核验成立):**用户按"在线 / 空闲 / 出纸正常"专程赶到点位,设备实际离线或缺纸 → 信任一次性崩塌**。打印是物理履约,用户白跑一趟的挫败远高于一次页面报错。

处理口径(**第一版必做,不可延后**):
- 真实数据接入前,这些状态一律**隐藏**,不是改成"未知"也不是留着标"仅供参考"——设备状态没有"参考"一说,要么真要么不显示
- 距离在 `getLocation` 接入前一律隐藏
- 到机码在真实 `pickupCode` 接入前一律隐藏(后端已有门控 `pickupCodeVisibleFor`,`member-print-orders.service.ts:5,103`)
- 接真后,状态必须来自 `TerminalHeartbeat` / `TerminalCapability`(`schema.prisma` 已有两张表),并显示**上报时间**;心跳超时即显示「状态未知」而非「在线」

原型阶段用 mock 本身是正常的,问题在于**切真的顺序**必须是「先隐藏 → 再接真」,不能出现真假混显的中间态。

### 4.5.5 主动触达:AI 主动开口的物理前提

§1.1 判据 ① 是「AI 主动开口」。核验结果:

| 层 | 现状 |
|---|------|
| 小程序 | ❌ `requestSubscribeMessage` 零处 |
| 后端 | ❌ 全仓无微信订阅消息 / 模板消息实现(`subscribeMessage` / `templateMessage` 零命中) |
| 站内通知 | ⚠️ 有 `MemberNotification`(`schema.prisma:1956`)与 `UserNotification`(`:2139`)两张表 |

**没有订阅消息,「AI 主动开口」只在用户已经打开小程序时成立——那不是主动,那只是首页做得好。**

真正的主动需要一条能在用户离开后触达的通道,微信生态里只有订阅消息。但它有一条硬约束必须写进设计:

> **微信订阅消息是「一次性订阅」** —— 用户授权一次只能发一条。长期订阅仅对政务、医疗等特定类目开放,本项目走生活服务 / 商业服务 / 打印类目,**拿不到长期订阅**。

因此设计上不能做成"推送中心",只能在**用户自然产生期待的时刻**请求订阅:

| 请求订阅的时机 | 用户预期 | 发出的那一条 |
|--------------|---------|------------|
| 提交 AI 诊断 / 优化任务 | "我在等结果" | 报告已生成 |
| 下单支付成功 | "我在等出纸" | 到机码可用 / 已出纸 |
| 材料包组装 | "我在等打包完" | 材料包已就绪 |
| 收藏招聘会 | "我怕忘了" | 活动前一天提醒 |

**这是合规且用户预期内的用法**,与"骚扰推送"有本质区别。每条订阅消息文案同样要过 §7.1 的恒定合规校验,且**绝不能推投递 / 预约类内容**。

## 5. tabBar 重构:AI 下沉为环境层,腾出的位置给对象

**核心改动:取消「AI」tab。** 理由见 §1.2 末段——AI 作为 tab 意味着用户必须先想到"我要找 AI",这与「AI 主动开口」直接矛盾。

**定稿为 4 个 tab**(2026-08-01 三模型评审后从 5 个收敛,理由见本节末):

| 现状 | 定稿 | 理由 |
|------|------|------|
| 首页 | **今天** | 不是入口墙,是 **AI 生成的任务主线**——打开即知道该做什么(判据 ①) |
| 打印 | **材料** | 打印是动作不是对象。这个 tab 装"我的求职材料"(简历 / 文档 / 材料包 / 到机码),打印是其上的动作 |
| 求职 | **发现** | 统一承载第三方岗位/招聘会/企业 + 微应用货架 |
| AI | ~~取消~~ | AI 下沉为环境层(见下) |
| 我的 | **我的** | 账户 / 权益 / 订单 / 记录 |

**AI 取消 tab 后去了哪:三个位置,覆盖率反而更高**

1. **「今天」页整页就是 AI 的输出** —— 任务主线由 AI 按真实状态生成,这是主动开口的主阵地
2. **全局常驻唤起点** —— 每页固定位置的小青入口(建议右下角悬浮,或复用导航栏右侧),随时可问,不占 tab
3. **页内嵌入式建议** —— 在用户当前正在做的事旁边给建议(如简历页给"这段经历可以量化"、打印页给"要不要一起打印证件照")

`pages/assistant/assistant` **保留为全屏深聊页**,只是不再占 tab —— 从悬浮入口、任务卡「问小青」、页内建议「展开细聊」三处进入。

原来 AI tab 下的工具网格不消失,归并进「发现」的微应用货架——本来它们就是 `ai_skill` 微应用。

**打印不会消失**,它变成材料页与任务卡上的「到机履约」动作——与差异化策略里的到机履约是同一件事,不是新概念。

**为什么从 5 个收敛到 4 个:** 原方案把「备面」单列一个 tab,理由是模拟面试 / 岗位匹配 / 职业规划已实现但埋得太深。这个理由站不住:**如果 AI 真的是环境层,「该练面试了」就应该由「今天」页主动推给用户,而不是等用户自己点进「备面」tab 去找。** 给它单列 tab 恰恰是承认了 AI 推不动——那就回到了本方案批判的"入口墙"模式。备面因此定为「今天」页的任务类型之一,同时在「发现」的微应用货架里可主动检索。

**tab 数收敛的另一收益:** 4 个 tab 时每个 tab 的宽度更大,触控目标更宽裕(小程序自定义 tabBar,需自行保证 ≥48px 可点区域,主操作 ≥56px)。

**与原型冻结的关系:** 小程序 57 屏原型**从未在微信开发者工具渲染过**(仅 Node 静态校验),属待验证草案,可按本方案重构。真正冻结的是 Kiosk 86 路由基准(`docs/design/kiosk-proto-2026-07/`)——**Kiosk 侧任何改动仍须先审查该基准**,本方案不触碰。

## 6. 最高杠杆的一处改动:给 manifest 加「投放面」

成本最低、收益最大的单点改造。现在 manifest 有 `entryType` 但没有「这个能力在哪些端可见」:

```ts
// packages/shared/src/types/toolboxMicroApp.ts —— 增量扩展,不破坏现有结构
export type ToolboxMicroAppSurface = 'kiosk' | 'miniprogram'

export interface ToolboxMicroAppManifest {
  // ...现有字段保持不变
  surfaces?: ToolboxMicroAppSurface[]          // 缺省视为 ['kiosk'],向后兼容
  launchBySurface?: Partial<Record<ToolboxMicroAppSurface, ToolboxMicroAppLaunch>>
}
```

**⚠️ 实施陷阱(已核验,必须同步改否则静默丢数据):**

`toolbox-governance.helpers.ts:48-83` 的 `normalizeSnapshot()` 是**显式白名单重建**,不是透传——它逐字段构造返回对象。`toolbox-governance.service.ts:227` 又用 `JSON.stringify({ ...snapshot })` 把归一化结果写进 `snapshotJson`。

因此只加 TS 类型字段是**无效的**:`surfaces` 会在归一化时被静默丢弃,类型上看起来支持、运行时永远读不到。改动清单必须包含:

1. `packages/shared/src/types/toolboxMicroApp.ts` —— 加类型
2. `toolbox-governance.helpers.ts` —— `normalizeSnapshot` 白名单加 `surfaces` / `launchBySurface`,并校验取值 ∈ `{kiosk, miniprogram}`(参照现有 `entryType` / `riskLevel` 的 `badRequest` 写法)
3. `NormalizedToolboxSnapshot` 接口同步扩字段
4. 缺省值 `['kiosk']` 保证**历史版本快照向后兼容**(老 snapshot 无该字段时不能变成"对所有端可见")
5. 新增 verify 断言:老快照 parse 后 `surfaces` 必须等于 `['kiosk']`

好消息:`parseSnapshot` 走 `JSON.parse` + 归一化,**没有 strict 模式拒绝未知字段**,所以扩展本身不会让历史版本 parse 失败——风险只在"静默丢弃",不在"报错"。

**⚠️ 投放目标设计(关键决策,直接关系熔断是否有效):**

小程序面**不要建第二张投影表**。核验 `suspendApp:364-395` 的熔断实现:

```
suspendApp = ① toolboxApp.status → 'suspended'(与端无关)
           + ② 遍历 terminalToolboxConfig 清除投影(仅覆盖终端)
```

若给小程序建一张 `MiniprogramToolboxConfig` 投影表,熔断的 ② 就**扫不到它**——应用已下架但手机上还能启动。这是安全漏洞。

正确做法:新增 `GET /api/v1/toolbox/miniprogram/apps`,**按 `toolboxApp.status === 'published'` + `surfaces ∋ 'miniprogram'` 实时查询**,不做预投影。这样熔断的 ① 自动生效,零额外扫描逻辑。

代价:每次请求要查库(可加短 TTL 缓存,但**熔断必须能立即穿透缓存**,建议 TTL ≤ 60s 或熔断时主动失效)。

配套:小程序侧做**一个**「微应用容器页」,由 manifest 驱动渲染。于是新能力上架 = 建 manifest + 审核发布,**不写小程序页面**,并自动继承审核发布、host 白名单、熔断下架、启动统计。

同时需要:`normalizeToolboxItemsForConfig` / `snapshotToKioskToolboxItem` 的 Kiosk 专用投影保持不变(不要为了复用而泛化,会牵动已进 CI 的 7 套 toolbox verify);小程序面走独立的轻量投影函数。

这才是「操作系统」区别于「一堆页面」的地方。

## 7. 交互内核怎么落地:四条判据的实现机制

§1.1 提了四条判据,这里给可实施的机制。**这是本方案与"再加 57 个页面"的真正分界线。**

### 7.1 ① AI 主动开口 → 「下一步引擎」

用户打开小程序,「今天」页首屏必须已经有答案。实现上**不是让模型自由生成**,而是规则优先、模型兜底:

```
真实状态输入(全部来自已有表,不需要猜)
  ├─ 简历:有无 / 上次诊断结果 / 距今天数        ← 见下方「取数注意」
  ├─ 资产:有无待打印文件 / 有无未组装材料包
  ├─ 订单:有无待到机履约的 pickupCode
  ├─ 权益:有无即将过期的权益
  └─ 行为:BrowseLog / ExternalJumpLog 最近浏览的岗位类型
        ↓
  确定性规则表(优先,可解释、可测试、零成本)
        ↓ 规则全不命中时
  模型生成兜底(带「AI 建议」标注)
        ↓
  「今天」页 1–3 张任务卡,每张带一个主按钮
```

规则表示例(应落成配置而非硬编码):

| 真实状态 | 主动建议 | 主按钮 |
|---------|---------|-------|
| 无简历 | 「先把简历放进来,后面都能用」 | 上传/扫描简历 |
| 有简历、无诊断 | 「花 1 分钟看看简历有哪些硬伤」 | AI 诊断 |
| 诊断分 < 70 | 「有 3 处可以马上改好」 | 简历优化 |
| 有待打印文件 | 「材料齐了,可以去服务点打印」 | 查看服务点 ⚠️**不带距离**,见下 |
| 有未使用 pickupCode | 「到机码还没用,到店扫码即可取件」 | 出示到机码 |
| 权益 7 天内过期 | 「有权益即将过期」 | 查看权益 |
| 全不命中 | 模型按最近浏览生成 1 条 | 视内容而定 |

**⚠️ 「看附近终端」这条本方案原先写错了(2026-08-01 核验修正):**

原表这一行的主按钮写的是「**看附近终端**」。核验后不可实现,需要两个条件,**一个都不满足**:

| 条件 | 现状 |
|------|------|
| 手机侧知道用户在哪 | ❌ `getLocation` 全仓零处 |
| 后端知道终端在哪 | ❌ `Terminal` 模型**只有 `locationLabel String?` 文本标签,无经纬度** |

所以第一版主按钮降级为「**查看服务点**」——只列点位名称与地址,**不显示距离、不显示"附近"、不排序**。想真正做「最近的」,分两档:

| 想做的 | 可行性 |
|-------|-------|
| 最近的**招聘会** | ✅ 今天就能做 —— `JobFair.latitude/longitude`(`schema.prisma:906-907`)已存在,注释就写着「场馆导航(生成手机扫码导航深链;无坐标时回退地址搜索)」。只缺手机侧 `getLocation` |
| 最近的**线下服务点** | ✅ 今天就能做 —— `OfflineAgency.lat/lng`(`schema.prisma:2073-2074`)已存在 |
| 最近的**一体机** | ❌ 需 schema 改动 —— 给 `Terminal` 加坐标,或建 `Terminal` → `OfflineAgency` 关联(当前两者**零关联**,`OfflineAgency` 有 `sourceOrgId`/`orgType` 但没有 Terminal relation) |

**⚠️ 取数注意(已核验,规则表落地前必须知道):**

「诊断分 < 70」这条**不能直接查列**。核验结果:

- 全 schema **零 `score` 字段**;`AiResumeResult` 只有 `payloadJson`(`kind` 仅 `'parse' | 'optimize'`,无 diagnose)
- 分数以 `ResumeSection[]` 形式存在 payload 内,是 **6 个维度各自的 `score`/`maxScore`**(`packages/shared/src/types/ai.ts:32-37`、`RESUME_SCORING_DIMENSIONS`),**没有汇总总分**

两种做法,**先做前者,后者等真有第二个消费方再做**:

| 做法 | 评价 |
|------|------|
| **✅ 先落这个:** 请求时读该用户最新一条 `payloadJson`,在内存里解析 6 维求和 | 单用户单条、非扫表,开销可忽略;**零 migration**,不阻塞 Phase 1.5;总分口径必须收敛成 `packages/shared` 里一个函数(如 `computeResumeOverallScore(sections)`),不许在 controller 里各写一遍 |
| 反范式加一列 `AiResumeResult.overallScore Int?`,诊断落库时一并写入 | 规则表可直接 SQL 比较,也便于做趋势图;但只有一个消费方时收益不抵一次 migration 成本。**触发条件:** 出现第二个消费方(趋势曲线 / Admin 统计 / 按分数筛选)时再加,并回填历史行 |

**不要误入的坑:** 看到"诊断分 < 70"就先开 migration 加 `score` 列。当前 schema 零 `score` 字段是事实,但这不等于"必须先加列才能做"——第一版用内存解析即可,把 migration 留到有第二个消费方时。

其余 6 条规则(有无简历 / 待打印文件 / pickupCode / 权益到期 / 浏览记录)都能直接查列,无此问题。**涉及的真实表名(已核对 schema):** `AiResumeResult:1307`、`FileObject:711`、`Order:198`、`BenefitGrant:1512`、`BrowseLog:1799`。

**合规硬约束(不可让"主动"越界):**
- 主动建议**只能推**简历/打印/材料准备/信息浏览/权益提醒
- **绝不能推**"去投递""帮你投递""要不要预约"——投递与预约永远是用户自己到来源平台完成的动作
- 建议必须基于**真实可查状态**;查不到就不显示该卡,不允许"看起来有内容"而编造(§9 不伪造能力)
- 模型兜底产出的卡必须带「AI 建议」标注
- **规则 7(模型兜底)的输出必须过服务端恒定合规校验后才能下发** —— 见下方专门说明

**规则 7 的合规校验:复用已有恒定守卫,不要新造一套**

模型兜底会产出自由文本,存在吐出"为你推荐 XX 岗位,帮你投递"这类撮合式文案的风险。仓库里已经有两套现成机制,选对那一套很关键:

| 已有机制 | 位置 | 能不能用在这里 |
|---------|------|--------------|
| `enforceForbiddenWords(reply, cfg.forbiddenWords)` | `services/api/src/ai/llm/llm-guard.ts:57` | ⚠️ **不够** —— 词表来自管理员可配的 `forbiddenWords`;`normalizeConfigForbiddenWords` 传空数组时不回落默认值,等于守卫可被后台关掉。主动卡片是系统自己开口,不能把合规底线交给后台配置 |

### 7.2 ② 意图直达 → 复用已有 `INTENT_ROUTES`,补三件事

地基已在 `llm-chat.service.ts:39-68`(意图正则 → 可点 route)。要补:

1. **入口前移** —— 唤起点从"AI tab"变成每页常驻 + 「今天」页顶部搜索/说话框
2. **意图接微应用** —— manifest 的 `assistantIntent`(`toolboxMicroApp.ts:165`,已有且 verify 强制校验)与 `INTENT_RULES` 打通,做到「说一句 → 直接进对应微应用」。**这是已有字段的兑现,不是新建机制**
3. **带参跳转** —— 现在 route 是裸路径,应支持携带意图参数直接到位。例:「打印我的简历」→ 落地页已预选好文件,而不是让用户再找一遍

**⚠️ 「复用 `INTENT_ROUTES`」的前置条件:路由命名空间不通(2026-08-01 核验,原方案漏了这一层)**

`INTENT_ROUTES` 的值全是 **Kiosk Web 路由**(`llm-chat.service.ts:39-46`):

```
resume → '/resume/report' / '/resume/source'      print → '/print/upload' / '/scan/start'
job    → '/jobs'        fair → '/job-fairs'       policy → '/renshi'
```

小程序用的是 `pages/xxx/xxx` 形式。直接 `wx.navigateTo('/resume/report')` **会失败**,而且失败得很安静——用户只看到点了没反应。核验补充:小程序 `utils/` 下 8 个文件(api / auth / config / favorites / history / mock-data / request / storage)**零意图 facade、零路由映射层**。

因此「复用 `INTENT_ROUTES`」不是拿来就能用,必须先补一层**按端解析的路由映射**:

| 方案 | 做法 | 评价 |
|------|------|------|
| **A(推荐)** | 在 `packages/shared` 维护 `intent → { kiosk, miniprogram }` 映射,后端按请求方 surface 返回对应路由 | 与 §6 的 `surfaces` 概念一致,一处定义两端消费;`launchBySurface` 已经是同一思路 |
| B | 小程序侧自建 Kiosk→小程序路径映射表,收到裸路由后翻译 | 快,但映射散在前端,Kiosk 改路由时小程序静默失效 |

**这是 1.5.4 的前置任务,不是可选优化。** 没有它,「意图直达」在手机上直接不工作。

### 7.3 ③ 步骤压缩 → 四个可量化手段

| 手段 | 做法 | 例子 |
|------|------|------|
| **预填** | 能从已有资产推断的默认值不问用户 | 打印默认选最新简历、默认 A4 单面黑白 |
| **批量** | 多个动作合并成一次 | 材料包一次组装、一次到机全部出纸 |
| **一次授权** | 同一目的的连续操作只确认一次 | 组包时一次确认,不逐份文件确认 |
| **异步化** | 耗时任务后台跑 + 完成通知 | AI 诊断/优化不阻塞用户,好了推通知 |

**验收方式:给每条核心链路定步数上限并写进 verify。** 例:
- 「上传简历 → 拿到诊断报告」≤ 3 步
- 「已有简历 → 生成到机码」≤ 3 步
- 「说一句话 → 进入目标功能且已预填」≤ 2 步

这条最容易被"加功能"悄悄破坏,所以必须量化成断言,而不是停留在口号。

**⚠️ 但断言放哪里要先想清楚(已核实,不能照直觉做):**

小程序源码在**独立仓库** `~/WeChatProjects/zhiyida`(独立 git repo,分支 `feature/miniapp-proto-pages`),不在本 monorepo 内。核实结论:

- 主仓 `services/api/scripts/verify-*.ts` **扫不到** `zhiyida` 的 `.wxml` / `.js`
- 主仓 verify 脚本与 `.github/workflows/` 里**零处**引用 `WeChatProjects` / `zhiyida`,即跨仓扫描无先例,不要假装能顺手做
- `packages/shared` 里**也没有**现成的声明式流程步骤定义(无 `FLOW_STEP_DEFINITIONS` / `FLOW_STEPS` 之类)可以直接借用

所以三个选项,按代价排序:

| 方案 | 做法 | 代价 / 风险 |
|------|------|-----------|
| **A(推荐先做)** | 断言写在 `zhiyida` 仓自己的 CI(或一个本地 `verify-steps.mjs`),主仓不管 | 最省;缺点是两仓门禁分裂,主仓 CI 绿不代表步数没退化 |
| B | 在 `packages/shared` 新建流程步骤声明(如 `MINIAPP_CORE_FLOWS`,每条含 `steps: string[]`),小程序页面跳转按它实现,主仓 verify 断言数组长度 | 能进主仓 CI;但**这是新建而非复用**,且小程序独立仓要能 import `packages/shared`(需发包或路径映射),Phase 1.5 阶段可能不值得 |
| C | 小程序并入 monorepo | 收益最大、代价最大,与"不做物理目录迁移"的现行口径冲突,**当前不做** |

**建议:Phase 1.5 走 A,把"步数上限"当成 `zhiyida` 仓的门禁;等小程序功能稳定、确实要长期守护时再评估 B。** 不要在方案里写"进 CI"就当已经解决了 —— 那是两个不同仓库的 CI。

### 7.4 ④ 优雅收尾 → 交付成品,不交付原料

- **AI 输出必须成品化**:排好版的 PDF / 可直接打印的材料包,而不是让用户复制粘贴文本
- **结论先行**:报告首屏一句话说清结论 + 最多 3 条可执行动作,细节折叠在后
- **可带走**:每个 AI 结果都要能进「我的文档」、能打印、能在一体机取到
- **视觉延续既有语言**:墨青纸感 / fusion-youth 已定版,不为"AI 感"引入炫技视觉;AI 生成内容一律带「AI 生成 / 仅供参考」标注

**与到机履约的关系(重要,别做反了):** 「最少步骤」指的是**手机端准备阶段**的步骤压缩,不是"绕开一体机让手机自成闭环"。正确形态是:手机把 20 步压到 3 步并生成到机码,用户到机扫码一次出纸——**手机压缩准备成本,一体机承担交付**。这与 §3 原则 3 一致。

**因此"成品化"必须配一条 UI 硬规则,否则会把自己的履约漏斗打穿:**

`docs/product/miniprogram-vs-kiosk-differentiation-strategy-2026-07.md` 的核心防线是「手机准备、一体机交付」,并明确指出最大战略误区是把小程序做成一体机等比缩小版 —— 若用户在手机上就能拿到与到店相同的结果,一体机会退化成低频普通打印机,固定成本(硬件 + 点位 + 耗材 + Agent 运维)无法被履约频次覆盖。

上面"AI 输出必须成品化""可带走"这两条,如果实现成手机端一个显眼的「保存 PDF 到本地」,客观效果就是鼓励用户回家自己打印。所以规则是:

| 界面 | 主 action(视觉主按钮) | 次 action(弱化) |
|------|---------------------|----------------|
| AI 成品预览页(简历/优化稿/规划书 PDF) | **生成到机码**(不写"附近",见 §4.5.4 陷阱一) | 存到「我的文档」 |
| 材料包组装完成页 | **生成到机码** | 存到「我的文档」 |
| 「我的文档」内某个文件 | **去终端打印** | 分享 / 另存 |

补充两点,避免这条被误读成"不给用户导出":

- **不禁止本地保存** —— 用户对自己材料的处置权不能剥夺,禁止导出既不合理也不合规友好。这里控制的只是**视觉权重与默认路径**,不是可用性。
- 本地保存不额外收费、不设障碍;差异化靠的是一体机能提供的、手机给不了的东西(即时出纸、装订、证件照、扫描原件、无需自备设备),不是靠阉割手机端。

反过来说:如果某个成品在手机上导出后用户完全没有到机需求(例如纯线上投递用的 PDF),那它本来就不属于一体机履约漏斗,不必强行往到机码上引 —— 强行引会变成噪音。**判断标准是"这份成品最终是否需要物理纸张",不是"能不能让用户多来一趟"。**

**0.1c 详解:微信身份与换绑的交互(2026-08-01 复审补充,本方案原先漏了)**

先说好消息——核验后,底座比预期扎实,**不需要新建换绑机制**:

| 已有能力 | 位置 | 评价 |
|---------|------|------|
| 会员手机号换绑**四步双验证** | `services/api/src/member-auth/member-phone-rebind.service.ts` | ✅ 旧号 step-up → 拿 `stepUpToken`(原子消费,一次性)→ 新号 SMS → 提交换绑 → **立即 `revokeMemberSessions` 踢掉全部旧会话**,且不自动签发新 token(强制用新号重登)。设计是对的 |
| 到机码可见性门控 | `payment/order-status.service.ts` 的 `pickupCodeVisibleFor`,由 `member-print-orders.service.ts:103` 消费 | ✅ 仅 `paid` 且未退款、非终态才返回码,否则 `null` |
| 合作机构侧换绑 | `auth/partner-phone-rebind.service.ts` | ✅ 同类机制 |

**真正的缺口:上面这套全部以 `phoneHash` 为锚点,而 `wxOpenId` 是一个新增的、并行的身份维度。** 引入微信登录后会出现三个此前不存在的问题:

| 风险 | 场景 | 处置要求 |
|------|------|---------|
| **换绑后 OpenID 悬挂** | 用户把账号换绑到新手机号,但 `wxOpenId` 仍指向原账号行 | 换绑事务里必须**一并迁移或清空 `wxOpenId`**;不能只改手机号 |
| **订阅消息错投** | 订阅消息发给 OpenID。若 OpenID 与账号绑定关系变了却没同步,通知会推给**上一个持有人**——内容是求职材料与订单状态,属敏感信息 | 发送前必须**实时校验 OpenID ↔ 账号绑定仍然有效**,不能用缓存的绑定关系;换绑即作废该 OpenID 的待发队列 |
| **一机多人 / 借号** | 同一微信登录过两个手机号账号,或家人共用微信 | `wxOpenId @unique` 约束 + 换绑时显式解绑,避免一个 OpenID 同时能进两个账号 |

落地口径:`wxOpenId` 的绑定与解绑必须**复用现有 step-up 机制**(不要新造一套验证),并写进换绑事务的同一个 transaction;换绑成功后除 `revokeMemberSessions` 外,还要**清理该用户所有待发订阅消息**。

1. **能力分工不越界**(§4.5.2)—— 手机永远不做物理出纸的替代品,不提供"电子件即终点"的暗示
2. **指标成对看** —— 「小程序 DAU」必须与「**到机完成率**」「**单台日均订单**」一起看。前者涨、后者不涨或下跌,说明方向错了,不是成功

## 9. 合规红线(OS 化最大的风险是叙事膨胀)

公司**无人力资源服务许可证**,以下不因「升级为操作系统」而放宽:

**⚠️ 命名必须内外分层(外部审查建议,已采纳):**

「操作系统」是**内部技术架构语汇**,不适合作为对外注册与宣传口径——微信小程序审核看的是"你提供什么服务",而"求职操作系统"极易被判入**招聘类目**,而我们**没有人力资源服务许可证**,一旦判入即驳回。

| 场合 | 口径 |
|------|------|
| 内部架构 / 本文档 / 代码注释 | AI求职操作系统、随身 Shell、OS 对象、微应用内核 |
| 微信小程序注册 / 类目提交 / 应用简介 | **AI求职打印服务**(与营业执照、已有定位一致) |
| 对外宣传 / 用户可见文案 | AI求职材料服务、简历与打印服务助手 |

- **任何场合都绝不能讲「招聘操作系统」。** 即便对内也不要用,避免文案顺手泄漏到 UI。
- 岗位 / 招聘会 / 企业只做**第三方与官方来源信息入口**。禁止平台内投递、代收简历、候选人筛选、面试邀约、Offer 管理、候选人推荐、自营招聘闭环。
- 按钮文案白名单:查看岗位 / 去来源平台投递 / 扫码投递 / 查看招聘会 / 去来源平台预约 / 扫码预约。
- 数据边界(CLAUDE.md §10):只记浏览 / 收藏 / 外部跳转 / 打印 / AI调用。**投递结果与预约结果永不记录**,不同步候选人数据。
- 微应用 8 项禁用能力表(`TOOLBOX_MICRO_APP_FORBIDDEN_CAPABILITIES`)继续生效;Phase 1 仍**禁止第三方代码执行**(JS / WASM / 插件)。「OS」不等于开放第三方代码市场。
- 微信类目:生活服务 / 商业服务 / 打印,**必须避开招聘类目**。

**⚠️ 但选对类目不等于安全(外部评审补充,本方案原先漏了):**

审核员看的是**功能实际内容**,不只是你勾的类目。「AI 简历诊断」「岗位匹配参考」这类功能,即使注册在打印类目下,**仍可能被要求补充人力资源服务许可证**——因为它们看起来在做求职撮合。这个风险独立于类目选择,不能靠选类目规避。

预案(提审前就要准备好,不要等驳回):

| 措施 | 具体做法 |
|------|---------|
| **首屏定位明确** | 应用简介、首屏、截图都以「材料准备 + 打印」为主叙事,AI 是加工工具而非撮合服务 |
| **岗位页自证为信息入口** | 岗位 / 招聘会页突出来源机构、同步时间、外部 ID、「去来源平台投递」——让审核员一眼看出这是导流展示,不是自营招聘 |
| **功能命名去撮合化** | 「岗位匹配」在用户可见处表述为「**岗位匹配参考**」并标注仅供参考;避免「智能推荐岗位」这类可被读成撮合的说法 |
| **准备说明材料** | 提前写一份功能说明:不收简历、不代投递、不做企业侧筛选,岗位数据均来自第三方授权来源 |
| **必要时分期提审** | 首版可只提"简历打印 + 材料服务",岗位 / 招聘会入口在通过后以更新方式加入,降低首审风险 |
- 不伪造能力:AIGC 标注「AI 生成 / 仅供参考」;无真实回流不显示已打印;无真实设备数据不显示设备正常。
- 变现不承诺求职结果(禁保面试 / 保录用 / 内推 / 代投);赞助方只获品牌曝光,**永不获得简历或投递数据**。

用户说「微信有备案,服务器也有备案」——**两句都成立,而且服务器侧的两项都已实证**。但「备案」在这里指的是**三件不同的事**,不能互相替代:

|---|---|---|---|---|

| **a2** | **⚠️ 用户隐私保护指引里声明「手机号」** —— 本轮新发现,原方案漏列 | 用户(需后台权限) | 分钟级;补充声明 5 分钟生效 |
| c | `utils/config.js`:`baseUrl: 'https://api.example.com'` → `'https://zyidai.cn'`,`USE_MOCK: true` → `false` | 我 | 一行改动,当天可做 |
| d | **`EndUser.wxOpenId` + 微信登录端点**(全 schema 零 `openid`/`unionid`) | 我 | 唯一真实剩余阻塞,即步 2 |

| **a3** | **确认小程序主体为非个人且已完成微信认证**;了解 `getPhoneNumber` 按次收费 | 用户 | 查询 |

**a2 详解:去掉一个假阻塞后,发现了一个真前置(2026-08-01 自查)**

`pages/launch/launch.wxml:14` 已经写了 `open-type="getPhoneNumber" bindgetphonenumber="onGetPhoneNumber"` —— 登录入口就靠它。但全仓**零处**隐私声明:`grep` `usePrivacyCheck` / `requirePrivacyAuthorize` / `onNeedPrivacyAuthorization` / `getPrivacySetting` / `openPrivacyContract` 全部无命中,`app.json` 也没有 `permission` / `requiredPrivateInfos`。

微信官方文档(`framework/user-privacy/PrivacyAuthorize`)原文:

> 「仅有在指引中声明所处理的用户信息,才可以调用平台提供的对应接口或组件。**若未声明,对应接口或组件将直接禁用。**」

未声明时的运行时报错是 `"errMsg": "A:fail api scope is not declared in the privacy agreement", "errno": 112`。另外 `__usePrivacyCheck__` 已在 2023-10-17 后失去开关意义 ——「不论 app.json 中是否有配置,隐私相关功能都会启用」,**不能靠不配置来绕过**。

**后果:** 如果只做 a + c 就切真,登录按钮会以 errno 112 静默失败,而现场表现会像「后端登录端点写错了」—— 排查方向完全被带偏。所以 a2 必须与 a 同批做完。

好消息是它**不是审批项**:官方文档写「补充的隐私类型声明,将在 5 分钟后生效」,量级与配域名相同。(首次填写指引是否另有审核,该页未说明,需看《用户隐私保护指引填写说明》;若后续要用定位 / 录音 / 相册,须在同一处一并声明 —— 与 §10.4 的四项手机独占能力直接相关。)

#### a3 `getPhoneNumber` 自身的三道门(第四轮复审促成,核验后全部成立)

登录按钮 `launch.wxml:14` 依赖 `getPhoneNumber`,而这个接口本身有三个原方案没写的约束(均已对官方文档核实):

| 约束 | 官方口径 | 对我们的影响 |
|---|---|---|
| **主体资质** | 「目前该接口针对**非个人主体,且完成了认证的小程序开放**」 | 个人号或未完成微信认证 → 登录路径根本开不了。这是**真正的资质门**,须与小程序备案一并确认 |
| **按次收费** | 2023-08-28 起「每次组件调用成功,收费 0.03 元」;每账号 1000 次**体验额度**,正式/体验/开发版共用 | 免费类目只含政府 / 非营利 / 事业单位+政务民生 / 公立医疗 / 学历教育 —— **我们走生活服务·打印类目,不在免费名单,要付费**。1000 次额度在真机联调期很容易被吃掉 |
| **额度耗尽的表现** | 用户点按钮时报 `e.detail.errno === 1400001`,并默认弹半屏提示 | 现场会表现为「登录突然坏了」。可用 `phone-number-no-quota-toast="false"` 关掉用户侧弹窗,但**问题不会消失** |

另有两条实现细节,直接影响步 2 的端点设计:

- **两个 `code` 不能混用。** `getPhoneNumber` 回调里的 `code`(5 分钟有效、只能消费一次)与 `wx.login` 的 `code` 是两套,分别换手机号和 OpenID。新方式「不再需要提前调用 `wx.login`」—— 但我们**同时要 OpenID**(`wxOpenId` 是 §0.0 的字段),所以两个调用都要保留,后端两次兑换不能互相顶替。仓库里 `utils/auth.js` 已有 `wx.login` 封装,不用重做,但端点要能分别接收。
- **服务端 IP 白名单。** `phonenumber.getPhoneNumber` 是服务端接口,需 `access_token`;若公众平台开启了 AppSecret 的 IP 白名单,生产出口 IP(`120.48.13.190`)必须在名单内,否则取 token 直接失败。这一条不配会表现成「后端登录端点写错了」,和 a2 是同一类误判陷阱。

> ⚠️ 未核实项:网上普遍称合法域名每月有修改次数上限(常见说法为每月 5 次)。两次检索均未拿到官方口径,**不作为事实写入**,但配置 a 时建议一次配全(request / upload / download 一并想清楚),避免反复改动踩到未知限制。

**为什么把「DevTools 首次渲染」和「删伪造设备状态」合并成一步(本轮新判断):**

原方案把它们分列为 0.4 与 1.0。核验后认为应合并:

- 54 页**从未在开发者工具渲染过**,只做过 Node 静态校验。删掉 `home.wxml:101/104`、`print-store.js:6-7`、`print-pickup.js:5` 之后必然留下空态,而**空态是否正确只能靠渲染确认** —— 分两步等于开两次 DevTools、做两次回归
- 删除动作本身零依赖、纯删除、不需要任何后端配合,和渲染排查天然同批
- 渲染过程必然发现更多问题(WXSS 兼容、组件缺失),这些和伪造状态都属于「上线前必清的既有债」,一次收干净

**但步 1 内部有严格次序(复审 Q2 补充,已采纳):**

复审指出合并会**丢失对照基线** —— 先删再渲染,出问题时无法区分「既有渲染缺陷」与「删除引入的回归」。这条成立,且是我漏掉的。步 1 内部必须是:

1. **先全量渲染 54 页并留证**(截图 / 报错清单),此时代码未动 —— 这是基线
2. **再删 4 处伪造状态**
3. **只对受影响页复渲染**(`home` / `print-store` / `print-pickup`),与基线对比

第 3 小步只覆盖受影响页,不是再来一次全量 —— 既保住基线,也不放大范围。

### 10.3 一处自我修正:交互内核不能与 Phase 1 并行

方案 §8 原写「Phase 1.5 建议与 Phase 1 并行」。**这条是我写错的,现在推翻。**

下一步引擎的全部价值在于**读真实状态、给真实建议**。而它要读的状态里,最关键的一项(订单 → 到机码 → 出纸)正是步 4 才打通的。在步 4 之前接线,会出现这种输出:

> AI 建议:「你的文件已就绪,去取件」——而到机码是 `print-pickup.js:5` 里那个硬编码的假码。

**这比不给建议更糟。** 不建议只是功能缺失,建议了却指向假状态是伪造能力(违反 CLAUDE.md 不伪造能力红线),而且是 AI 主动说出口的伪造 —— 比页面上静态显示假状态更严重。

修正后的口径:**规则表可以先写**(纯配置、零成本、可评审),**接线必须等步 4**。这与 §8 约束一「不要在 mock 数据上重构」是同一条原理,只是从信息架构延伸到了 AI 输出。

### 10.4 六步做完之后仍然不成立的事(第三轮复审 Q3,核验后成立)

复审的第三问最有价值:**六步全部按序完成,最可能的失败形态是「工程闭环完成,用户价值没闭环」** —— 数据变诚实了、能登录了、履约跑通了,但仍然是个「更诚实的网页壳」。核验后**这条成立**,而且比它说的更具体:

| 手机独占能力 | 六步做完后的状态 | 为什么 |
|-------------|----------------|--------|
| 订阅消息 | ❌ 仍为零 | 明确排在六步外(等模板审批) |
| 定位 | ❌ 仍为零 | `Terminal` 无坐标已推迟(§10.5) |
| 扫码 `wx.scanCode` | ❌ 仍为零 | **核验发现:履约流程里手机是被扫方,不是扫方。** `print-pickup.wxml:20` 写「一体机上「扫码取件」对准此码」—— 手机只负责**展示**码,Kiosk 扫。所以到机码闭环做完,`wx.scanCode` 依然用不上 |
| 麦克风 | ❌ 仍为零 | 六步中无任何环节涉及 |

也就是说:**四条判据里的 ①「AI 主动开口」在六步做完后仍不成立**(§8 Phase 1 已单独承认过这一点,此处是它的完整代价 —— 不只是判据 ① 缺失,而是四个独占能力**一个都没落地**)。

**这不改变六步的顺序,但改变对它的预期定位:六步是「让 OS 有资格开始」,不是「OS 建成」。** 它交付的是诚实的数据、可用的身份、跑通的履约 —— 这三样是地基,不是差异化本身。真正的差异化(§4.5.3 融合矩阵)全部排在六步之后。

必须把这一点写在前面,否则六步交付时会出现最坏的一种误判:**以为 OS 已经做完了。**

**顺带核出步 4 的一个未列依赖:** 小程序**没有任何二维码生成能力**(全仓零 `createCanvasContext`、零 qrcode 库;`print-pickup.wxss:10` 的 `pf-qr` 只是一个虚线框加图标字形)。到机码要能被 Kiosk 扫,必须真的生成可扫码图 —— 这项不在原 1.3 描述里,须补进步 4。

**这四项还各自有一道隐私声明门(§10.1 a2 的延伸):** 定位(`chooseLocation` / `getLocation`)、录音(麦克风)、相册等都属隐私接口,**未在「用户隐私保护指引」声明即直接禁用**(errno 112)。所以后续启用任何一项,除了写代码,还要回公众平台补声明。这不构成额外阻塞(补充声明 5 分钟生效),但会在「代码写完却调不通」的时候造成误判 —— 提前记在这里。

### 10.6 三个最容易毁掉整轮价值的点

不是难点,是**做错一次就难回头**的点:

1. **订阅消息的第一条**。一次性订阅只有一次机会,首条推软提醒或营销 → 用户关授权 → 通道永久报废,且长期订阅只对政务/医疗类目开放,**没有第二次机会**。第一条必须是用户正在等的结果(§4.5.5 四个正当时机表)
2. **`normalizeSnapshot` 是白名单重建**。加 TS 字段不改白名单 = 字段静默丢失,不报错、不告警,只是数据没了
3. **AI 主动开口的文案必须过恒定词表**。`enforceForbiddenWords` 是管理员可配的、可被空数组关掉;系统主动发起的文案只能用 `DIAGNOSIS_GUARD_TERMS` 那种**常量表 + 命中即丢**的口径(§7.1 规则 7 兜底)

### 10.7 这份顺序的不确定性

**步 1 之后的一切估算都是估算。** 54 页从未渲染过,渲染结果可能推翻步 1 的工作量判断 —— 如果发现大面积 WXSS 兼容或组件缺失,步 1 会膨胀,后续顺序不变但排期要重估。这是唯一诚实的说法,现在给不出工时。

## 11. 一句话结论

**治理内核已经建完了(百宝箱),交互内核几乎为零——而用户能感知到的"操作系统"全在交互内核这一侧。**

**而小程序目前技术上就是一体机的缩小版:81.1% 的 `wx.*` 调用是导航和 toast,手机最值钱的四个能力——定位、订阅消息、扫码、麦克风——一个都没接。**

**执行顺序见 §10。原先我把「备案域名 + 微信主体资质」写成唯一的日历阻塞 —— 这个前提是错的,已在 §10.1 更正:`zyidai.cn` 早已备案、上 HTTPS、在标准 443 上真实提供 API。因此没有审批等待期,工程侧六步全部可以立刻开始;需要你的只剩两个分钟级后台动作(加 request 合法域名、确认小程序备案状态)。**

所以真正要做的四件事:

1. **先停止伪造**(Phase 1.0:删掉「出纸正常」「● 在线」「机器空闲」这些硬编码的设备结论——这是当前唯一的合规违规,且是纯删除)
2. **让小程序能上线**(Phase 0:`EndUser` 加微信身份字段 + 登录端点 —— 域名已备好,这一步现在是纯后端工作量)
3. **让能力有处可落**(Phase 1:到机码闭环 —— 手机准备、到机交付这条唯一的物理差异化链路先跑通)
4. **让 AI 能开口**(Phase 1.5 下一步引擎 + 「今天」页让 AI 在用户打开时说话;订阅消息让 AI 在用户离开后还能说话——后者以第 3 步为前置,但不阻塞它)

一句话:**OS 的演进不是再加 57 个页面,而是让用户不必知道有哪 57 个页面。**

而小程序独立存在的理由,只有一句:**它是唯一能在用户离开之后还继续替他推进求职的那一端。** 一体机做物理履约,手机做主动、私密、随身的那部分——不是把一体机搬到手机上。
